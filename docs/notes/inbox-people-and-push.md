# Chats tab, inbox, people, direct conversations and push

> The Chats tab and inbox, direct invites, profiles and direct conversations, push notifications and the pending Apple Developer account steps. Moved out of `README.md` and `CLAUDE.md` on 2026-10-17 and kept as written. The reference part describes the feature as the README did; the dated notes record decisions, lessons and the evidence behind them, newest last, so an older sentence can be superseded by a later one or by a marker such as "(removed 2026-10-14)". Read this file before touching the area; the rules that apply everywhere are in `AGENTS.md`.

## Reference (from the README)

- People: every person named in the app opens a profile (their initials, their name, a "Message" button and the groups you have in common, each row opening the group); the event detail lists who is in under "Who's in" (the host first, with a "Host" chip; your own row says "You"), its "Hosted by" line links to the host, a public group's Members segment is readable by any signed-in user, and a sender's name or avatar in a chat opens them. "Message" opens a direct conversation, which is a two-member private group named after the person, listed on the Chats tab as a person row ("Direct message") and never among your groups on Home; see [People](#people).
- Push notifications for game reminders are built end to end (app, backend, infrastructure) and verified on the simulator, but **cannot deliver until the Apple Developer Program account exists**; see [Pending: Apple Developer account](#pending-apple-developer-account) for the exact steps that remain.

### Pending: Apple Developer account

Everything for push reminders is in place except Apple's side (2026-10-02). Until then Laurel logs `APNs key not configured; pushes are logged only` at start and writes the reminder to the inbox alone, and a debug build on the simulator logs `Device registration failed: refused("no valid “aps-environment” entitlement string found for application")` when it is not signed with a team. Once the account exists (USD 99/year), in this order:

1. **Apple.** Enrol at developer.apple.com. Certificates, Identifiers & Profiles: register the App ID `iris.lily` with the **Push Notifications** capability; Keys, "+", enable **Apple Push Notifications service (APNs)**, download the `.p8` (shown once) and note its **Key ID** (10 characters) and the account's **Team ID** (Membership page).
2. **rose** (`/Users/makshr/rose`, README first-time setup step 10): put the three values into the secret named by the `RosePushStack` output `ApnsSecretArn`, then restart the service so the task reads them:
   ```
   aws secretsmanager put-secret-value --secret-id <ApnsSecretArn> --secret-string \
     "$(jq -n --arg t <TEAM_ID> --arg k <KEY_ID> --rawfile p AuthKey_<KEY_ID>.p8 '{teamId:$t,keyId:$k,privateKey:$p}')"
   aws ecs update-service --cluster lily-cluster --service laurel --force-new-deployment
   ```
   Laurel then logs `APNs push enabled for topic iris.lily` at start. Repeat the first command after any deploy that changed the secret *resource* (it writes the blank placeholder back).
3. **Lily.** In Xcode, Signing & Capabilities of the `lily` target: set the team. The Push Notifications capability is `lily.entitlements` (repository root, `aps-environment` `development`; Xcode switches it to `production` for an App Store or TestFlight build), which only the Release configuration signs with; the Debug configuration signs with `lily.debug.entitlements`, which carries no capability, so a personal (free) Apple ID team can run a debug build on an iPhone (personal teams cannot provision Push Notifications, and Xcode answers "Cannot create a iOS App Development provisioning profile" and then "No profiles for 'iris.lily' were found"). A debug build never receives a push for that reason; it logs the refused registration and carries on. To test push on a device with a paid team, add `aps-environment` `development` to `lily.debug.entitlements`. Nothing else changes in the project.
4. **Try it.** Debug build on a real iPhone (a simulator gets a token only on Apple silicon with a signed build; `xcrun simctl push` still works for the banner itself), sign in, join a game that starts in one to two hours (the prompt comes up on entering the app), lock the phone, wait for the sweep. Laurel's log shows `Push reminder-<eventId> to user <sub>: 1 of 1 devices`.
5. Optional follow-ups once this works: pushes for invites and chat messages (one `PushNotifier.notify` call each in Laurel), badge counts, Sign in with Apple on the same account.

### Chats and inbox

The Chats tab (debug builds, behind `AppConfig.FeatureFlags.chat`; bar order Home, Explore, Chats, Profile) lists every conversation: the **inbox** pinned first, then the caller's rooms, group rooms and direct conversations together, most recently active first (`SportGroup.mineOrder`, the backend's `MINE_ORDER`: by the last message, a silent room by its creation, ties by name; a room the device adds itself, a joined group or a new conversation, is inserted where a reload would place it), each with an unread dot (a conversation is a person row: the other person's initials in the accent, their name, "Direct message") and a context menu on long press whose one item clears the chat for the caller ("Clear chat" for a group, "Delete chat" for a conversation; see [Groups](groups.md#groups)); a guest sees the sign-in prompt instead, and nothing is requested for them. The tab's badge counts the rooms with unread messages plus one while the inbox holds something unseen (`unreadCenter.count + (inbox.hasUnread ? 1 : 0)`); Home rows carry no dots, because they open the group's detail, not the room.

- **The inbox** is one conversation titled with the app's name ("iskra") whose rows are system cards: an **invite** ("**Noor** invited you to **Climbing Buddies**", the group's visibility, Accept / Decline while it is pending and not expired, afterwards "You joined", "Declined" or "Expired") and a **game reminder** ("Game reminder", the game's title, its place, when it starts as the day, the clock time and the distance ("Today, 6:30 PM · in 58 minutes"), "Hosted in <group>" for a grouped game; the whole card opens the game's detail). Accepting is `POST /api/me/inbox/{id}/accept`, which answers the item and the group with the caller's membership; the group goes into Mine at once and its chat opens; a repeat on an accepted invite answers the same shape. Declining is `POST .../decline`. Opening the inbox marks it read (`PUT /api/me/inbox/read` with the newest item's id; the backend keeps the marker monotonic), and so does an item that lands while it is open. Verdicts on an invite (`INVITE_NOT_PENDING`, `INVITE_EXPIRED`) reach the popup and reload the inbox, so the card shows what the backend has.
- **Where it comes from.** `GET /api/me/inbox?limit=50[&before=<id>]` pages by ULID (ids sort as time, so an ascending page's last item is the newest); `InboxStore` (`Features/Inbox/State`, app-lifetime, a `SessionObserver` cleared on sign-out) is the one source for the Chats row's caption, the badge and the inbox screen, loaded on the shell sync (launch, foreground, sign-in) and on the Chats tab with the one staleness rule of every cached list (`AppConfig.Lists`: fresh for 60 s, no retry for 10 s after a failure; `StoreLoader` runs it, one request at a time per user, dropping an answer for a previous caller), with "Load earlier" fetching the page before the oldest item (a page whose anchor moved meanwhile is dropped and asked again). A live `inbox_item` on `users/<sub>` (once the realtime connection exists) goes through `InboxStore.apply`. A kind this build does not know decodes and stays hidden (no card, no dot, no badge), so a newer backend cannot break the page; the reminder captions ("Today, 12:00 · in 1 hour") are judged from the view model's clock, not the wall clock.
- **Reminders** are written by the backend one hour before a game starts, one per participant (host included), into the inbox, and since 2026-10-02 also **pushed** to the user's registered devices through APNs, so a reminder reaches a phone whose app is closed. A game created less than an hour ahead gets none.
- **Push notifications** (`Core/Push`). A signed-in user entering the app (launch with a restored session, or a sign-in) is asked for the notification permission once, as the shell appears (`PushCoordinator.offerReminders()` from the root view's sync; the system prompt, no pre-screen), and again after the first successful join or create should that ask not have happened (`PushOptIn.offerReminders()` from `EventDetailViewModel` and `CreateEventViewModel`); the system remembers the answer, so no later call shows anything. Guests are never asked: reminders need an account. While the permission is granted, every shell sync of a signed-in user (launch, foreground, sign-in; `ShellSync`, last in its order) runs `PushCoordinator.sync()` (concurrent syncs join one registration): `registerForRemoteNotifications` through `SystemPushRegistrar` (answered by `LilyAppDelegate` through `PushEventRelay`, with a 10 s timeout), then `PUT /api/me/devices` `{token, platform: "ios", environment: "sandbox" | "production" (by build configuration), appVersion}` when the token or the user changed or the last registration (kept in `UserDefaults`) is a day old. A sign-out awaits a registration still in flight (never cancelling it: a cancelled PUT may have landed) and then sends `DELETE /api/me/devices/{token}` for every token the device may hold (the one known before and the one that registration stored, two when it rotated) **before** the session flips (`SessionObserver.sessionWillEnd()`, awaited by `SessionController.signOut()`), so the Bearer still goes out; the whole waits `AppConfig.Push.unregisterTimeout` (3 s) at most (`Deadline.within`), since the row expires on the backend and another account registering the token takes it away. The backend's payload carries `kind: "event_reminder"` and `eventId`, or `kind: "match_reminder"` with `tournamentId`, `matchId` and `inboxItemId`; a tap (`LilyAppDelegate`, `userNotificationCenter(_:didReceive:)`) becomes a `PushTap` (`.event` or `.match`, ids only) and opens the game through `EventOpener` (the inbox's reminder card uses the same) or the tournament with the match's sheet up through `TournamentOpener`, on the Chats stack, or Home while chat is off; a tap that launches the app waits for the session restore (`PushCoordinator.pendingTap`). A reminder that arrives while the app is open shows as a banner too. Failures (no entitlement on a simulator, no network, a refused registration) are logged under `push`, never shown, and the device token never reaches a log line (the route is logged as `/api/me/devices/<token>`). `lily.entitlements` at the repository root carries `aps-environment` (`CODE_SIGN_ENTITLEMENTS` in both configurations); pushes need an Apple Developer Program team on the target and the APNs key in rose's secret (its README, first-time setup step 10). `-mock-events` swaps in `MockPushRegistrar` (grants without a prompt, a fixed token) and `MockDeviceRepository`, so the UI tests never meet the alert.
- **Mocks.** `-mock-events` serves four inbox items, oldest first (Noor's invite into her private Padel Open tournament, a reminder for "Sunset 5-a-side" starting an hour after launch, a match reminder for the caller's scheduled table-tennis match against Dev, then Noor's invite into the private Climbing Buddies, which nothing else reaches; see [Tournaments](tournaments.md#tournaments) for the two tournament kinds), remembers the read marker and the answers for the run, and computes invite candidates from the fixture rosters and game hosts: for Sunday Padel Crew they are Aiko, Ayşe, Dev, Jonas, Marta, Noor and Sam (its own members and its banned Priya are out), and inviting one of them marks the row "Invited" for the run.

### People

Every person the app names can be opened (2026-09-29): roster rows, event participant rows, the host line on an event and a sender's name or avatar in a chat push `UserProfileDestination(userId, displayName, context)`, which every stack root registers through `.groupDestinations` (`context` is `.fromChat` when a conversation's info button or the other person's bubbles push it, and that profile then offers no "Message" back into the room it came from); the caller's own rows say "You" and are not links, and guests are never offered one (names are members-level information, like a roster).

- **Profiles.** `GET /api/users/{userId}` answers `UserProfile {userId, displayName, sharedGroups: [GroupSummary {id, name, visibility, type?, memberCount}]}`: the person's current display name and the live groups both are in, sorted by name (the caller's own id answers their own groups). `UserProfileView` shows the initials, the name (also the inline title), a prominent "Message" button for anyone but the caller (not on the profile a conversation's info button opens, though: that chat is one Back away and the button would only push it again) and "Groups in common" as rows that open the group's detail (through the `EventGroupRef` destination, since a summary is not the whole group); "No groups in common yet" when there are none, a retry when the load failed (the popup says why: "Couldn't load this profile"); the reload the screen runs on the way back from a pushed group keeps the profile on screen. `UserRepository` (`Features/People/Interfaces`) is the seam, `RemoteUserRepository` and `MockUserRepository` (profiles from the fixture rosters: a person is whoever any roster names, the groups in common are the caller's groups whose roster names them) the implementations, `UserProfileViewModel` the screen's flow.
- **Direct conversations.** A conversation with a person **is a group of kind `direct`**: `SportGroup.kind` (`GroupKind`, `group` or `direct`; a payload without the field, older fixtures and samples included, reads as `group`, and a value this build does not know is kept as `unknown(name)`: such a room stays on Chats, is no community and offers chat and the roster only, no group actions) and `counterpart {userId, displayName}` (the other person, as the caller sees them) are the only additions, and the other fields are fixed by the backend: `name` = the person's display name (so every screen that shows the name shows the person), private, two of two members, `channelEpoch` 1 forever, both permissions off, `member` on both sides. Everything chat already does (history, sending, read markers, unread, realtime rooms, blocks, deleting your own messages) therefore applies unchanged, and the room is a `ChatView` titled with the person, without a member count, whose info button opens their profile instead of a group detail. "Message" lives on a profile (`POST /api/conversations {userId}`; idempotent, one id per pair, so a repeat answers the same room and `TRY_AGAIN` is repeated once): the conversation goes into Mine at once and its chat opens on the Chats tab. What a conversation cannot do, on the device (`GroupAccess.conversation`: chat and the two-person roster only) and on the backend (`403 FORBIDDEN`): be edited, deleted as a group, left, invited into, given roles, or host a game; "Delete chat" (the room's menu, or a long press on its Chats row) is the per-side way out: the conversation leaves the caller's Chats tab and returns, without the old messages, when either side writes again. **Chats versus Home:** `MyGroupsStore.groups` holds everything and feeds the Chats tab (a conversation is a person row captioned "Direct message", the accent avatar of every single person), the unread set and the realtime rooms; `MyGroupsStore.communities` (kind `group`) is what "your groups" means on Home, in the event form's Group picker and in the invite sheet, so a conversation is never a row there, never a group in common on a profile and never a place to host a game. A conversation the other side starts arrives on `users/<sub>` as a `membership_changed(joined)` for a room Mine has never seen, which only reloads Mine. Refusals with copy of their own: `USER_NOT_FOUND`, `CONVERSATION_LIMIT` ("You have too many conversations", the cap `AppConfig.People.maxConversations` = 200), the terms gate, the rate limit; anything else is "Couldn't start the conversation". The mock ships one conversation, with Marta (`mock-dm-mock-user-marta`: six lines, her last three unread, so the Chats tab shows a person row with a dot from the start), and creates `mock-dm-<userId>` for anyone else, so the room, Mine and the Chats tab treat it like any group.
- **Who's in.** `GET /api/events/{eventId}/participants` answers `{items: [EventParticipant {userId, displayName, joinedAt, isHost}]}`, the host first, then by join time, never paged, for signed-in callers who may read the event; the detail lists them under its facts (`EventDetailViewModel.participants`, loaded on appear and again after a join, a leave or the refetch that follows a refusal), each row a link to the person's profile with a "Host" chip on the host's, the caller's own saying "You". The host line under the title links to the host's profile when the host's id is known and the caller is signed in and not the host. The mock lists the fixture's host, then `participantCount - 1` deterministic roster names, then the caller as "You" when they joined.
- **Roster.** A public group's Members segment is open to every signed-in user (see [Groups](groups.md#groups)); every roster row but the caller's own opens the person's profile. Only a row the caller may act on carries a context menu.
- **Statistics.** No client kind is recorded for a profile view: Laurel's `InteractionKind` has no `PROFILE_VIEWED` and refuses kinds it does not mark client-reportable, and `Interaction` has no column for the target user, so the plan's "skip it if it needs a column" applies.
