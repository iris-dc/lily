# Build, tests, CI and the simulator

> ci.sh internals, shards, the test gate, simulator and XCUITest lessons, screenshot and recording recipes, the CI runner's flakes and what fixed them. Moved out of `README.md` and `CLAUDE.md` on 2026-10-17 and kept as written. The reference part describes the feature as the README did; the dated notes record decisions, lessons and the evidence behind them, newest last, so an older sentence can be superseded by a later one or by a marker such as "(removed 2026-10-14)". ## Reference (from the README)

`-skipPackagePluginValidation` is needed by every `xcodebuild` call (the README's build command and `ci.sh`) because Amplify pulls in `smithy-swift`, whose build plug-in `xcodebuild` otherwise refuses to validate without an interactive approval; Xcode asks once in the IDE.

The `ui` and `ui-ipad` stages pick a simulator for you (lazily: `lint`, `archive-products` and `restore-products` never call `simctl`, so they run on a Mac whose runtimes are unavailable, and the `Xcode:` and `Destination:` lines print once, by the first stage that runs `xcodebuild`; `XCODEBUILD_DESTINATION` overrides the pick), and both test stages pass `-parallel-testing-enabled NO`: simulator clones intermittently failed to launch the UI test runner, and for the unit tests a clone made the suite take minutes on a loaded CI runner where it otherwise finishes in seconds; a hand-typed `xcodebuild ... test` would run without that flag. A test stage passes only when its log shows a passed test: it fails with "no tests were executed" when none shows and with "every test was skipped" when the last `Executed N tests, with M tests skipped` line has N == M (`LilyIPadTests` alone on an iPhone), because `xcodebuild` exits 0 and prints a passing suite when `-only-testing` matches nothing; `ci.sh lint` self-checks that gate over five fixture logs.

Tests use Swift Testing and fakes for every interface (`lilyTests/Support/TestDoubles.swift`, with fixtures in `TestFixtures.swift` (`SportEvent.fixture`, `EventDraft.fixture`), the scriptable `FakeEventRepository.swift` beside them (it can hold requests open and turns a created draft into a hosted, joined event) and the API client fakes and contract samples in `NetworkingDoubles.swift`; `makeEventListViewModel(...)` builds a list view model over fakes and `settle(until:)` / `settle(untilAsync:)` yield until a condition holds, bounded). Every fake that can park a request does so through the shared `HoldsRequests` protocol over `RequestHold` (`Support/RequestHold.swift`: `holdsRequests`, `releaseRequests()`), calls are recorded as `Recorded<Value>`, and `SpyLogger` (`Support/SpyLogger.swift`) is asserted by count plus fragments (`count(in:at:)`, `hasLine(in:at:mentioning:)`, `lines(...).mentioning(...)`), never by whole sentences; `ScriptedAttempt` counts how many tries a repeat cost; `EventDetailHarness`, `CreateEventHarness`, `GroupHarness`, `RealtimeHarness`, `TournamentHarness` and `PushHarness` build the view models over the fakes (one `TermsCountingReporter` serves them all); `LocationDoubles` holds the location fakes, `TestFixtureFiles` is the one bundle lookup for `lilyTests/Fixtures`, `makeSignedInMockDependencies(extraArguments:)` builds a signed-in mock composition root, `TestDefaults` removes its `UserDefaults` suite and `StubBackend` its handler when the test ends, and `AppErrorCases` lists every `AppError` case (a new case fails to compile until listed). `SendFailingWithTests` proves `send(_:failingWith:)` once and `BackendErrorCodeTests.everyCodeMapsToItsCase` holds the one code-to-case table, so a repository suite pins only its route-specific codes; `ReleaseAfterCancelTests` pins that the chat view model, the realtime controller, the Discover view model and the session controller are released after cancel or sign-out.

The UI classes are grouped into shards of similar running time in `UI_SHARDS` in `scripts/ci.sh`; `ci.sh lint` fails when a test class under `lilyUITests/` (any class deriving from `LilyUITestCase` or `XCTestCase`, whatever its name) is in no shard (or in two), when `LilyIPadTests` is in one (it would only skip itself on an iPhone) or the workflow's `shard:` matrix does not list every shard, so a new test class has to be placed before CI goes green.

Linting uses [SwiftLint](https://github.com/realm/SwiftLint) (`brew install swiftlint`) with the rules in `.swiftlint.yml`; CI runs it in strict mode, so every warning fails the build, and pins the release (0.65.1, downloaded from GitHub's `portable_swiftlint.zip` and verified against `SWIFTLINT_SHA256`; both values sit in the workflow's top-level `env:` and change together), because a release's newly default-on rule would otherwise turn the gate red with no code change; `ci.sh lint` prints `SwiftLint <version>` and fails on a mismatch only when `SWIFTLINT_VERSION` is exported, so a developer Mac lints with whatever brew installed. Lint also runs `python3 -I scripts/test_l10n_check.py` (the catalog checker's own unittest suite) before `scripts/l10n-check.py`, the shard check and the test-gate self-check.

GitHub Actions (`.github/workflows/ci.yml`) runs on every push and pull request to `main` on `macos-26` runners in two stages. The `build-and-unit` job selects the newest Xcode 26 (and hands it to the UI jobs as the job output `developer_dir`, which they take as `DEVELOPER_DIR`, failing loudly when that Xcode is not on their runner instead of picking another), installs the pinned SwiftLint release into `$HOME/.swiftlint` ahead of the image's brew copy, runs `scripts/ci.sh build-and-unit` (lint with the string-catalog and shard checks, one build for testing, the unit tests without rebuilding) and archives the simulator products and the `.xctestrun` as a tar (`ci.sh archive-products`; a tar because `upload-artifact` stores every file as 644 and the apps would not launch). Then a matrix of `ui-tests` jobs, one per shard (`1` to `4` on the iPhone, each about 18 minutes of tests on the runner, `ipad` for `LilyIPadTests` on an iPad; both simulators are arm64, so one build serves all; the UI jobs may run 60 minutes, since a constrained runner once took a 34-minute shard past 45), restores the archive (`ci.sh restore-products`) and runs `scripts/ci.sh ui-shard <shard>` through `xcodebuild test-without-building -xctestrun`, which needs neither the project nor a package resolution. Every UI stage first warms the simulator up (`warm_up_simulator`: boot, install the built app, launch it once with the mock arguments, terminate) and runs one throwaway XCUITest session (`warm_up_test_session`: the family's landing test, verdict printed and ignored), because on a cold runner the first XCTest launch of a shard timed out at 60 s and the iPad's first accessibility queries did the same, both before any assertion; the device is resolved once as a UDID (the newest runtime's), so the warm-up and xcodebuild share it (resolved twice by name they once booted two iPads on a runner with two runtimes). A shard retries a failing test once (`-retry-tests-on-failure -test-iterations 2`) and names every test that passed only on the retry, so a cold runner's launch timeout does not fail the run and a flake still shows in the log; local `ui` and `ui-ipad` runs never retry. Run as one job the suite had outgrown the 45-minute job limit; each job keeps that limit, and the result bundles of every job are uploaded as artifacts (`test-results-build`, `test-results-ui-<shard>`). The runner needs Xcode 26.5 or newer, the same minimum as the README's "Run it" section. The workflow declares `permissions: contents: read`. Every `uses:` in the workflow is pinned to a commit SHA, with the release tag it was resolved from in a trailing comment; Dependabot (`.github/dependabot.yml`, `github-actions`, weekly) proposes the bumps as one grouped pull request, so a week's updates cost one CI run.

To run on the mock auth service, launch with `-mock-auth`; add `-mock-auth-fail` to make every auth call fail and see the error popup, or `-mock-auth-confirm` to walk the confirmation step with the code `123456` (previews can use `AppDependencies.makeMock(authBehavior: .fail(.network))` or `.requireConfirmation(code:)`). Without any of them the app talks to the real pool.

## Dated notes

- **Build and test with `./scripts/ci.sh [lint|build|unit|ui|ui-ipad|all]`.** SwiftLint runs in strict mode from `.swiftlint.yml`; fix violations rather than disabling rules. It picks a simulator, writes logs and `.xcresult` bundles to `build/results/`, and `all` runs locally what GitHub Actions runs across jobs (lint, one build for testing, both test bundles without rebuilding, then the iPad class on an iPad). Since 2026-10-09 CI is two stages (`.github/workflows/ci.yml`): `ci.sh build-and-unit` on one runner (lint, build-for-testing, unit; then `archive-products` tars `build/DerivedData/Build/Products/{Debug-iphonesimulator,*.xctestrun}` into `build/products.tgz`, 84 MB, because `upload-artifact` drops executable bits) and a matrix of `ci.sh ui-shard <1|2|3|ipad>` jobs that `restore-products` and run `xcodebuild test-without-building -xctestrun` (no `-scheme`, no package resolution). The one 45-minute job had been outgrown: the UI suite alone takes 22 minutes on a developer Mac (Tournament 337 s, Chat 221, Groups 211, Smoke 187, EventEdit 129, People 91, SignIn 68, Discover 44, Profile 32, Language 25) and longer on a runner. **A new UI test class must be added to `UI_SHARDS` in `ci.sh`**, grouped by running time; `ci.sh lint` (`check_ui_shards`) fails when any test class under `lilyUITests/` (deriving from `LilyUITestCase` or `XCTestCase`, whatever its name; `class LilyXxxTests: LilyUITestCase` until 2026-10-14) is in no shard or in two, when `LilyIPadTests` is in a shard, or a shard names a class that does not exist, and when the workflow's `shard:` matrix does not list every entry of `UI_SHARDS` (a fourth shard needs a `4` there), so neither can be forgotten. `ui-shard N` runs `UI_SHARDS[N-1]` from the products on disk and needs a prior `build-and-unit` (or `all`); the `.xctestrun` holds `__TESTROOT__`-relative paths, so the archive restores anywhere. The first sharded run (2026-10-09) took 20 minutes for shard 2 and failed two tests that pass on a Mac: a `press(forDuration:)` on the room's first row turned into a scroll on the runner (the test now swipes the row into a hittable position first and presses up to three times until "Reply" exists), and a `Form` footer hint was asserted with `exists` right after typing (now `waitForExistence`). **The GitHub runner is two to three times slower than a Mac: never assert with `exists` right after an action, and give a long-press menu a retry.** A full disk breaks the gate in confusing ways (a unit-test host crash loop with `Fatal error: Index out of range` and `tee: No space left on device`); UI `.xcresult` bundles in `/tmp` reach 250 MB each, so delete them after judging. A test stage passes only when its log shows a `Test Case '...' passed` / `Test case '...' passed` line or Swift Testing's `Test run with N tests in M suites passed` summary (`require_executed_tests`; the `Executed N tests` with N > 0 alternative went 2026-10-14); otherwise it reads the last `Executed N tests, with M tests skipped` line and fails with "every test was skipped" when N == M (`LilyIPadTests` alone on an iPhone, a class-level XCTSkip) and "no tests were executed" else, because `xcodebuild` exits 0 when `-only-testing` matches nothing; `check_executed_tests_gate` self-checks the pattern in lint over five fixture logs. Both test stages run with `-parallel-testing-enabled NO` (2026-09-23 for unit): with clones the unit suite took minutes on a loaded CI runner and one timing-based test failed; without them the same 380 tests finish in under ten seconds and the log switches to the Swift Testing format above. If `xcrun` cannot find `simctl`, `xcode-select` has fallen back to the Command Line Tools; ask the user to run `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`.
- **Never touch CoreSimulatorService with `launchctl` or `pkill`.** It broke the simulator for the whole login session once and required a reboot. If runtimes show as unavailable, ask the user to reboot.
- **Never seed app state with `simctl spawn <udid> defaults write`.** The value lands outside the app container: the app can read it but not clear it, and test clones inherit it. Use the launch arguments in `AppConfig.LaunchArguments` instead (`-reset-session`, `-start-as-guest`, `-mock-location`, `-mock-auth`, `-mock-auth-confirm`, `-mock-auth-fail`, `-mock-events`, `-mock-events-fail` (2026-10-14), `-hold-popups` and `-freeze-aurora` (2026-10-15), `-app-language <code>`). UI tests already pass them. They are honoured in debug builds only (`AppConfig.LaunchArguments.isHonored`; `AppDependencies.makeDefault` reads `CommandLine.arguments` only when it is true), like the local identity header, so a release build cannot be started as a guest or on mock data from the outside.
- **UI tests run with `-parallel-testing-enabled NO`.** Simulator clones intermittently failed to launch the test runner.
- **A UI run can flip the simulator's keyboard language** (2026-10-02: two typing tests failed, the hierarchy dump showed a Russian keyboard, the email field still typed fine because its keyboard type is Latin while the password field got one character). A `typeText` into a field grazes the keyboard switcher, and iOS persists the choice in the simulator's `com.apple.keyboard.preferences` as `KeyboardLastUsed`, so every later test that types into a default-keyboard field fails until it is reset. Diagnose with `xcrun simctl spawn <udid> defaults read com.apple.keyboard.preferences KeyboardLastUsed`; fix with `defaults write ... KeyboardLastUsed -string "en_US@sw=QWERTY;hw=Automatic"` and `KeyboardsCurrentAndNext -array` of the same value, then `xcrun simctl shutdown <udid>` and `boot` (a device preference the run itself changed, not app state, so the rule above does not apply). Driving the switch from a test does not work: the secure and email keyboards show no globe, and on this simulator keyboard elements report frames one screen height too low, so taps on them miss.
- **The UI test classes are `LilySmokeTests`, `LilySignInTests`, `LilyGroupsTests`, `LilyChatTests`, `LilyPeopleTests`, `LilyEventEditTests`, `LilyLanguageTests`, `LilyTournamentTests`, `LilyDiscoverTests`, `LilyProfileTests`, (since 2026-10-11) `LilyRosterTests`, (since 2026-10-14) `LilyStateTests` and the iPad-only `LilyIPadTests` in the `lilyUITests` target**, all extending `LilyUITestCase` (`lilyUITests/LilyUITestCase.swift`: the launch with `-reset-session -mock-location -mock-auth -mock-events`, `relaunch(appending:)` and every helper), so one test is `-only-testing:lilyUITests/LilySmokeTests/<name>` or `.../LilySignInTests/<name>`. When the identifier matches nothing, `xcodebuild` still exits 0 and prints a passing suite, so confirm a `Test Case '...' passed` line for your test actually appears before trusting a green run. Map annotations are not descendants of the map element in the accessibility tree: query them from `app`, not from `app.maps`.
- **No `.pbxproj` edits are needed for new files.** The project uses synchronized folder groups; anything under `lily/`, `lilyTests/`, `lilyUITests/` joins its target automatically. Info.plist is generated, so plist keys go in as `INFOPLIST_KEY_*` build settings (the location usage text is one). A key with no such setting (`CADisableMinimumFrameDurationOnPhone`, added 2026-10-24: an `INFOPLIST_KEY_` form of it builds but never reaches the plist) goes in `lily-Info.plist` at the repository root, set as `INFOPLIST_FILE` in the app target's three configurations; `GENERATE_INFOPLIST_FILE` merges it with the generated keys (checked with `plutil -p` on the built app's Info.plist: the display name, the usage texts and the new key all there).
- **Keep `lily/` to Swift sources, `Assets.xcassets` and the two string catalogs (`Localizable.xcstrings`, `InfoPlist.xcstrings`).** The flip side of synchronized groups: every other file in there joins the app target and is copied into the app bundle. Stray copies of `README.md`, a CI workflow and `.claude/settings.local.json` once shipped inside `lily.app`; a stray `.git` copy in the same folder made Xcode write 171 lines of `.git/...` membership exceptions into the project file to keep those out. `.gitignore` does not protect you, because Xcode reads the filesystem and not the index. Check with `find lily -type f ! -name '*.swift' ! -name '*.xcstrings' | grep -v Assets.xcassets`, which should print nothing.
- **The only git repository is the project root.** `lily/` is the app source folder, not a repo. A leftover `.git` copy inside it made `git status` report every tracked file as deleted and the source folders as untracked, which looks like catastrophic loss and is not. Run git from the root or with `-C`, and if a status shows mass deletions, check `git rev-parse --show-toplevel` before believing it.
- **Concurrency:** the app target compiles with default `@MainActor` isolation and approachable concurrency; the test targets do not. Mark test suites `@MainActor`, and mark plain data types `nonisolated` so they stay `Sendable` and usable from tests.
- **To see what a screen actually looks like**, add a temporary XCUITest that writes `XCUIScreen.main.screenshot().pngRepresentation` to a directory passed in as `TEST_RUNNER_<VAR>=...` (the simulator can write host paths); it must be an environment variable of the xcodebuild process, `TEST_RUNNER_SHOT_DIR=/tmp/x xcodebuild test ...` (the prefix is stripped, the test reads `SHOT_DIR`). Written after the action as `TEST_RUNNER_SHOT_DIR=/tmp/x` it becomes a build setting (the log lists it under "Build settings from command line") and never reaches the runner, which cost a session an hour on 2026-09-11; keep a hardcoded fallback directory in the test so a misrouted variable still yields screenshots. Or drive the app by hand and use `xcrun simctl io <udid> screenshot`. Note that `XCUIScreen` screenshots blank out `SecureField` contents, which looks like a rendering bug; `simctl` shows them.
