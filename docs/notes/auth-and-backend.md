# Auth, session, networking and the backend

> Cognito through Amplify, the session state machine and its restore rules, the networking seam, the wire contract in words, usage statistics, AWS deployment. Moved out of `README.md` and `CLAUDE.md` on 2026-10-17 and kept as written. The reference part describes the feature as the README did; the dated notes record decisions, lessons and the evidence behind them, newest last, so an older sentence can be superseded by a later one or by a marker such as "(removed 2026-10-14)". Read this file before touching the area; the rules that apply everywhere are in `AGENTS.md`.

## Reference (from the README)

Early days. Auth is real: email + password against the Cognito user pool `lily-users` through Amplify Swift, configured in code (no JSON file in the bundle), with the verification code Cognito emails after sign-up entered in the app; Apple and Google stay on the sheet and answer "Coming soon" until the pool has identity providers. Events and profiles come from the Laurel backend when it runs locally (see [Backend](#backend)) or from in-memory mocks with `-mock-events`; `-mock-auth` swaps Cognito for a mock. The AWS side (Laurel on Fargate at `https://api.iskra.red`, DynamoDB, the Cognito user pool) is defined and deployed by the `iris-dc/rose` CDK repository; release builds point at it and send the Cognito access token as a Bearer (see [AWS deployment](#aws-deployment)).

- Session persistence across relaunch: the guest choice, and the signed-in user (Amplify keeps the tokens in the keychain and refreshes them; the app only caches who is signed in). A relaunch checks the cached user against the pool (since 2026-10-11): one whose refresh token expired is dropped and the app opens signed out, one that cannot be checked offline is kept and the backend's 401 decides, a sign-out interrupted before the pool was told is finished, and a pool session left behind a guest choice is ended with the guest standing.

### Architecture notes

- **Session state machine.** `SessionController` owns `SessionState` (`loading` (removed 2026-10-17: the state starts from the cache, see the dated note at the end), `signedOut`, `guest`, `signedIn`). Views only read it; all transitions are methods on the controller.
- **Auth is Cognito through Amplify, behind two seams.** `AuthService` (`restoreSession`, `signIn(with:)`, `signUp`, `confirmSignUp`, `resendConfirmationCode`, `signOut`) is what the app calls; `CognitoAuthService` implements it, and `AuthTokenProvider`, over a `CognitoClient`, the thin mockable surface the service needs (`isSignedIn`, `accessToken`, `currentUser`, `fetchEmail`, `signIn`, `signUp`, `confirmSignUp`, `resendCode`, `signOut`, failing with `CognitoClientError`). `AmplifyCognitoClient` is the one file that imports Amplify: it maps `AuthError`/`AWSCognitoAuthError` to `CognitoClientError`, reads the access token from `fetchAuthSession()` (Amplify refreshes it), and configures Amplify once, on its first call, from `AmplifyConfigurationBuilder` (the legacy `awsCognitoAuthPlugin` JSON built from `AppConfig.Cognito`, stating `USER_SRP_AUTH` explicitly) instead of an `amplifyconfiguration.json` in the bundle. Configuring on first use rather than at construction keeps Amplify out of the unit tests, which build the default composition root. `CognitoAuthService` maps the client errors to `AppError` (wrong or unknown credentials to `invalidCredentials`, since the pool hides user existence; `emailNotConfirmed`, `emailTaken`, `invalidConfirmationCode`, `tooManyAttempts`, `sessionExpired`), makes the `AuthUser` from `sub` and the email attribute (`AuthUser.displayName(fromEmail:)`), signs the pool out again when that read fails after the pool accepted the sign-in (or on a restore without a cached user), so the app is never a guest over a pool session, and answers Apple and Google with `providerUnavailable` ("Coming soon") until the pool has identity providers. Since 2026-10-11 `restoreSession()` also asks the pool for a token before trusting the cache (Amplify keeps `isSignedIn` true after the refresh token expired; an expired one drops the cached user and signs the pool out, so the app opens signed out, while a check that fails offline keeps the user and the backend's 401 decides), finishes a sign-out interrupted before the pool was told (`StoredSession.signingOut`, written before Amplify is asked and cleared once it answered) and ends a pool session found next to a guest choice, the guest standing; every compensating pool sign-out goes through `signOutOfPool(after:)`, whose own failure is logged ("Pool sign-out after <step> failed too"), the one line that explains a later launch's silent sign-in. `confirmSignUp` answers a `ConfirmOutcome` (`signedIn`, `confirmedButSignInFailed`, `failed`): a confirmed account whose sign-in did not land is reported once and the email form returns to sign-in, because the pool refuses a second confirmation.
- **SessionStore is a hint, not truth.** It stores the guest choice and the signed-in user as last seen, so a relaunch shows the profile without a round trip; `CognitoAuthService` only trusts a cached `.signedIn` while Amplify still has a session whose refresh token is alive (a check that cannot be made offline keeps it) and drops it otherwise; a `.signingOut` marker records a sign-out the pool has not confirmed yet, so the next launch finishes it, and a guest choice always outranks a leftover pool session. Tokens never live there: Amplify keeps them in the keychain. The mock stores its fake session in the same place.
- **Networking seam:** repositories depend on the `APIClient` protocol and describe a call as an `APIRequest` (method, path, query items, optional `Encodable` body, response type). `URLSessionAPIClient` builds the URL from the base URL it is given (`AppDependencies.apiBaseURL(from:logger:)`: `AppConfig.API.baseURL` for the build configuration, or the `-api-base-url` launch argument in debug builds), sends and decodes JSON with the shared conventions in `APIJSONCoding`, adds `X-App-Version` on every request and `X-Local-User-Id` in debug builds when a user is signed in, and turns non-2xx answers into `APIError.http(status:body:)` with the backend's `{code, message}`; transport failures stay `URLError`. `APIClient.send(_:failingWith:)` then maps known backend codes to their `AppError`, other `URLError`s to `.network` and anything else to the caller's fallback, while cancellation passes through untouched so a screen the user left never raises the popup. Request failures are logged with method, path and status (never bodies or headers): a refusal the product expects (a 4xx carrying a known backend code, or any 401 or 429) at warning, a fault (a 5xx, an unreadable body, an unknown code such as `VALIDATION_FAILED`, which signals client-validation drift) at error; a request may name a `logPath` so a secret in the path never reaches the log (the device token's `DELETE` logs `/api/me/devices/<token>`). `BackendErrorCode.appError` is one exhaustive switch, so a code added without a mapping fails to compile.
- **Sign-in flow:** the sheet has a navigation bar with Close (its email form the system back button; see `design-and-ui.md`, 2026-10-28), mounts its own `.errorPopup`, because a sheet is drawn above the root where the shared popup lives (`ErrorCenter` tracks the mounts and only the topmost draws), and it dismisses when `session.state.user` appears, which also works for guests who are already inside the app. `SignInViewModel` and `EmailSignInViewModel` own their sign-in `Task` and cancel it when the sheet disappears; `SessionController` treats `CancellationError` as a quiet exit, holds one authentication slot for sign-in, sign-up and confirmation alike, and `signOut()` clears local state before the remote call and ignores re-entry. Email sign-in and sign-up answer an `EmailAuthResult` (`signedIn`, `confirmationRequired`, `failed`): a sign-up the pool wants confirmed, or a sign-in refused because the email was never confirmed, is not an error and shows no popup; `EmailSignInViewModel` switches its `mode` to `.confirm`, where `canSubmit` needs `AppConfig.Cognito.confirmationCodeLength` digits, `submit()` runs `SessionController.confirmSignUp(email:code:password:)` (confirm, then the normal sign-in with the kept password; it answers a `ConfirmOutcome`, and on `confirmedButSignInFailed` the form returns to sign-in with the email and password kept, since the pool refuses a second confirmation, while a refused code keeps the confirm step and its code), `resendCode()` asks for a new code and the mode toggle reads "Back to sign in". `UserDefaultsSessionStore` logs cache hit, miss and invalidation and discards an unreadable blob with a warning.

### Backend

Events and profiles come from **Laurel**, the Spring Boot backend (its own repository), which the app reaches at `AppConfig.API.baseURL`. The base URL follows the build configuration and the device: **debug** builds on the **simulator** use `AppConfig.API.localBaseURL`, `http://localhost:8080` (the Mac's loopback), while **release** builds and **debug builds on a phone** use `AppConfig.API.productionBaseURL`, `https://api.iskra.red` (Laurel on AWS, deployed by `iris-dc/rose`; see [AWS deployment](#aws-deployment)); a phone's loopback is the phone, and an app opened from the home screen gets no launch arguments, so a debug build there would otherwise answer "You're offline" to everything.

**Simulator.** The simulator shares the Mac's loopback interface, so a Laurel started locally with its `local` profile (DynamoDB Local, auth bypass, seeded with the same nine fixture events the mocks produce) is all that is needed: start it, run the app, and Explore shows the seeded events. Participation is not seeded: against the backend every game shows Join and Home starts empty, while the mocks pre-join every fourth fixture so the tab has content. Plain HTTP to `localhost` needs no App Transport Security exception, because ATS exempts unqualified host names.

**Physical iPhone.** A device on the same Wi-Fi reaches the Mac by its Bonjour name. Add the launch argument `-api-base-url http://<mac-name>.local:8080` to the `lily` scheme (Product → Scheme → Edit Scheme → Run → Arguments; the Mac's name is under System Settings → General → Sharing, "Local hostname"). `-api-base-url` takes a value, the next argument (as `-mock-user-id`, `-realtime-endpoint` and `-app-language` do); `AppConfig.LaunchArguments.value(following:in:)` reads it and `AppDependencies.apiBaseURL(from:logger:)` accepts it when it parses as a URL with a scheme and a host (logged at info as `API base URL overridden: <url>`; anything else is logged at warning and ignored). Like every launch argument it is honoured in debug builds only. Laurel binds all interfaces, so nothing changes on its side; macOS may ask once whether to allow incoming connections for Java. iOS shows the Local Network permission prompt on the first request (the usage text is the `INFOPLIST_KEY_NSLocalNetworkUsageDescription` build setting of the Debug configuration only: a release build ignores the argument and never reaches a `.local` host), and that first request may fail before you tap Allow: pull to refresh.

**Release.** `https://api.iskra.red` takes the Cognito access token the app sends as `Authorization: Bearer <token>`; anonymous reads (`GET /api/events?scope=upcoming`, `GET /api/events/{id}`) work without one, so guests browse, and everything else answers 401 without a valid token, which the app shows as "Session expired".

Without a backend, launch with `-mock-events`: `MockEventRepository` serves the fixtures and joins, leaves and creates in memory (a created game is hosted by the signed-in mock user under the host name "You", with the draft's client id as its id), and `MockProfileRepository` accepts every display name. Previews use the same mocks through `AppDependencies.makeMock()`, and the UI tests pass the argument so they never depend on a running server. Without either, every list load and join reports "You're offline" through the popup, and the lists show the refreshable "Couldn't load events" state (the landing preview fails silently, logged at warning, and the miniatures keep showing the sample games).

**Identity.** The user id is the Cognito `sub`. The app authenticates with the Cognito **access token** (`Authorization: Bearer <token>`, `AppConfig.API.Headers`), read per request from an `AuthTokenProvider` (`CognitoAuthService` over Amplify, which refreshes tokens itself); a guest has none and sends no `Authorization` header, and the client asks for one only while the app's session has a user (`IdentityProvider.currentUserID`), so a token Amplify still holds after a sign-in the app rolled back never personalises a guest's requests. A 401 from the backend maps to `AppError.sessionExpired` and a 429 (Laurel's rate limit, code `RATE_LIMITED`) to `AppError.rateLimited`, whatever was asked and before the code lookup (`APIError.appError(fallback:)`); the popup then reads "Slow down a moment". Locally, Laurel's `local` profile still bypasses auth for requests **without** a Bearer header and trusts the `X-Local-User-Id` header a **debug build** adds for the signed-in user (`AppConfig.API.sendsLocalUserHeader`, `true` only under `#if DEBUG`); a debug build signed in through Cognito sends a real token too, which the local Laurel validates for real, so start it with the pool and client ids (`COGNITO_USER_POOL_ID=eu-central-1_JmfE31ODT COGNITO_APP_CLIENT_ID=54dul3essertek166u2st78s4a`); it ignores the local header when a Bearer token is present. A guest against the local backend runs as its `local-dev` user, which the backend treats like any other user; it is the app that hides Join and Leave for guests (`Participation.hidden`), so a header-less `curl` can join as `local-dev`. The header value comes from an `IdentityProvider` (`SessionIdentityProvider` reads `SessionController.state.user?.id`), so the client never depends on the session controller. Right after a successful sign-in the app `PUT`s the user's display name to the profile endpoint, fire and forget, so the backend can stamp the host's name onto events; a failure is logged, never shown.

**Contract, in words.** JSON, UTF-8, ISO-8601 instants in UTC (`2026-09-13T17:00:00Z`; the app also reads fractional seconds and always writes without). Every request carries `X-App-Version: <CFBundleShortVersionString> (<CFBundleVersion>)`, e.g. `1.0 (42)` (`AppConfig.API.Headers.appVersion`; the value is an `AppVersion` read once from `Bundle.main` and injected into `URLSessionAPIClient`, so tests pin it), so the backend can tell app versions apart in its logs and statistics. Query values are percent-encoded with `+`, `&` and `=` escaped (`URLComponents.percentEncodedQuery`), because `URL.append(queryItems:)` left a `+` bare and Laurel's servlet layer read it as a space. `GET /api/events?scope=upcoming|joined` lists events: `joined` returns the caller's upcoming events, hosted ones included, uncapped and ascending by start (past games are not listed); `upcoming` is capped at 100 (Laurel's `events.upcoming-limit`) and **ordered by relevance for the caller, not by start**. Explore sends the user's position with that request as `lat` and `lon` when it is known (`EventRepository.events(in:near:)`; `Coordinate.rounded(toDecimals:)` at `AppConfig.Events.positionPrecision`, two decimals, about a kilometre, printed with fixed decimals and a `.` whatever the locale; never sent with `joined`), and the backend weighs distance, the event types the caller views and joins, the hosts they join, their own participation and the start time; a guest with a position gets distance and time, without one the plain start order, and the app tolerates any order (a game created from Explore goes to the top of that list, by start time on Home). `POST /api/events/{id}/participants` joins and `DELETE` on the same path leaves; both return the updated event. `PUT /api/events/{id}` (`UpdateEventPayload`: the create body without `clientEventId` and `groupId`, an absent optional removing the stored one) replaces every editable field for the host and returns the event; `403 NOT_HOST` ("Not your game") for anyone else, `409 CAPACITY_TOO_LOW` ("Too few spots") when the new capacity is below the people already in, which the form prevents beforehand by flooring the stepper at that count (neither applies while the edit allows extra players, when the capacity is a target the host may set below them, nor when it sends none, which lifts the limit), and anything else without copy becomes `.eventUpdateFailed` ("Couldn't save your changes"). `POST /api/events` creates a game and answers `201` with the event, the caller as host and first participant; the body (`CreateEventPayload`) carries `clientEventId`, `title`, `type`, `startsAt`, `location {name, coordinate}`, the optional `capacity` (left out for a game without a limit), `allowsExtraParticipants` (always sent; `true` makes a capacity the number of players needed, so joins past it are accepted and the game is never full) and the optional `description`, `lookingFor`, `skillLevel` and `price`, left out when blank or free. `clientEventId` is a UUID the app chooses once per draft (`EventDraft.clientId`) and sends with every attempt; the backend uses it as the event id (lower-cased), so a create repeated after a lost answer or a `TRY_AGAIN` gets the same game back instead of making a second one, and `409 EVENT_ID_TAKEN` means another user's game already has that id. `EVENT_ID_REUSED` (409, the same id retried with a different body) is handled the same way: the app knows neither code, maps both to `.eventCreationFailed`, and its refetch of the id then finds the game that did land. The form's limits (`AppConfig.Events.Creation`: 80 UTF-16 units of title, 120 of place name, 1000 of description, 300 of "looking for", counted with `utf16.count` because Bean Validation's `@Size` counts Java's `String.length()`, so an emoji is two; 2 to 200 players; a price with at most seven integer digits and two decimals) mirror the backend's constraints, so a draft that passes on the device never earns a `400 VALIDATION_FAILED`; the app additionally requires a start at least 15 minutes ahead, where the backend only requires the future. `PUT /api/profile` with `{"displayName"}` returns the profile. An event carries `id`, `title`, `type` (`EventType`, including `other`), `startsAt`, `location {name, coordinate {latitude, longitude}}`, `capacity` (absent for a game without a limit), `allowsExtraParticipants` (read as `false` when absent, so older payloads and fixtures keep decoding), `participantCount`, `hostUserId`, `hostName`, `isJoined` (whether the caller participates) and the optional details `description`, `lookingFor`, `skillLevel` (`beginner|intermediate|advanced`) and `price {amount, currencyCode}` (a JSON number, absent means free); optional fields are absent, never `null`, and `SportEvent` decodes the shape directly, key for key. Failures carry `{"code", "message"}`: `EVENT_NOT_FOUND` (404), `EVENT_FULL`, `ALREADY_JOINED`, `NOT_A_PARTICIPANT`, `HOST_CANNOT_LEAVE`, `TRY_AGAIN` (409; the last means the write lost a race with another player or was throttled by DynamoDB and is safe to repeat) `VALIDATION_FAILED` (400) and `RATE_LIMITED` (429, with a `Retry-After` header; the app maps it to `.rateLimited`, "Slow down a moment", by the code and by the status alone when the body is missing, the way a 401 becomes `.sessionExpired`, whatever was asked); the first six map to their own `AppError` cases and copy, anything else (including `EVENT_ID_TAKEN`) becomes `.eventsUnavailable` on a read, `.participationFailed` on a join or leave and `.eventCreationFailed` ("Couldn't create your game") on a create, and a transport failure becomes `.network`. `GET /api/events/{id}` returns one event: the detail screen fetches it after any of the 409s, and after a 500 or a transport failure on a join or leave (the write may have committed before the answer was lost), so the count on screen and in the lists behind it is the server's before the popup explains the refusal; a `TRY_AGAIN` is first repeated once after `AppConfig.API.tryAgainDelay`.

**Usage statistics.** The taps the backend cannot see for itself are reported by a signed-in user to `POST /api/interactions` (`Core/Statistics`): `event_viewed` (event id, type and host id) when a detail opens, `filter_applied` when the filter panel closes on a changed filter or "Show all events" is tapped, and `presentation_changed` (`list` or `map`). The body is `{"interactions": [{"kind", "occurredAt", ...}]}` with at most `AppConfig.Statistics.batchSize` entries, answered `202 {"accepted": n}`. A `filter_applied` carries the **shape** of the filter (`FilterSummary`: the selected type names (at most `AppConfig.Statistics.maxFilterTypes`, 32, Laurel's cap; the first sorted names), the radius in metres, and whether a price cap, a level, a date range or "open spots only" is set), never the amount, the dates or any text; no interaction carries a coordinate, by construction of `Interaction`. `RemoteInteractionRecorder` buffers them per user and posts when `batchSize` (10) have gathered, `flushDelay` (30 s) after the first one, when the app goes to the background (`AppRootView`), or before a sign-out while the Bearer still goes out (`RemoteInteractionRecorder` is a `SessionObserver`; capped at `AppConfig.Statistics.signOutFlushTimeout`, 3 s, and what is still buffered once the session has ended is dropped); the buffer is capped at `maxBuffered` (100, oldest dropped) and a failed post is a warning under the `.statistics` log category, never a popup or a retry. **Guests send nothing, ever**: an interaction recorded without a signed-in user is dropped on the spot, and entries recorded for a user who signed out before the flush are dropped then. Mock runs (`-mock-events`, previews, UI tests) use `NoOpInteractionRecorder`. The backend records joins, leaves, creates and list views itself, keeps per-user aggregates and a Firehose stream to S3 (see the `iris-dc/rose` and `iris-dc/laurel` READMEs); only the Cognito `sub` identifies a user there.

### AWS deployment

The infrastructure lives in the `iris-dc/rose` CDK repository (eu-central-1): an Application Load Balancer in front of one ECS Fargate task running Laurel at `https://api.iskra.red` (Route 53 zone `iskra.red`, ACM certificate), three on-demand DynamoDB tables, a Cognito user pool `lily-users` (email + password; Apple and Google identity providers are follow-ups) with the app client `lily-ios`, CloudWatch alarms and a monthly budget. The pool id and the client id the app will need are the `UserPoolId` and `UserPoolClientId` outputs of rose's `RoseAuthStack`. Pushing to `rose/main` deploys, and a green `laurel/main` run triggers a rose deploy with that commit.

Release builds point at `https://api.iskra.red` (`AppConfig.API.productionBaseURL`) and send the Cognito access token as a Bearer: `AppDependencies.makeDefault()` wires `CognitoAuthService(client: AmplifyCognitoClient(...))` as both the `AuthService` and the API client's `AuthTokenProvider`, with the pool and client ids from `AppConfig.Cognito` (no `amplifyconfiguration.json`; the file names stay git-ignored so a generated one can never ship by accident). The backend validates issuer, expiry, `token_use == access` and `client_id`. Apple and Google identity providers in the pool are the follow-up. See `CLAUDE.md` for the reasoning.

## Dated notes

- **Backend calls go through one seam.** `Core/Networking/`: repositories depend on the `APIClient` protocol and build an `APIRequest` (method, path, query, optional `Encodable` body, response type); `URLSessionAPIClient` is the only type that knows URLs, headers and JSON conventions (`APIJSONCoding`: ISO-8601 instants, read with or without fractional seconds, written without). Every path lives in `AppConfig.API`, and so does the base URL per build configuration: `localBaseURL` (`http://localhost:8080`; the simulator reaches the Mac's loopback, and ATS exempts unqualified host names, so no plist exception) is `baseURL` under `#if DEBUG && targetEnvironment(simulator)`, `productionBaseURL` (`https://api.iskra.red`) otherwise (since 2026-10-17: a debug build opened from a phone's home screen gets no launch arguments, so the scheme's `-api-base-url` does not reach it, and with `localhost` as its default it answered every request with "You're offline", the phone's loopback being the phone; a debug build on a device now talks to production by default, and `-api-base-url http://<mac-name>.local:8080` still points it at a Laurel on the Mac). `api.iskra.red` is defined by the `iris-dc/rose` CDK repo at `/Users/makshr/rose` (Laurel on Fargate behind an ALB; Cognito pool `lily-users`, client `lily-ios`, ids in the `RoseAuthStack` outputs; it resolves only after rose's first-time setup) and takes the Cognito access token the app sends as a Bearer (anonymous reads work without one; see the Cognito note below). A debug build on a physical iPhone reaches a Laurel on the same Wi-Fi through the one launch argument that takes a value, `-api-base-url http://<mac-name>.local:8080` (`AppConfig.LaunchArguments.apiBaseURL`; the value is the next argument, read by `AppConfig.LaunchArguments.value(following:in:)`, which returns `nil` when the flag is missing, last, or followed by another `-` flag); `AppDependencies.apiBaseURL(from:logger:)` takes it when it parses as a URL with a scheme and a host (info `API base URL overridden: <url>` under `.network`), otherwise warns and keeps `AppConfig.API.baseURL`, and hands the result to `URLSessionAPIClient(baseURL:)`. The device shows the Local Network permission prompt once (`INFOPLIST_KEY_NSLocalNetworkUsageDescription` in the app target's Debug block of the pbxproj only, because a release build ignores the argument and must not ship a development-only permission string; there is no build-setting form of `NSAppTransportSecurity`, and a `.local` host name needs none) and the first request may fail before it is answered: pull to refresh. Use `client.send(request, failingWith: fallback)` from repositories: it maps the backend's `{code, message}` codes to `AppError` (`APIFailureMapping.swift`), other `URLError`s to `.network`, everything else to the fallback, and lets cancellation through untouched. Fakes: `FakeAPIClient` records requests and replays queued responses; `StubBackend` + `StubURLProtocol` stub a unique host per test for the real client.
- **The local identity header is debug-only.** Laurel's `local` profile bypasses auth for requests without a Bearer header and trusts `X-Local-User-Id` on them. `AppConfig.API.sendsLocalUserHeader` is `true` only under `#if DEBUG`; the value comes from an `IdentityProvider` (`SessionIdentityProvider`, which reads `sessionController.state.user?.id`; `AppDependencies` links it after the controller exists because the controller's own profile sync goes through the client). Never send it in release, never log it. - **Cognito through Amplify Swift (2026-09-22).** `amplify-swift` (up to next major from 2.61.0; `Amplify` and `AWSCognitoAuthPlugin` products, app target only) is configured **in code**, once, from `AppConfig.Cognito` (`region`, `userPoolId`, `appClientId`, the `RoseAuthStack` outputs) through `AmplifyConfigurationBuilder` (the legacy `awsCognitoAuthPlugin` JSON with `CognitoUserPool.Default` and `Auth.Default.authenticationFlowType = USER_SRP_AUTH`, decoded into Amplify's `JSONValue`; the Gen2 `AmplifyOutputs.data` shape exists in 2.61 but cannot state the flow, and the pool's `lily-ios` client allows SRP + refresh only): no `amplifyconfiguration.json` in the bundle, nothing to keep in sync by hand, and the `.gitignore` entries stay so a generated one can never ship. `AmplifyCognitoClient` (`Core/Auth/Implementations`, the only file importing `Amplify`, `AWSCognitoAuthPlugin` and `AWSPluginsCore`) configures Amplify lazily on its first call behind one static `Task`, not in `AppDependencies` at construction, because the unit tests build the default composition root (`makeDefault(arguments: [])`) and nothing there may reach Amplify; it also signs a stale Amplify session out before a sign-in, since Amplify answers `invalidState` otherwise. - **Cached-first session restore (2026-10-17, on the user's report that the app showed a dark screen for seconds).** `SessionController.init` reads the `SessionStore` and starts from it (`.signedIn(cached user)`, `.guest`, or `.signedOut` for nothing and for a `.signingOut` marker), so the first frame is the landing or the shell and `SessionState.loading` and the `LaunchView` with the wordmark are gone (`Wordmark`, `LilyTheme.Fonts.wordmark`, `Typography.wordmarkTrackingPerPoint` deleted; the system's generated launch screen covers the process start). `restore()` is idempotent: the first call starts one `Task` that asks `authService.restoreSession()`, later calls join it. The answer is settled over the state the first frame showed, and only when the state is still that one (a sign-in or sign-out made meanwhile wins, logged at debug "Session changed during the restore check"): a session equal to the cache logs "Session verified" at debug; a session the cache missed sets `.signedIn` ("Session restored for user"); nil over a cached user runs `endCachedSession(of:)`, which cancels the profile sync, awaits `sessionWillEnd`, clears a `.signedIn` store, sets `.signedOut` and calls `sessionDidEnd`, logged at warning "Cached session dropped: the pool has no session for user"; nil over a guest or nothing keeps "Restored guest mode" / "No stored session".
