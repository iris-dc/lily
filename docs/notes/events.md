> The feed and its filter, join and leave, creating and editing a game, player limits, event types, prices and currency, relevance and position staleness, statistics. ## Reference (from the README)

- Event detail with join and leave for signed-in users: the button follows the caller's relation to the event (Join, Leave, "Event is full", "You host this game" (renamed "You host this event" 2026-10-18); nothing for guests; a game that allows extra players or sets no limit is never full), the count and capacity bar update from the server's answer, and the list behind it reflects the change on the way back. The host also gets Edit in the toolbar (since 2026-09-30): the game's form, prefilled, titled "Edit game" with Save, where every field but the group can change (the group a game is hosted in stays, shown read-only); the spots cannot drop below the people already in (and a game past 200 players still opens, the stepper clamped at the maximum), the start only has to lie a minute ahead (`AppConfig.Events.Editing.startMargin`, 60 s for the request's round trip; no 15-minute margin, so a host can fix the place of a game about to start), Save is enabled once something differs, and the saved game replaces the detail and the list behind it at once.
- Creating a game from Explore: the floating "+" over the list and the map is a menu, New game or New group; New game opens a form sheet with a title, the event type, when, a place name or the spot on a map, either is enough (the spot starts from your position; typing a place offers real places to pick (autocomplete, suggestions under the field), and a typed name alone is geocoded into the spot on Create, so a "Gdansk" game lands near Gdansk, and a bare pin is named after its spot), the number of players, and the optional description, "looking for", level and price per person (the price is read strictly as one number in the user's locale, no grouping; text that is no number holds Create with "Enter the price as a number" rather than making the game free). The draft is checked on the device against the same limits the backend enforces (text lengths counted in UTF-16 units, as the backend counts them, so an emoji counts two), so the Create button is enabled exactly when the backend would accept it; the new game appears in the Explore list when the active filter matches it, and always on Home, which lists hosted games alongside joined ones, and its detail says "You host this game". When the answer to a create is lost, the app asks the backend whether the game exists before showing a failure, so a game that did land is never reported as missing. A guest picking either item of the "+" menu gets the sign-in sheet instead. (superseded 2026-11-11: the "+" opens the creation wizard — a kind page, then one page per idea; the fields, the device-side checks and the lost-answer rule are unchanged. See the slice-3 entry in the dated notes.)
- Currency (2026-10-09): prices are typed in the user's currency, the device region's (złoty in Poland, euro in Spain, dollars in the US) or one fixed in a Currency row on Profile; every game keeps and shows the currency it was created in, and the filter's price cap is judged in the user's, leaving games priced in another currency out while it is set. See [Currency](#currency).

### Currency

Every price is stored with its currency (`Price {amount, currencyCode}`, an ISO 4217 code the backend keeps per event), and a card or detail always shows a game in the currency it was created in, formatted for the user's locale; nothing is ever converted. What the user's own currency decides is the **input** side: the currency a price typed into the create form is in, the currency a price added to a free game on the edit form is in (a priced game keeps its own), and the currency the Explore filter's price cap is typed and judged in. It is resolved by `CurrencyStore` (`Core/Currency`) in this order: the Currency row on Profile when the user fixed one (a menu with "System (<the region's code>)" and the currencies of `AppConfig.Currency.offered`, each with its name in the app's language: EUR, USD, GBP, PLN, CHF, CZK, HUF, RON, SEK, NOK, DKK, UAH, CAD, BRL), else the currency of the device's region (`Locale.currency`: PLN in Poland, EUR in Spain, USD in the US; the region stays the device's when the app's language is fixed, so a Pole using the app in English still gets złoty), else `AppConfig.Currency.defaultCode` (EUR, also the mock fixtures' currency). The choice is kept in `UserDefaults` (`lily.currency.preference`, `CurrencyPreference` as `system` or the code through `UserDefaultsChoiceStore<CurrencyPreference>`, shared with the language choice; a code the menu no longer offers reads as system) and forgotten by `-reset-session` like the language. **The price cap is judged in the user's currency as it is now** (`EventFilter.matches(_:from:currencyCode:)`): a free game always passes, a game priced in that currency passes at or under the cap, and a game priced in another currency stays out while a cap is set, since an amount cannot be compared across currencies; without a cap every game shows. A change on Profile applies at once: the form's and the panel's symbol (`Price.symbol(for:)`) and the visible games follow it without a reload. `LilyProfileTests/testPickingACurrencyOnProfileChangesThePriceFieldsSymbol` walks it on the simulator.

- **Location:** `LocationService` returns one fix or `nil`; the app never blocks on it. `CoreLocationService` reads a `LocationUpdateSource` (`CoreLocationUpdateSource` wraps `CLLocationUpdate.liveUpdates`, which prompts for when-in-use permission; the usage text is an `INFOPLIST_KEY_` build setting) and races the first fix against `AppConfig.Location.fixTimeout` in a task group, so cancelling its caller closes the stream. The seam lets the timeout, denied and first-fix paths be unit tested with a scripted fake. `CachedLocationService` wraps it in production: concurrent callers share one upstream request (which deliberately outlives any single caller's cancellation, bounded by `fixTimeout`, so the fix it obtains is cached for the next screen), a fix is reused for `fixTTL` (300 s) and a missing fix for `failedFixTTL` (30 s), so sibling tabs never open two CoreLocation streams. The events screens ask for the position on every appearance (`loadUserLocation()`; a hit within the TTL costs nothing, a later ask follows the user) and again when the app returns to the foreground (`refreshUserLocation()`, which asks the cache to `forgetMissingFix()` first, because that is the one moment permission may have changed in Settings), so the distance filter becomes available without a relaunch and distances, the default radius and the position sent for relevance follow the user instead of staying where the app was first opened; a miss after a fix keeps the view model's last known position rather than blanking the distances (the cache itself remembers the miss for `failedFixTTL`), and the position is logged at info only when it became known or changed. `Coordinate` stays Foundation-only; the CoreLocation bridge lives in `Coordinate+CoreLocation.swift`. Distance is computed on-device with a haversine, no network; `EventLocation.distance(from:)` is the one distance rule events, groups and tournaments delegate to, and `Measurement.roadText(locale:)` formats it in the app's locale, read per call. A caller cancelling its fix is a debug line, not the "Location unavailable" warning.
- **Events list caching:** `EventListViewModel.loadIfStale()` (used by `.task`) reuses events loaded within `AppConfig.Lists.staleAfter` (60 s, the one rule of every cached list since 2026-10-13) when a tab reappears; pull-to-refresh calls `load()` and always reloads; a cancelled load is logged, not reported; a failed load shows a refreshable "Couldn't load events" state instead of the empty state, and `loadIfStale()` does not retry it for `AppConfig.Lists.retryAfterFailure` (10 s), so switching tabs while the backend is down does not hammer it; a change made elsewhere or a change of caller ends that wait early, because it proves the backend is up and the answer different. A join or leave on the detail screen comes back through `replace(_:)`, which updates the list in place (and drops the event from a joined-only list when the user left), and bumps the shared `ChangeTracker` (`AppDependencies.eventChanges`); every other list compares the version it loaded against it and reloads on its next appearance, so Home shows a join made from Explore without waiting out the 60 s. A list also remembers the user it loaded for and reloads after a sign-in or sign-out, because `isJoined` is the server's answer for that caller. Explore sends the user's position with the request when it is known (`EventRepository.events(in:near:)`, so the backend can order by distance); content loaded for another position than the one known now counts as stale (without one while one is known, or for a place the user has since left; positions are compared as `Coordinate.coarse`, the same rounding (`AppConfig.Events.positionPrecision`) the repository sends, so GPS drift never counts), and a position that arrives or moves while the request is out earns one reload from `load()` itself, so the backend's order for where the user is replaces the answer without waiting for the next appearance (Home never sends a position and never reloads for one). Every one of these decisions is logged under `.cache`: the reason for a reload (never loaded, changed elsewhere, caller changed, position became known, position changed, retry after failure, older than TTL), a skipped reload (fresh, or waiting to retry) and the invalidation of sibling lists in `replace(_:)`. A failed load reports the mapped error ("You're offline", "Events unavailable"), never a blanket one. The rules themselves (TTL, version, caller, cooldown and, since 2026-10-13, the coarse position: `recordSuccess(position:)`, `stalenessReason(position:)`) live in `ContentFreshness` (`Core/Changes`), a value `EventListViewModel` and `TournamentListViewModel` hold directly and `MyGroupsStore` and `InboxStore` through `StoreLoader`; neither list keeps a position of its own, `load()` reloads once when a successful load left the content stale for any reason (never after a failed or cancelled one), a call while one is in flight is dropped, and the tournament list's `replace` mirrors the events list's (in place while the row still belongs to the scope, removed when not, inserted by start when the list lacks it). `EventListViewModel.listState` / `TournamentListViewModel.listState` (`ListState`) is what a group's segments draw through `ListSegment`; Explore's own ladder is `EventListScreenState`. This view-model-level check is interim until the cached `EventRepository` ships.
- **Filter panel and capacity bar.** `EventFilter` holds every criterion: `types` (a set of `EventType`, which now includes `other`), `maxDistanceMeters` (defaults to `AppConfig.Events.defaultFilterRadiusMeters`, 10 km, so the default filter already limits distance and still counts as inactive; `nil` is "anywhere"), `maxPrice` (free-form cap, `nil` any, zero free only), `skillLevel`, `dateWindow` (`DateWindow`: whole days, inclusive; switching dates on proposes today plus `defaultFilterDateSpanDays`) and `openSpotsOnly`; `isActive` is simply "differs from the default". `EventListViewModel.filter` is `private(set)` and changed only through `updateFilter { }`, which logs each change; `visibleEvents` is what list and map render, judged against `userLocation` for distance, and while the position is unknown the distance criterion is skipped rather than hiding every game (the panel shows a note instead of the distance choice). The type chips are `EventType.known`, the same list the create forms offer (until 2026-09-30 the panel listed only the types present in the loaded page, which hid a type whenever no such game was loaded); a game whose type this build does not know draws as "Other" but matches no type selection, a level it does not know counts as none (`SkillLevel.ifKnown`), and a stored filter naming a type or level this build does not know (one kept by a newer build) restores without it; `isEverythingFilteredOut` swaps in a "Show all events" empty state whose action is `showEverything()` (`EventFilter.everything`, no criterion at all), because the default radius alone can hide every game and a reset would keep it. A list without a filter button (Home) starts from `.everything` for the same reason (`AppDependencies.makeEventListViewModel`). `EventFilterButton` drops `EventFilterPanel` down as a popover, kept a popover on iPhone too via `presentationCompactAdaptation(.popover)`, so it reads as a dropdown: type chips in a `FlowLayout`, a segmented distance choice, a decimal `TextField` for the price cap with the user's currency symbol (`Price.symbol(for: viewModel.priceCurrencyCode)`, which follows the Profile choice) beside a "Free only" chip that sets the cap to zero, a level picker, a dates toggle with two compact `DatePicker`s, and the open-spots toggle; Reset and Done sit in the header. Only Explore is `filterable`. Amounts are compared without conversion in the user's currency (`EventFilter.matches(_:from:currencyCode:)`; a game priced in another currency is left out while a cap is set, see [Currency](#currency)), and filtering is on device over the loaded page until the backend takes the criteria as query parameters. `CapacityBar` (`EntriesBar(event:)` since 2026-11-02; `CapacityBar` removed) fills with the occupied share (red, amber when nearly full, muted grey when full) over a faint track, and the label under it counts the same way ("6 of 10 joined"); a game that allows extra players (`SportEvent.playerLimit == .minimum`) fills red up to the number it needs and stays red and open past it ("6 joined · 4 needed"), and a game without a limit (`capacity == nil`, `.unlimited`) draws no track at all, just "N joined"; `isFull` and `isNearlyFull` are always false for both, so "Open spots only" keeps them and Join stays on. The fixtures carry fixed participant counts so the feed shows an open, a nearly full, a full game, one short of and one past the players it needs (Hills ride, Bouldering intro) and one without a limit (Easy 8k loop).
- **Optional event details.** `SportEvent.description`, `lookingFor` (the host's own words for who is still needed), `skillLevel` (`SkillLevel`: beginner, intermediate, advanced, the offered `known` list; `nil` means any level, and such games match every level choice in the filter; a level a newer backend sends decodes as `unknown(name)`, goes back out as it came, and reads as none on the detail and in the filter) and `price` (`Price`: amount plus ISO currency code; `nil` means free, and so does a zero amount) are all optional with `nil` defaults in the explicit initialiser, so existing call sites keep compiling and payloads written before a field existed keep decoding (tested). `SportEvent.priceText` is the one price formatter ("Free" or the localised amount); the detail screen adds price and level rows to the facts card only when set, shows the description under the title and "Looking for" in its own card, and paid games get a small glass price chip on `EventCard` and the price in the `EventPreviewCard` caption; free games stay uncluttered. Whole amounts drop their minor units ("€5"), other amounts keep the currency's usual form ("€7.50"), formatted in the user's locale (`Price.text(in:)` takes a locale for tests). Stacked fact rows use `.labelStyle(.iconColumn)` so glyphs of different widths share one text edge. Fixtures cover every detail present and absent.
- **Join and leave:** `EventDetailViewModel` owns the event on screen, runs one change at a time (`isBusy`), replaces the event with the server's answer and hands it to the list; failures go to `ErrorCenter`. A `TRY_AGAIN` is repeated once after `AppConfig.API.tryAgainDelay`; a refusal that means the event moved on (`eventFull`, `alreadyJoined`, `notAParticipant`, `hostCannotLeave`, a second `tryAgain`; logged at warning, since a full game is a product state and not a fault) refetches it through `EventRepository.event(id:)` so the detail and the lists show the server's state before the popup explains why. So does a failure that leaves the outcome unknown, a 500 (`participationFailed`) or a transport error (`network`): Laurel commits the join before it reads the event back, so the write may have landed although the answer was lost; when the refetched event already shows what the user asked for (in after a Join, out after a Leave) the popup is skipped and an info line says the write landed, otherwise it shows; the refetch tolerates its own failure (since 2026-11-01 through the shared `WriteGate` and `LostAnswer`, see the dated entry). A join or leave that fills the last spot logs "Capacity reached for event <id>". `Participation` decides the control from the event and the caller: hidden for guests, `hosting` when `hostUserId` is the caller, `leave` when `isJoined`, `full` when no spots remain, otherwise `join`. The detail reads the caller through the same `IdentityProvider` the API client uses.
- **Creating a game.** `CreateEventViewModel` owns an `EventDraft` (`Features/Events/Models`): the form's fields plus `issues(now:)`, which names everything still wrong, in form order, against `AppConfig.Events.Creation` (text lengths in UTF-16 units, as the backend counts them), so the Create button is enabled exactly when the backend would accept the body and each section's footer can show its first issue. The Players section is a segmented choice (`create-player-limit`, `PlayerLimit`: "Any number", "Up to", "At least") over a stepper that hides for "Any number" and reads "N players needed" for "At least"; the draft keeps the stepper's value either way and sends `capacity` only when a limit is set, with `allowsExtraParticipants` for "At least", so the backend takes joins past that number or any number at all. A new draft proposes the next full hour at least a day ahead (`defaultStartOffset`, `Calendar.nextFullHour(after:)`: a date on the hour is kept); `prepare()` takes the spot from the `LocationService` when none is set yet, and `LocationPickerView` moves it; without a spot the picker opens on the user's position (MapKit's default view when that is unknown) and ignores the map's first settle, so leaving it without a drag keeps the spot unset; opened on a spot already set (an edit, a group's or a tournament's place, a match's venue) it keeps that spot until the pin has moved at least `AppConfig.Location.pickerMinimumMoveMeters` (1 m; `PickerSettlePolicy`, one rule for every form through `PlacePickerRow`), because the map's own arrival settles nudge the pin by centimetres and used to turn Save on; `PlaceFields` (the name field plus that row) is the place section of the event, group, tournament and match-schedule forms, and `PlaceDraft` the shared place validation behind `EventDraft.place` and `TournamentDraft.place`. `CreateEventPayload` is the wire body, built only from a draft with a coordinate, with blank details and a free price left out; `EventDraft.eventPrice` (in the draft's `currencyCode`, the user's when the form opened) and `EventDraft.makeEvent(hostUserId:hostName:coordinate:)` are the one place a draft becomes a `Price` or a stored `SportEvent` (the payload, the mock and the test fake use them), and `Price.parseAmount(_:locale:)` reads what is typed into a price field, here and in the filter panel, strictly (the whole trimmed text must be one number in the locale's form, grouping never, so "5,50" on a US device is not 550), with `Price.inputText(_:locale:)` as its seeding counterpart; the form's field is bound to the draft's own `priceText` (`price` is derived in the draft's locale), so unreadable text holds Create with "Enter the price as a number" instead of making the game free, while the panel keeps its own text and applies a readable cap, clears it on empty text and leaves unreadable text alone. The draft's `clientId` is chosen once and sent with every attempt, so a retry after a lost answer cannot make a second game (the backend answers the one it has). `submit()` runs one create at a time and stays quiet on cancellation; after a failure that leaves the outcome unknown (`.network`, `.eventCreationFailed`: the backend commits before it answers) it fetches `EventRepository.event(id: draft.clientId)` first and treats the create as landed when that event exists with the caller as host (logged `Create landed for event <id> despite <error>`, no popup; the counterpart of the join/leave refetch in `EventDetailViewModel`), while every other failure, and a lookup that finds another host's game or fails (a warning), reaches the `ErrorCenter`; a lookup that finds nothing is the check's answer, a debug line, and the popup shows the create's failure (`CreateFlow` in `Core/Networking` is this path for the event, group and tournament forms) (the sheet mounts its own popup, like the sign-in sheet); on success the sheet dismisses and `EventListViewModel.add(_:)` inserts the game into the list behind it, first on Explore (whose order is the backend's relevance for the caller, so there is no slot to compute) and by start time on Home (a joined-only list only takes a game the caller is in, and the host always is; never twice for one id), bumps the shared `ChangeTracker` (`AppDependencies.eventChanges`) so Home reloads on its next appearance, and logs the invalidation under `.cache`. The floating "+" (`CreateMenuButton`: a `Menu` with New game and New group under `menuStyle(.button)` so `lilyFloatingActionButton()` styles it; a guest gets the sign-in sheet from either item) is a `ZStack` sibling of the Explore content inside the safe area, above the floating tab bar, and the map's selected card sits at the bottom leading edge with `DesignTokens.Layout.floatingButtonFootprint` kept free on its right, beside the "+" (2026-11-05; before that it was lifted above the button), so the two never overlap; a guest gets the sign-in sheet from it. `MockEventRepository.create` mirrors the backend in memory: the draft's client id is the event id, the `IdentityProvider`'s user the host (named "You"), and a repeated client id answers the existing game. (superseded 2026-11-11: `CreateMenuButton` became `CreateButton`, one tap opening the creation wizard, and the form's sections became the wizard's event pages; see the slice-3 entry.)
- **Editing a game.** `EditEventViewModel` (`makeEditEventViewModel(for:onChange:)`) starts from `EventDraft(editing:)`, the event as a draft (`clientId` is the event's id), and judges it by `EventDraft.Rules.editing(participantCount:)`: a start at least `AppConfig.Events.Editing.startMargin` (60 s, the request's round trip and clock skew; the backend requires only the future, and no 15-minute lead time applies) ahead and a capacity floor at the people already in (`.capacityBelowParticipants`; the form's stepper starts there, so the issue is a safety net) unless the draft allows extra players or sets no limit, when `Rules.capacityRange(for:)` is the backend's whole range and the needed number may sit below the count (nothing is judged without a limit), as the backend's condition allows; the range's floor is clamped at the backend's maximum, so a game with more than 200 players still opens for editing with the stepper at 200, while the unclamped count still judges `.capacityBelowParticipants`. `hasChanges` is `draft != EventDraft(editing: original)` (since 2026-11-02 `draft != originalDraft`, built once in `init`), `canSubmit` needs it, and `submit()` sends `EventRepository.update(id:_:)` through `LostRace.attemptTwice` (Laurel pins the start its pre-read saw, so a second edit landing meanwhile is a `TRY_AGAIN` and the same request then goes through) (`PUT /api/events/{id}` with `UpdateEventPayload`), hands the answer to `EventDetailViewModel.accept`, which replaces the event and calls the same `onChange` a join does, so `EventListViewModel.replace` updates the list behind (and re-sorts a list in start order when the start moved). (superseded 2026-11-11 for the create half: `CreateEventSheet` is deleted and creating walks the wizard; `EventDraftSheet` stays as the edit sheet's shell.)

- **Usage statistics and privacy.** `InteractionRecorder` (`record(_:)`, `flush()`) is the seam the event screens report to; `RemoteInteractionRecorder` is the only type that posts, `NoOpInteractionRecorder` is wired wherever the repositories are mocked, so no preview, UI test or `-mock-events` run ever sends a statistic. Recording is fire-and-forget on the main actor: a guest's interaction is dropped at `record`, another user's at `flush`; sending happens at the batch size, on one timer (`Task` over an injected `sleep`, cancelled by any flush; the timer lets go of its slot before it flushes, so its own flush never cancels the post) after the first entry, when the root view sees the scene go to the background, or before a sign-out while the Bearer still goes out (`sessionWillEnd()`, capped by `Deadline.within` at `signOutFlushTimeout`; what is still buffered once the session ended is dropped). What is sent is what the backend cannot see for itself (the detail opened, the filter changed, the presentation switched) and is reduced to ids, types and flags before it leaves the view model (`Interaction`, `FilterSummary`): no coordinate, no amount, no date range, no text. The hooks are `EventDetailViewModel.recordViewed()` (once per instance, from the detail's `.task`), `EventListViewModel.filterPanelOpened()` / `filterPanelClosed()` (from `EventFilterButton`, one interaction per panel session and only when the filter changed) and `presentationChanged(to:)` (from `EventListView`); those and the other filter helpers live in `EventListViewModel+Filter.swift`, a split forced by SwiftLint's `type_body_length`, while every stored property stays in the main file. A failed post is a warning under the `.statistics` log category and is not retried.

## Dated notes

- **Fixtures are geographic:** mock events are scattered around `AppConfig.Location.mockCenter` (Berlin). Set the simulator location there to see realistic distances.
- **Join/leave rules live in `Participation`,** decided from the event and the caller's id: guests see nothing; the host (`hostUserId == caller`) sees "You host this game"; a participant (`isJoined`) sees Leave; a full event Join-disabled ("Event is full"); otherwise Join. The server's answer replaces the event on the detail and reaches the list through `EventListViewModel.replace(_:)`, which also bumps `AppDependencies.eventChanges` (a `ChangeTracker`) so sibling lists reload on their next appearance. A failure after which the event is worth another look (`AppError.needsRefresh`, private to `EventDetailViewModel`: the 409s in `isParticipationConflict`, which are logged at warning as expected product states, plus `.participationFailed` and `.network`, because Laurel commits a join before it reads the event back, so a 500 or a lost connection may hide a write that landed) refetches it through `EventRepository.event(id:)` and pushes the fresh event through the same `onChange` before the popup, and skips the popup when the fresh event already shows the asked-for change (the write landed; refusals are never skipped); `TRY_AGAIN` is repeated once after `AppConfig.API.tryAgainDelay` first (tests inject `.zero`).
