# Languages and copy

> The seven languages, the catalog rules, the Russian register pass. Moved out of `README.md` and `CLAUDE.md` on 2026-10-17 and kept as written. The reference part describes the feature as the README did; the dated notes record decisions, lessons and the evidence behind them, newest last, so an older sentence can be superseded by a later one or by a marker such as "(removed 2026-10-14)". Read this file before touching the area; the rules that apply everywhere are in `AGENTS.md`.

## Reference (from the README)

- Seven languages (since 2026-10-03): English, Russian, Spanish, French, Ukrainian, Polish and Portuguese. The app follows the device's language (English when the device speaks none of them) and a Language row on Profile fixes one, applied at once without a relaunch; the backend's reminder push and Cognito's confirmation mail follow it too. See [Languages](#languages).

### Languages

The app ships in English (the source language and the fallback), Russian, Spanish, French, Ukrainian, Polish and Portuguese (`AppLanguage`; the codes are the `.lproj` folders: `en`, `ru`, `es`, `fr`, `uk`, `pl`, `pt`, so `pt-BR` and `pt-PT` devices both get Portuguese). Which one shows is decided in this order: the Language row on Profile when the user fixed one (a menu with "System" and every language naming itself, stored in `UserDefaults` under `AppConfig.Storage.Keys.languagePreference`), else the system's pick among the app's localizations (`Bundle.main.preferredLocalizations`, which honours the per-app language in iOS Settings), else English; the stored choice goes through `UserDefaultsChoiceStore<LanguagePreference>` (`Core/Preferences`, the one store behind the language and the currency choices: nothing stored or a value this build cannot read is the system choice, logged once by key). `AppLocale` reads `Locale.autoupdatingCurrent` per call, so a Region change in Settings reaches prices, distances and the Profile currency row without a relaunch. A pick applies at once: `LanguageStore` (`Core/Localization`, on `AppDependencies.language`) persists it, sets `AppLocale` and publishes the language, and `AppRootView` rebuilds the whole tree under `.id(language)` with `.environment(\.locale, ...)`, so every screen, the tab bar and every formatted date, distance and price relabel without a relaunch (the navigation stacks kept in `AppNavigation` survive; a screen's own `@State` restarts).

- **Every line of copy is read through `localized(_:)`** (`Core/Localization/Localized.swift`): `AppBranding` and `ErrorMessageMapper` hold `static var`s and functions, never `static let` strings, so a lookup happens at read time, in the language of that moment. The key is the English text (`localized("Sign in")`), so a language without the translation falls back to English, and a `String.LocalizationValue` interpolation (`localized("\(count) spots left")`) becomes the catalog's `%lld` or `%@` placeholder and picks the plural variant for its number in the language's rules (Russian, Ukrainian and Polish have one/few/many; the catalog carries them). `localized` reads the fixed language's `.lproj` through `Bundle(path:)` (the main bundle while the system chooses, so iOS applies the user's preferred languages) and formats with `AppLocale.locale`, the chosen language in the user's region (a Russian reader in the US keeps US units and the US calendar), because `String(localized:locale:)` alone does **not** switch the language and `String(format:)` evaluates plural categories with the locale it is given, not the lproj's. Model text (`EventType.displayName`, `SkillLevel.displayName`, the day chips, `Price.text`, road distances, file sizes) goes through the same `localized` / `AppLocale.locale`, and SwiftUI's own `Text(date, format:)` follows the environment locale.
- **The catalog** is `lily/Localizable.xcstrings` (one key per line of copy, translations as Xcode's String Catalog JSON; edit it in Xcode's catalog editor or by hand) plus `lily/InfoPlist.xcstrings` for the camera and location usage descriptions. The build compiles them into `<code>.lproj/Localizable.strings` + `.stringsdict` + `InfoPlist.strings`; `knownRegions` in the project file needs no edit. `scripts/l10n-check.py` (run by `ci.sh lint`, after its own unittest suite `scripts/test_l10n_check.py`) fails when a `localized("...")` literal in the code has no key, a key is no longer used, a language lacks a translation, or a translation's placeholders differ from the key's, and checks `InfoPlist.xcstrings` against the project file: every `INFOPLIST_KEY_NS…UsageDescription` the Release configuration sets must be a key translated into every language, `CFBundleDisplayName`/`CFBundleName` stay English by design, and a usage string only the Debug configuration sets (`NSLocalNetworkUsageDescription`) must not be in the catalog, because a development-only permission string must not ship; `LocalizedCatalogTests` checks the compiled bundles the same way and that the lookups answer in the right language and plural form. Adding copy: write `localized("The English text")`, add the key with six translations to the catalog, run the check; one `localized` declaration per key across `lily/Config`, a same-meaning repeat being a `static var` alias of it; two roles that share one English text get keys naming the role ("Message (verb)", "Any (price)") with an explicit `en` value. Adding a language: a case in `AppLanguage`, the translations for every key, the two usage strings.
- **Backend and mails.** The device registration (`PUT /api/me/devices`) carries `locale`, the language the app shows, and the reminder push is composed in it by Laurel (`i18n/push_<code>.properties`, English fallback); a language change re-registers the device (`AppRootView`'s sync key includes the language, and `LastDeviceRegistration` remembers the locale it sent). Sign-up and "Resend code" pass `clientMetadata: {locale}` to Cognito (`AmplifyCognitoClient`), which rose's Custom Message Lambda reads to mail the confirmation code in that language.
- **Launch arguments.** `-app-language <code>` shows the app in a language for one run without storing the choice (screenshots of every language without a tap on Profile; an unknown code is ignored with a warning); `-reset-session` also forgets the stored language, so every UI test starts in the simulator's language. `-hold-popups` keeps every error popup up until it is dismissed instead of letting it fade after four seconds, for UI tests on a runner too slow to catch it (`LilySignInTests`, `LilyStateTests`). `-freeze-aurora` keeps the aurora on its first frame, as Reduce Motion does: its 30 fps redraw keeps the simulator's compositor at two fifths of a core on a Mac and starved the GitHub runner, which renders in software; every UI test launches with it. `LilyLanguageTests` picks Russian on Profile and checks the screen and the tab bar relabel, then goes back to English.
- **Translations** were written in one pass with the feature (2026-10-03) and should be read by native speakers before launch; the Russian catalog had that read on 2026-10-15 (a native-register pass that rewrote 117 Russian values, 108 of them strings the previous release carried, into neutral, idiomatic Russian: lowercase вы, вы-imperatives, «чат» for a direct conversation, «Мест нет» for every "full", singular bracket stages); the other six languages are still waiting for theirs. The terms are consistent per language (a "game" is игра / partido / match / гра / gra / jogo, a "spot" место / plaza / place / місце / miejsce / vaga), Russian and Ukrainian address the user as вы, French as vous, Spanish and Polish informally, Portuguese is neutral between the two varieties. A key that serves two roles with different grammar gets a role key with an explicit English value (`Message (verb)`, `Any (price)`, `Not allowed (draws)`).

## Dated notes

- **Languages (2026-10-03; en, ru, es, fr, uk, pl, pt).** `Core/Localization`: `AppLanguage` (codes = `.lproj` names; `systemChoice(preferredLocalizations:)` over `Bundle.main.preferredLocalizations`, fallback English; `init(localization:)` drops the region, so `pt-BR` is Portuguese), `LanguagePreference` (`.system` / `.fixed`, stored as `system` or the code under `AppConfig.Storage.Keys.languagePreference` through `LanguagePreferenceStore` / `UserDefaultsLanguagePreferenceStore` (removed 2026-10-14: `UserDefaultsChoiceStore<LanguagePreference>`)), `AppLocale` (a `Mutex`-guarded process-wide `Context`: the `.lproj` path copy is read from and the locale formats and plural rules follow, `Context.locale(for:)` = the language with everything else of `Locale.current` kept, so the region's units and calendar stay), `localized(_ key: String.LocalizationValue)` (**the one lookup**: `String(localized: key, bundle: context.bundle, locale: context.locale)`) and `LanguageStore` (`@Observable`; `preference`, `language`, `locale`, `select(_:)`; the `apply` closure defaults to `AppLocale.set` and the tests inject a spy, so no test mutates the global; `AppDependencies.makeLanguageStore(arguments:defaults:logger:apply:)` in `App/AppDependencies+Localization.swift` is internal for the same reason). **Every `AppBranding`/`ErrorMessageMapper` string is a `static var` or a function over `localized(...)`**, never a `static let` (a `let` would freeze the first language); keys are the English text, interpolations become `%lld` (Int) / `%@` (String) and the catalog's plural variations pick the form (`localized("\(count) spots left")`); two-argument strings avoid verb agreement in ru/uk/pl ("Участников: %lld из %lld") because a positional plural would need `substitutions`, which nothing here uses; a translation that reorders arguments writes `%1$@`/`%2$@` (ru "Новая игра от %1$@: %2$@"); `InboxItemRow` bolds the invite's names by formatting two markers (`\u{FFFC}1`, `\u{FFFC}2`) and replacing them in the `AttributedString`, so any order works. **Measured on the simulator (2026-10-03):** `String(localized:locale:)` does **not** switch the lproj (it formats only), `LocalizedStringResource(locale:)` and a `Bundle(path: <code>.lproj)` do; `String(format:)` and `String(localized:bundle:)` evaluate plural categories with the *locale argument* (`String(format:locale:)`, `String(localized:bundle:locale:)`), not the lproj's language, so a bundle without the locale gave "2 мест" (en rules) and with it "2 места"; `Bundle.main.localizations` lists every catalog language without a `knownRegions` edit. `AppRootView` puts `.id(language.language)` and `.environment(\.locale, language.locale)` on its root `Group` (copy lands in views as plain strings, so a new language needs the tree rebuilt; `AppNavigation`'s paths survive, view `@State` restarts) and the sync `SyncKey` carries the language so `PushCoordinator.sync()` re-registers the device (`DeviceRegistrationPayload.locale`, `LastDeviceRegistration.locale: String?` for stored rows without one, `languageCode` closure injected; Laurel stores it and renders the reminder per device language from `i18n/push_<code>.properties`); `CognitoClient.signUp/resendCode(..., languageCode:)` send `clientMetadata[locale]` (`AppConfig.Cognito.localeMetadataKey`) for rose's Custom Message Lambda; `AuthProvider.Kind.email`'s display name is localized, the brands are not. Formatting sites that read `Locale.current` now read `AppLocale.locale` (`ChatDayLabel`, `InboxItem+Caption` when the calendar has no locale, `Measurement+Road`, `Price.text/symbol/parseAmount` defaults, `FileCardInfo.sizeText`, `EventPreviewCard`); `EventDetailView` formats its date through `Text(date, format:)` so the environment locale applies. `LanguageRow` (`Features/Profile/Views`) is a `GlassCard` with a `Picker(.menu)` (`profile-language`; options "System" + `nativeName`s, a `Text(verbatim:)` each); the `.menu` picker is a button in XCUITest and its items are `app.buttons["Русский"]`. Launch: `-app-language <code>` (transient, never stored: `LanguageStore(launchChoice:)`; a code the app does not ship is a warning under `.localization` and the system choice), `-reset-session` also clears the stored choice (so UI tests start in the simulator's language). The catalogs are **hand-maintained JSON** (`lily/Localizable.xcstrings`, `lily/InfoPlist.xcstrings`; about 600 keys, no `extractionState`, plural keys as top-level `variations.plural`); `xcodebuild` did not rewrite them during builds, Xcode's editor may; `scripts/l10n-check.py` (in `ci.sh lint`) extracts `localized("...")` and the multi-line `localized("""..."""` form (a `\` joins lines, used where a literal would pass SwiftLint's 160 columns), matches each against exactly one key with `\(...)` as a placeholder wildcard, and requires every key used, every language present and the placeholders equal; `LocalizedCatalogTests` reads the compiled `.strings`/`.stringsdict` of every `.lproj` from `Bundle.main` (the unit tests are hosted in the app) and pins ru/pl plural forms and the English one-forms. A key may carry an explicit `en` value when two roles share one English text and need different translations (`Message (verb)`, the profile's button, beside the composer's noun `Message`; `Any (price)`, the price field's placeholder, beside the distance menu's `Any`): the key names the role, the `en` localization is what English shows, and `LocalizedCatalogTests` pins both; every other key stays the English text itself. Tests: `AppLanguageTests` (+ `LanguagePreferenceTests`, `AppLocaleContextTests` in the same file), `LanguageStoreTests`, `LocalizedCatalogTests`, `AppDependenciesLanguageTests`, the language cases in `PushCoordinatorTests`, `PushModelsTests` and `CognitoAuthServiceTests`; UI: `LilyLanguageTests`. Screenshots of landing, Explore, detail, filter panel, Profile and Home in all seven languages were judged (2026-10-03): nothing clipped; the filter panel's Level menu value wraps to two lines in ru/pl ("Любой уровень"), accepted. The translations were written by the agent in one pass and need a native read before launch. The first full `ci.sh all` after the change failed three UI tests under load (two on `Multiple matching elements` for the Chats tab button right after a sign-in, one on the sign-in popup's hittability), none of them touching the language; all three passed alone and the complete UI suite passed on a rerun (918 s against 1405 s), so treat that pattern as a load flake before suspecting the root view's `.id`.
- **Russian copy pass (2026-10-15, on the user's request: "more neutral and close to how native speakers would say it", with "Вы просматриваете как гость" -> "Вы авторизованы как гость" as the example; the user wrote "авторизированы", the catalog carries the standard spelling).** The whole Russian catalog went through a Workflow of six native-writer agents (about 100 strings each, reading the call sites under `lily/Config` for context) and six independent reviewers; 117 Russian values were rewritten (108 of them strings the previous commit already carried, the other nine among the intro keys written the same day), the rest were judged native already. The rules that came out of it, for the next string: **the Russian register is neutral formal (lowercase вы, вы-imperatives: Войдите, Нажмите, Смахните), never ты**, which the intro slides had used; a direct conversation is a «чат» (never «беседа», which Russian messengers use for a group chat) and the row caption is «Личная переписка» (agrees with «Активна сегодня»); counts under bars are «Участников: N» (the «%lld joined» plural is invariant now); «Мест нет» / «Мест в группе нет» / «Мест в команде нет» / «Мест в турнире нет» for every "full"; bracket stages are singular («Четвертьфинал», «Полуфинал», «Финал»), a bye is «Без соперника», a walkover «Техническая победа: %@», a reported result «Ожидает подтверждения», a scheduled match «Назначен»; Discover is «Поиск» / «Поиск групп» / «Все турниры»; «Назначить администратором» / «Снять права администратора» while the role badge stays «Админ». **A key shared by two roles with different grammar gets a role key**: `AppBranding.Tournaments.Create.drawsNotAllowed` is `localized("Not allowed (draws)")` (en "Not allowed", ru «Не разрешены» pairing with «Разрешены», plural adjectives in es/fr/uk/pl/pt too), because the bare "Not allowed" is the group permission error's title («Недостаточно прав») and one word fit neither place in any language; `LocalizedCatalogTests.aRoleKeyShowsItsEnglishValueAndItsOwnTranslation` pins it with the other two role keys. The reviewers flagged, unchanged: the Ban family («Заблокировать» / «Заблокированные» / «Разблокировать») reads like the personal Block (an «Исключить из группы» / «Исключённые» rename is a product call); «Round of %lld» receives the entry count and reads «Раунд с %lld участниками» (passing entries / 2 would allow the native «1/%lld финала»). UI: `LilyLanguageTests` asserts the new guest title. The other six languages were not reviewed this way yet.
- **Game to event, all languages (2026-10-18).** The 36 renamed keys (see `events.md`) carry new translations in the six languages, written in this session without a native reviewer: ru событие, uk подія, es evento, fr événement, pl wydarzenie, pt evento, with the surrounding grammar adjusted ("Nouvel événement", "l’événement", "Pas encore d’événement", "wydarzeń"). Two keys whose English never said game were retranslated (four values) because their translation did: `%@ created %@` in ru, uk and pl ("Новое событие от %1$@: %2$@"), and "You're already in" in pl ("Już jesteś na liście" for "w grze"). The location permission string moved with them in `InfoPlist.xcstrings`. A native read of the six languages is still owed, as for everything but the Russian pass.
- **A language change rebuilds the tabs' trees, not the bar (2026-10-26, on the user's "when I change the language the menu closes abruptly, like reloaded, the tab bar's red pointer slides from the left to Profile, and the tab icons turn bold until I tap the tab").** `AppRootView` put `.id(language)` on the whole tree, `MainTabView` included, so a pick recreated the `TabView`: a fresh iOS 26 bar slides its indicator in from the first tab, draws its glyphs at its own weight until a tab is tapped (the light outline comes from a `UIImage` symbol configuration the bar honours on the next selection), and the Profile menu vanished with the old tree instead of closing. Now each tab's content carries `.id(language)` inside `MainTabView` (its body reads the store, so the titles re-render in place), the landing keeps its own `.id`, and `LanguageRow` selected inside `withAnimation(.smooth(duration: normal))`, so the Profile screen crossfaded into the new language while the menu closed on its own curve (the animation went again later the same day, below). Verified on an iPhone 17 Pro simulator by a recording of English → Russian → English judged frame by frame by a subagent: the menu's items and glass fade out over four frames, the bar's selection pill stays at its place (its edge eases 3 pt for the wider «Профиль»), the glyph strokes measure the same 1.33 pt in every screenshot, and both languages are superimposed for about 330 ms of crossfade; the screenshot after the way back is byte-identical to the one before. One trace was left: for about five frames the Language card was blank, since the menu's source view stayed hidden until the dismissal ended and the new tree's card was still fading in; and the crossfade itself dimmed the whole screen by about a quarter for a dozen frames with a one-frame step back (the user: "the button jumps and blinks a bit"). So Profile, where the language is picked, is no longer rebuilt: `MainTabView` hands it the language as a plain input (`ProfileView.language`), a changed input re-runs its body in place, and every row reads its copy afresh from there (`LanguageRow` observes the store, `CurrencyRow` reads `\.locale` to name the currencies, the guest prompt's message changes with the body; `FeedbackRow`, whose only input is a closure, which SwiftUI does not count as a change, kept the old language on the recording and takes the language as its `.id`). `LilyLanguageTests` also checks the Currency and Contact cards' titles in Russian, the rows that go stale if a Profile row neither reads its copy in body nor takes the language as its identity. The cards' own control moved from a `Menu` to a popover the same day (`profile-and-feedback.md`); see the same date in `shell-and-navigation.md` for the bar.
