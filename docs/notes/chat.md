# Chat: rooms, realtime, replies, attachments

> The room cache and realtime controller, chat screens, clearing a chat, replies, attachments (pictures, videos, files) and their caps. Moved out of `README.md` and `CLAUDE.md` on 2026-10-17 and kept as written. The reference part describes the feature as the README did; the dated notes record decisions, lessons and the evidence behind them, newest last, so an older sentence can be superseded by a later one or by a marker such as "(removed 2026-10-14)". Read this file before touching the area; the rules that apply everywhere are in `AGENTS.md`.

## Reference (from the README)

- **Chat.** One chat room per group, visible to members (`ChatView`, pushed on the Chats stack from a Chats row, a group's "Open chat" or an accepted invite; the tab bar hides while it is open). Messages are REST writes: `POST /api/groups/{id}/messages` with a `clientMessageId` chosen once per composed message and kept through every retry, so the backend replays a repeat instead of storing a duplicate, and the bubble keeps its identity when the stored message replaces the optimistic one; a send answered `TRY_AGAIN` (the sender's own overlapping writes racing on the backend) is repeated once with the same id (`LostRace.attemptTwice`), and every chat failure goes through `GroupErrorReporter`, so a `TERMS_REQUIRED` on a send or a delete raises the terms sheet as on the groups screens. History is read from `GET /api/groups/{id}/messages` with `limit` and either `before` or `after`: a page is `{items, hasMore, channelEpoch, nextBefore, nextAfter}`, the two cursors being message ids to continue from, present only with `hasMore` and in the direction asked (they may name a message the caller cannot see, so a page of hidden or already-held messages still advances); when a page names none, the app pages before the oldest id it holds and moves its watermark to the newest id returned. A message is text only (`Text(verbatim:)`, no link detection, so a pasted URL never opens on tap), at most 2 000 UTF-16 units, drawn as a plain fill (accent + white for the caller, surface + ink for others; glass is kept for the composer and the day chips because a room scrolls dozens of bubbles at once). One sender's messages within five minutes and on the same day form a run; the timeline (`ChatTimeline`, pure) inserts day chips, shows the sender's *current* name from the roster, hides blocked senders and turns deleted messages into an italic "Message deleted". Deleting a message is for the sender and the group's admins. A message can answer another: Reply, first in a bubble's long-press menu (for any member's message that is not deleted; system rows cannot be answered), puts a preview above the composer ("Replying to Marta", one line of the original, an X) and focuses the field; the send carries `replyToMessageId`, and the backend snapshots a compact quote onto the stored message (`replyTo {messageId, senderUserId, senderName, excerpt?, kind, attachmentKind?}`, the excerpt cut to `AppConfig.Chat.replyExcerptLength`, 120 UTF-16 units, the same cut the app makes for its preview), so pages need no lookup. The bubble draws the quote above its text (a bar, the sender's name, two lines of the excerpt or "Photo" / "Video" / "File" for a media target without text); tapping it scrolls to the original, loading up to `maxReplyLookupPages` (3) older pages when it lies before the history held, and washes it in the accent for a moment. The server never rewrites a stored quote, so a quote reads "Message deleted" only once this device knows the original is gone (the room's tombstones). A reply refused with `REPLY_TARGET_NOT_FOUND` ("That message is gone") keeps its bubble, failed and without the quote, and Retry sends it as a plain message. Clearing the room is per side: `DELETE /api/groups/{id}/messages` moves the caller's history floor to now (the floor the backend already honours on every page) and drops their read marker, so the messages before it are gone for the caller alone while every other member keeps them; the backend's `hidden` verdict decides what follows (not the room's kind): a group keeps its row and its cached room is seated at the floor (what lies at or below it dropped, the watermark moved there, so a quiet cleared room is not fetched again and a live line still lands), a direct conversation (whose item reads "Delete chat") is dropped at once everywhere (Mine, cache, dot, realtime subscription) and leaves the Chats tab until either side writes again and then returns with only the new lines; under `-mock-events` the mock's sent, replied and floor ids are minted per room above every fixture row, and its clear reads the room as read on the next Mine load (`ChatHistoryClearer` in `Features/Chat/Services`, shared by the room's menu and the Chats rows' context menu, both behind a confirmation). A system row (`event_created`) names the game once it is fetched and opens it. The read marker is sent when the room opens, at most once a minute while it is open, and when it closes or the app goes to the background; `UnreadCenter` (fed by the Mine load, live messages and the open room) drives the dot on a Chats row and, with the inbox's unread flag, the badge on the Chats tab; a Mine load is merged into it, not copied: a live mark newer than the snapshot's read marker stays, and the snapshot's flag is taken only when its newest message is newer than what was read here, so joining or editing a group cannot bring a read room's dot back. A 429 closes the composer for the `Retry-After` seconds with "Slow down a moment" under it. Report and Block sit in another member's live message's menu (never on a tombstone, and the caller's own tombstone has no menu at all): Report opens the report sheet over `ReportTarget.message(id:groupID:)`, Block sends `PUT /api/blocks/{userId}` and `BlockListStore` (`Features/Groups/State`, loaded once per user by the shell sync, cleared on sign-out) hides the sender's rows at once, live inserts included. The unsent outbox (`ChatOutbox`, `Features/Chat/State`) is in memory: a failed or in-flight bubble survives leaving the room and shows with Retry on the next open, a sign-out empties it, and a message that failed to send is lost when the app is killed.
- **Attachments (pictures, videos and files).** A "+" leading the composer's field opens Photo library (the system picker for pictures and videos, no permission prompt), Camera (hidden where there is none, the simulator included) or File (the files importer, any type, several at once); it shows only while `GET /api/me` says `attachmentsEnabled` (the backend has a bucket; without one it answers `409 ATTACHMENTS_DISABLED` and the button is simply absent). Each picked item becomes an `AttachmentDraft` in the composer's `AttachmentComposerModel` (`DeviceMediaPreparer` behind the `MediaPreparer` seam routes it to one of three workers). A picture is downsampled to 2048 px on the longest side and re-encoded as JPEG at quality 0.85 (`ImagePreparer` over `CGImageSource`, off the main actor, so a HEIC or a PNG leaves the device as `image/jpeg` and a 48 MP photo is never decoded whole) with a 512 px thumbnail (at most 200 KB, left out when it will not fit). A video is exported at `AVAssetExportPreset1280x720` into an MP4 (`VideoPreparer`, so a 4K recording leaves the device as 720p `video/mp4`), a frame at 0.5 s becomes its thumbnail through the same image path, and its duration and dimensions ride along as hints; a clip longer than 3 minutes is refused before any export, one over 50 MB after it. A file is copied in under the draft's id (`FilePreparer`, reading the importer's URL under its security scope), typed from what the system knows (`application/octet-stream` when nothing), named after itself (cut to 255 UTF-16 units), refused over 25 MB, and gets no thumbnail (the backend refuses one on a file). Every draft then asks for a ticket (`POST /api/groups/{id}/uploads` with `{clientAttachmentId, kind, contentType, sizeBytes, width, height, thumbnail {contentType, sizeBytes}}` -> `{attachmentId, upload {url, headers}, thumbnailUpload?, expiresAt}`) and PUTs both files to the presigned targets with exactly the headers the ticket names (`URLSessionAttachmentUploader`, a session of its own with `waitsForConnectivity` and a 120 s timeout; two uploads at a time through a `SlotGate`, an item removed while it waits handing its slot on). The strip above the field shows each item at 72 pt (a picture as its thumbnail, a video as its thumbnail under a play badge, a file as a chip with its type glyph, name and size) with its progress ring, a failed glyph that retries on tap (a new ticket) and an X (removing an item, or leaving the room with items still preparing or uploading, cancels its work, a running video export included, and deletes its files; the Photos import copy of a video is removed after the prepare in any case, the files importer's original never; a thumbnail that cannot be made leaves the picture or clip to go without one); Send opens once every item is uploaded (words alone, attachments alone or both), and the message's `attachments` names the tickets' ids (`{attachmentId, kind, contentType, sizeBytes, fileName?, width?, height?, durationSeconds?, hasThumbnail}`, `text` omitted when blank). Caps mirror Laurel's (`AppConfig.Chat.Attachments`): 10 per message, 10 MB per picture after re-encoding, 50 MB and 180 s per video after the export, 25 MB per file, file names cut at 255. **A direct conversation takes smaller caps** (`AttachmentCaps.direct`, since 2026-10-09): 20 MB per video and 5 MB per file, pictures unchanged, because anyone can start a conversation from a roster or a profile; the composer hands its room's caps (`AttachmentCaps.caps(for:)`) to the preparers, the mock ticket judges by the room's kind like Laurel's `attachments.direct-*-max-bytes`, and over a cap the item is refused on the device with "That's too big", whose body names the three caps of that room. The stored message carries `attachments [{id, kind, contentType, sizeBytes, fileName?, width?, height?, durationSeconds?, url, thumbnailUrl?, urlExpiresAt}]` with presigned links good for an hour; the bubble draws pictures and videos as a gallery (one at its own aspect ratio, two side by side, three or four as squares, "+N" on the fourth beyond that; a video tile carries a play badge and its length; a caption below, and media alone is the bubble itself) and files as cards under it (type glyph, name, size, a download glyph until the bytes are on the device; a file card keeps the bubble's fill), a tap opens a viewer over black (`AttachmentViewerSheet`) that pages through every picture and video of the message from the tapped one ("+N" opens the first hidden one; "n / m" in its bar; pinch to zoom, double-tap to reset, Share; a video plays only while its page is on screen, once the clip is on the device, a ring showing the download), or opens the file in QuickLook (downloaded with a ring on the card first), and a tombstone drops them all. A kind this build does not know (`AttachmentKind.unknown`) still decodes, draws as a file card and is never uploaded. Links are never cached, only bytes by attachment id: `DiskAttachmentCache` keeps them under `Caches/Attachments/<id>` and `<id>.thumb` (200 MB, least recently used out first; a sign-out clears it and the `tmp/AttachmentPreviews` copies before the session flips, and a removal the file system refuses is logged, never claimed), the files of an item just sent are copied in under the stored id before its bubble appears, once per id however many answers settle the same message, so it never downloads, and `AttachmentLoader` fetches a miss once (reporting progress when asked; a picture stored without a thumbnail is downloaded and cached once, whichever variant the gallery or the viewer asks for), refreshing the link through `GET /api/groups/{id}/messages/{mid}/attachments/{aid}` when it is within a minute of expiry and once more after a 403 (presigned links die with the backend's credentials); the player and QuickLook read a hard link to the cached bytes under `tmp/AttachmentPreviews/<id>/<name>`, named after the file or, for a video, the content type's extension, because both decide what they read from the name; both remove that copy when they close. Refusals with copy of their own: `ATTACHMENT_NOT_FOUND` (the upload never finished, or someone else's), `ATTACHMENT_TOO_LARGE`, `ATTACHMENT_TYPE_NOT_ALLOWED`, `ATTACHMENTS_DISABLED`; a ticket or PUT that fails otherwise is "Couldn't upload the attachment", a download "Couldn't load the attachment". Uploads are foreground only: backgrounding mid-upload fails the item and Retry asks for a new ticket.

### Realtime

The realtime API (AWS AppSync Events; the client lands in a later milestone, `Repositories.remote` wires `NoRealtimeTransport` until then) only pushes what the backend has committed, on `rooms/<groupId>/<channelEpoch>` and `users/<sub>`. Every leave, removal and ban bumps a room's `channelEpoch`, which renames its channel, so someone who left stops receiving without the server having to track sockets. `RealtimeSessionController` (`Core/Realtime`) holds the one connection while the app is active with a signed-in user, driven by `AppRootView` from `scenePhase` and the session (`setDesired(active:user:)`): `users/<sub>` plus the open room and the ten most recently active groups of Mine, closed in the background and on sign-out (it is a `SessionObserver`, like every per-user store), renewed with a force-refreshed token (`AuthTokenProvider.freshAccessToken()`, used for nothing else) five minutes before the token expires; a refresh that yields the same token falls into a backoff instead of looping.

- **Resume protocol.** Every open (launch, foreground, reconnect) subscribes first, reloads Mine once, then catches up over REST only the open room and the cached rooms whose newest message moved, three at a time. A naive foreground would fetch every room; this stays under five requests. A page that answers a newer epoch than the room is subscribed at makes the room resubscribe there and be caught up once more, by name, because its watermark already moved. One connect runs at a time: a caller finding one in flight waits for it and then makes its own attempt, and `close()` cancels the connect in flight, so a suspend or a sign-out during a slow connect opens nothing, or closes at once what the handshake still opened. When no connection comes up (no endpoint, no token, a failed open), the open room alone is caught up over REST, so a foreground against a local Laurel still shows what arrived meanwhile.
- **Two cursors per room.** `ChatRoomState` keeps what is shown and the REST watermark, which only `newest`/`newer` pages move, so the next catch-up always starts where REST left off; a lost publish is a delay, never a hole. The room cache (`InMemoryChatHistoryCache`, 300 newest rows per room) is the one owner of room state: the controller's live inserts and catch-ups land where the open chat reads. `ChatCatchUp` merges every page into the room as the cache holds it at that moment (`ChatHistoryCache.update`) and re-reads the watermark after each request, never from a copy taken before it, so a live insert, a tombstone or a drop that landed while the page was in flight is neither overwritten nor resurrected; a room dropped meanwhile stays dropped (`loadNewest` and `catchUp` answer `nil`).
- **Epochs.** A `member_left` carrying a newer epoch is trusted and resubscribed with a small jitter (no group read), and any answer carrying a newer epoch (a page, a send, a read marker, a group) makes the room resubscribe and catch up; one `moveEpoch` writes the cached room's epoch only when newer and logs "Epoch changed" once. A room the caller lost (a page or write refused with `NOT_A_MEMBER` / `GROUP_NOT_FOUND`, a conversation a clear hid) is dropped everywhere at once (`removeGroupLocally`: Mine, cache, dot, known epoch, open room, subscription).
- **Reconnects.** A lost connection, or a renewal whose refreshed token is missing, backs off along `AppConfig.Realtime.reconnectBackoffSeconds` (1, 2, 4, 8, 16, 30 s, jittered; `Backoff` and `RenewalDelay` in `Core/Realtime/Models` are the pure values that decide every wait); without a token the retries stop after `maxReconnectsWithoutToken` (8, about two minutes) until the next foreground, and a connect that does obtain a token starts the budget over. A connect that lands cancels a backoff still pending (an active <-> inactive flip re-runs the resume while one waits), a room resubscribed on the same channel within one turn is not read as a lost connection (every subscription carries its own id), a room whose resubscribe jitter is re-armed by a second `member_left` is waited out before the open chat counts itself subscribed, and the offline catch-up of the open room runs only while the app is active.
- **Endpoint discovery.** `GET /api/me` names the realtime endpoint; `-realtime-endpoint <url>` overrides it for a debug build against a deployed backend, and the release constant is the fallback. Against a local Laurel none is known, so the connection stays off and chat catches up over REST only: on appear, after a send and, for the open room, on every return from the background (`RealtimeSessionController.resume()` runs that catch-up itself when no connection came up, and only after a `suspend()`: an active <-> inactive flip fetches nothing).
- **Tournament rooms.** A tournament's room also carries `tournament_changed` and `match_updated` (see [Tournaments](tournaments.md#tournaments)); the controller bumps the tournament change counter on them and adopts a newer epoch, nothing else.
- **Mock transport.** `-mock-events` wires `MockRealtimeTransport`, an in-memory bus: the mock chat echoes every send to the room's channel after 200 ms, and `-mock-chat-replies` makes Marta answer after 1.5 s and deepens every room to 300 rows.

- **Chat screens.** `ChatView` (`Features/Chat/Views`) is `ContentScreen { ChatTranscript ... .safeAreaInset(edge: .bottom) { MessageComposer } }` with the group's name as its inline title, the member count as the subtitle (none for a direct conversation, whose title is the other person), the tab bar hidden and an info button that pushes `GroupInfoDestination` (the `.fromChat` detail, whose "Open chat" is hidden so the path never cycles) or, in a conversation, the other person's profile (which hides its "Message" button, so the path never cycles). `ChatTranscript` is a `ScrollView` + `LazyVStack` over `viewModel.rows` anchored to the bottom (`defaultScrollAnchor(.bottom)`, `scrollPosition`): `TranscriptScrollPolicy` (`Features/Chat/Models`, pure and unit-tested) decides from a `Snapshot` of each geometry report: pin the newest row above the composer once the first page has laid out (the default bottom anchor ignores the composer's safe-area inset), ask for the page before only when the reader has scrolled within `Layout.olderPageTriggerDistance` of the top after that first settle, and keep what was on screen where it was after the prepend by adding the new height to the offset (`ChatViewModel.loadOlder()` answers whether the page brought rows, and the policy learns whether the top moved from the room's `oldestID` handed to `willLoadOlder`, never from the content height, so bottom growth while an older page is pending, a live line or the keyboard, is neither compensated as a prepend nor turned into a second request; one older page runs at a time, a quote tap joins it, and a page whose anchor moved meanwhile is dropped); the caller's own messages always scroll into view, others' only while the list is already at the bottom (`onScrollGeometryChange` decides, within `Layout.atBottomThreshold`); a change of the bottom inset (keyboard, a growing composer) puts a list that was at the bottom back there, because the scroll view otherwise leaves the offset past the end. `MessageBubble` and `PendingMessageBubble` are plain fills (`Radius.bubble`, `Layout.bubbleMaxWidthFraction` of the list), never glass; `DaySeparator` is a `lilyChip(.regular)`; `MessageComposer` uses `lilyMultilineField()` (glass in a rounded rectangle at the field's minimum height, since a five-line capsule reads as a blob) and `lilyIconButton()` (a prominent glass circle) inside a `GlassEffectContainer`, and re-evaluates its cooldown caption once a second. A bubble's identifier is `message-client-<clientMessageId>` when the message has one (the caller's always, every member's from Laurel) and `message-<id>` otherwise (the mock's other senders); `MessageMenuItems` decides once what a long press offers and a row without items gets no menu; `BubbleFill.standsAlone` is the one rule for a message whose media is the bubble. `ChatViewModel` keeps its unsent bubbles in the shared `ChatOutbox`, flushes the read marker through `ReadMarkerFlusher` (`Features/Chat/Services`: at once on open, at most once per `readMarkFlushInterval` while open, at once on leave or background, a failed flush giving the id back) and holds its system rows' texts, lookups and destinations in `SystemRowContent`, which remembers a gone game or tournament so it is looked up once. The Chats tab carries `.badge(unreadCenter.count + (inbox.hasUnread ? 1 : 0))`, a Chats row its `UnreadDot`; `AppRootView` drives `RealtimeSessionController.setDesired(active:user:)` from `scenePhase` and the session, and sign-out closes the connection through `SessionObserver`. The room's "more" menu (`ChatRoomMenu`, a second trailing toolbar item) holds one destructive item, `ChatClearMenuItem`, which the Chats rows' context menu reuses (`GroupRowList<RowMenu>` takes an optional `rowMenu` closure; Home passes none), both worded by `ChatClearPrompt` and confirmed through the shared `chatClearConfirmation` modifier (the room's in `ChatView`, the rows' in `ConversationList`, which owns it for the compact list and the iPad sidebar alike) before `ChatHistoryClearer` runs; `hidesTabBarOnCompact()` is the one tab-bar hide of the room and the inbox. (Animated through the stack root's `animatesTabBar(depth:)` since 2026-10-18; see `shell-and-navigation.md`.) Replies: `ReplyPreviewBar` is its own glass block above the field inside the composer's `GlassEffectContainer` (a container element, `chat-reply-preview`, so the X keeps `chat-reply-cancel`); `QuoteBlock` is a plain fill inside the bubble (white at `Opacity.quoteFill` on the accent, ink on the surface, a `quoteBarWidth` bar, `Radius.quote`), one accessibility element `message-quote-<id>` whose label is name plus text; `QuoteStack` (a small `Layout` in `QuoteBlock.swift`) lays the quote over the text at the wider of the quote's own words and the text, so a short reply under a short quote still hugs its words where a `VStack` with `maxWidth: .infinity` would make every reply as wide as the list allows; both quote rows are `fixedSize(horizontal: false, vertical: true)`, because the bar is a shape and took the whole height the composer's inset offered; `MessageBubble` is an accessibility container (`.accessibilityElement(children: .contain)`) so the quote's identifier survives the row's own. A tapped quote runs `ChatViewModel.revealQuoted(id:)` and then `position.scrollTo(id:anchor: .center)` with a `highlightedMessageID` wash for `Duration.messageHighlight`. Pictures: `BubbleContent` (its own file, shared by `MessageBubble` and `PendingMessageBubble`) stacks quote, gallery and words in `QuoteStack`, and a message that is its pictures alone has no fill at all, the gallery clipped to `Radius.bubble` is the bubble; `GalleryGrid` fixes its width to `Layout.galleryWidthFraction` (0.6) of the list through `containerRelativeFrame`, which is what lets `QuoteStack` measure it (a flexible view would answer its ideal width, nothing) and keeps bubble padding plus another sender's avatar column inside `bubbleMaxWidthFraction` on every iPhone width; a single picture fits its own aspect ratio within `Layout.galleryMaxHeight` (a tall one gets narrower and keeps to the bubble's side), the rest are squares in a two-column `Grid` (a lone last tile spans both columns). Tiles are plain `Color.lilySurface` fills with the picture `scaledToFill` and clipped, a spinner while it loads, a faint glyph when it could not (no blur hash is on the wire). The composer's attach "+" and the viewer's Close and Share are `lilyGlassIconButton()` (a plain glass circle, the quiet sibling of the prominent Send); the viewer shares the decoded `Image` through `ShareLink` (the cached file has no extension, so a file URL would not share as a picture). The strip is `.scrollClipDisabled()` with top and trailing padding, so each tile's X can poke out of its corner. Videos and files: `AttachmentGallery` splits a message through `GalleryLayout.partition` into the grid's tiles (pictures and videos, a video under `PlayBadge` with `DurationBadge` in its corner) and `FileAttachmentCard`s under it at the same `galleryWidth`; `FileCard` (type glyph in a square, the name over the size, a trailing slot) is the one shape for a stored file, a picked file in the pending bubble and the strip's chip, a faint fill like a quote's (white on the accent, ink on the surface), so `BubbleContent` keeps its fill for a message that is a file alone (`mediaStandsAlone` false) while a picture or video alone stays the bubble itself. `AttachmentViewerSheet` is one full-screen pager over the message's pictures and videos (`ImageViewerPage`, `VideoPlayerPage`; `AttachmentSelection` keeps the tapped tile and sends the "+N" tile to the first hidden picture; a video plays only while its page is on screen): the video page downloads the clip through the loader first (a `ProgressRing` over black) and plays the named preview file in `VideoPlayer`, so the mock's `mock://` links play like the bucket's, and removes that preview copy when it closes; the tiles, the video thumbnail and the viewer load through one `AttachmentImageLoad` state box, and both galleries draw through `AttachmentColumn` over `GalleryItem`; files open through SwiftUI's `.quickLookPreview` (`QuickLookPreview`, which also removes the preview copy when the sheet closes), because a `QLPreviewController` hosted inside another presentation shows no Done button; on iOS 26 QuickLook's Done is an X labelled "close" under its own identifier `QLOverlayDoneButtonAccessibilityIdentifier`, which is what the UI test taps.

## Dated notes

- **Chat core and realtime (2026-09-25, slice S5a of M2; no chat screen yet).** `Core/Realtime`: `RealtimeTransport` (`connect(endpoint:)`, `subscribe(to:) -> AsyncThrowingStream<RealtimeEnvelope, any Error>`, `disconnect()`; errors `RealtimeTransportError.unauthorized/subscribeRefused/unavailable/connectionLost`), `RealtimeEndpointProvider` (`nil` = catch-up only), `RealtimeChannel` (`.room(groupID:epoch:)` -> `rooms/<id>/<epoch>`, `.user(sub:)`), `RealtimeEnvelope` (decoded from `type`; `.unknown(type:)` for anything new), `RealtimeSessionController` (@Observable, `SessionObserver`; `setDesired(active:user:)` is the shell's one input, `suspend()`/`resume()`, `syncRooms()` reads `MyGroupsStore.groups`, `setOpenRoom(_:)` and `ensureSubscribed(_:)` are the chat's, `envelopes(for:)`/`userEnvelopes()` (removed 2026-10-14) fan out; stored properties are internal because `+Connection.swift` (open, exp-bound renewal via `JWTClaims.expiration(of:)` + `AuthTokenProvider.freshAccessToken()`, same-or-older `exp` -> backoff table with jitter, backoff on lost connections, 401 -> `.sessionExpired` once, resume protocol; one connect at a time: `connect(fresh:)` waits out the task in flight and then makes its own attempt, `close()` cancels that task and bumps `connectionGeneration`, a superseded attempt opens no socket (or closes at once what the handshake still opened, in a task of its own since the superseded one is cancelled) and arms no reconnect timer, and one superseded while `isActive && user != nil` answers `true` so its caller tries again) and `+Routing.swift` (subscriptions, cache and unread updates, `member_left` trusted with jittered resubscribe, refetch only on a refused subscribe, `users/<sub>` handling, local drop of a group the caller lost) are extensions). **The room cache is the truth**: `ChatHistoryCache` (`InMemoryChatHistoryCache`, @Observable, `SessionObserver`) holds one `ChatRoomState` per group and both the controller and `ChatViewModel` read and write it, so the open chat sees what the controller's catch-ups and live inserts put there; `ChatCatchUp` (`Features/Chat/Services`) is the one REST catch-up (`loadNewest`, `catchUp` anchored to `restWatermark`, `catchUpMovedRooms` for the resume protocol, and `catchUpRooms(_:maxConcurrent:)` for its second pass over the rooms whose epoch a page moved, by name, because the first pass already moved their watermarks); every page is applied through `ChatHistoryCache.update` and the watermark re-read after each await, never from a copy taken before the request (found 2026-09-26: the copy overwrote a live insert or a tombstone that landed meanwhile and resurrected a room `removeGroupLocally`/`sessionDidEnd()` had dropped), `loadNewest` caches a stub before its request so a live message has somewhere to land, and both answer `nil` when the room is not cached or was dropped meanwhile; `ChatViewModel.mutateRoom` (the write behind `loadOlder`, `delete`, the send's settle and `adoptEpoch`) is the same `update` plus re-read and answers `nil` the same way, so no late answer re-creates a room (`ChatViewModelDroppedRoomTests`). `RealtimeSessionController.resume()` without a connection (`.unavailable`, no token, a failed open) catches up the open room alone over REST (`catchUpOpenRoomWithoutConnection`), because the resume protocol runs only after a connect and a local Laurel has no endpoint;
