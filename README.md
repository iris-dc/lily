# Lily

Meetup-style iOS app for sport events: sign in, create and join events, chat with participants.
iOS 26+, SwiftUI, Liquid Glass, dark-only design (for now) with a rust-leaning red accent over maroon. The backend, Laurel (`iris-dc/laurel`, a Spring Boot 4 service), runs on AWS on a tight budget: Cognito for identity, one small ECS Fargate task over DynamoDB for business logic and data; see AWS deployment below.

## Status

Early days. Auth is **mocked**; events and profiles come from the Laurel backend when it runs locally (see [Backend](#backend)) or from in-memory mocks with `-mock-events`. No AWS resources exist yet.

- Landing screen that explains the product (headline, live preview of upcoming events) with one tap into the app. Sign-in (Apple / Google / Email) is optional and lives in a sheet.
- Tabbed shell (Explore, My Events, Profile). Explore switches between a list (with distance from the user) and a map with one glass pin per event; selecting a pin shows a preview card that opens the event detail. A filter panel drops down from the Explore toolbar and narrows list and map by event type (multi-select, including "Other"), distance from the user's position (10 km by default), a maximum price you type in, skill level, a date range and open spots. An event may carry optional details: a description, who the host is looking for, a skill level and a per-person price; the detail screen shows whichever are set, and list cards and preview cards show the price of paid games. My Events asks a guest to sign in instead of requesting a user-scoped list.
- Event detail with join and leave for signed-in users: the button follows the caller's relation to the event (Join, Leave, "Event is full", "You host this game"; nothing for guests), the count and capacity bar update from the server's answer, and the list behind it reflects the change on the way back.
- Session persistence across relaunch (guest choice and mock session).
- Shared error popup, typed errors, logging facade, unit tests for all business logic.

## Requirements

- Xcode 26.5 or newer (the deployment target is iOS 26.5; the project was last upgraded with Xcode 26.6), with an iOS 26.5 simulator runtime.
- No AWS credentials needed to run or test.

## Run

Open `lily.xcodeproj`, select an iPhone simulator, run the `lily` scheme.

From the command line:

```sh
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer   # only if xcode-select points at the Command Line Tools
xcodebuild -scheme lily -destination 'platform=iOS Simulator,name=iPhone 17 Pro' build
```

## Test

```sh
./scripts/ci.sh unit     # unit tests (lilyTests)
./scripts/ci.sh ui       # UI smoke tests (lilyUITests)
```

Both pick a simulator for you, and the UI stage passes `-parallel-testing-enabled NO`, because simulator clones intermittently failed to launch the test runner; a hand-typed `xcodebuild ... test` would run without that flag. A test stage also fails with "no tests were executed" when its log shows no test case, because `xcodebuild` exits 0 and prints a passing suite when `-only-testing` matches nothing.

Tests use Swift Testing and fakes for every interface (`lilyTests/Support/TestDoubles.swift`, with fixtures in `TestFixtures.swift` and the API client fakes and contract samples in `NetworkingDoubles.swift` beside it; `makeEventListViewModel(...)` builds a list view model over fakes and `settle(until:)` yields until a condition holds, bounded).
UI smoke tests in `lilyUITests/` launch the real app with the `-reset-session`, `-mock-location` and `-mock-events` arguments (see `AppConfig.LaunchArguments`; `-start-as-guest` skips the landing; `-mock-events` serves the fixture events in memory so no backend needs to run). The arguments are honoured in debug builds only (`AppConfig.LaunchArguments.isHonored`); a release build ignores them. The tests query controls by the identifiers in `Config/AccessibilityIdentifiers.swift` and mirror those literals, as they mirror the launch arguments, because the test target cannot import the app module. They walk the landing → Explore and landing → sign-in sheet → mock Apple → Explore paths, plus the Explore map: switching list → map, and selecting a pin, which asserts the preview card stays clear of the floating tab bar. Another drops the filter panel down, picks Football, checks that list and map shrink to that one game, and resets the filters. Two more cover the sign-in sheet: with `-mock-auth-fail` a failed sign-in must show the error popup *above* the sheet, and signing in from the guest Profile tab must close the sheet. One more signs in, opens "Doubles, all levels", taps Join, checks the control turns into Leave with "2 of 4 joined", finds the game under My Events without a manual refresh, opens it from there, taps Leave, checks Join is back with "1 of 4 joined", and finds the card gone from My Events on the way back.

Run everything the way CI does:

```sh
./scripts/ci.sh          # lint, build for testing, unit tests, UI tests (the one step CI runs)
./scripts/ci.sh lint     # or: build | unit | ui
```

Linting uses [SwiftLint](https://github.com/realm/SwiftLint) (`brew install swiftlint`) with the rules in `.swiftlint.yml`; CI runs it in strict mode, so every warning fails the build.

Logs and `.xcresult` bundles land in `build/results/`.

## CI

GitHub Actions (`.github/workflows/ci.yml`) runs on every push and pull request to `main` on a `macos-26` runner: it selects the newest Xcode 26, installs SwiftLint with Homebrew (the runner image does not ship it), then runs `scripts/ci.sh all` as one step (lint, one build for testing, then unit and UI tests without rebuilding) and uploads the result bundles as an artifact. The runner needs Xcode 26.5 or newer, the same minimum as [Requirements](#requirements).

To make the mock auth fail and see the error popup, launch with `-mock-auth-fail` (previews can use `AppDependencies.makeMock(authBehavior: .fail(.network))`).

## Backend

Events and profiles come from **Laurel**, the Spring Boot backend (its own repository), which the app reaches at `AppConfig.API.baseURL`, `http://localhost:8080`. The simulator shares the Mac's loopback interface, so a Laurel started locally with its `local` profile (DynamoDB Local, auth bypass, seeded with the same nine fixture events the mocks produce) is all that is needed: start it, run the app, and Explore shows the seeded events. Participation is not seeded: against the backend every game shows Join and My Events starts empty, while the mocks pre-join every fourth fixture so the tab has content. Plain HTTP to `localhost` needs no App Transport Security exception, because ATS exempts unqualified host names.

Without a backend, launch with `-mock-events`: `MockEventRepository` serves the fixtures and joins and leaves in memory, and `MockProfileRepository` accepts every display name. Previews use the same mocks through `AppDependencies.makeMock()`, and the UI tests pass the argument so they never depend on a running server. Without either, every list load and join reports "You're offline" through the popup, and the lists show the refreshable "Couldn't load events" state (the landing preview fails silently, logged at warning, and just shows no events).

**Identity.** The user id is the Cognito `sub`. Locally the backend has no Cognito, so a **debug build** identifies the signed-in user with the `X-Local-User-Id` header (`AppConfig.API.sendsLocalUserHeader`, `true` only under `#if DEBUG`); release builds never send it and will carry a Cognito token instead. A guest sends no identity and runs as the backend's `local-dev` user, which the backend treats like any other user; it is the app that hides Join and Leave for guests (`Participation.hidden`), so a header-less `curl` can join as `local-dev`. The header value comes from an `IdentityProvider` (`SessionIdentityProvider` reads `SessionController.state.user?.id`), so the client never depends on the session controller. Right after a successful sign-in the app `PUT`s the user's display name to the profile endpoint, fire and forget, so the backend can stamp the host's name onto events; a failure is logged, never shown.

**Contract, in words.** JSON, UTF-8, ISO-8601 instants in UTC (`2026-09-13T17:00:00Z`; the app also reads fractional seconds and always writes without). `GET /api/events?scope=upcoming|joined` returns events ascending by start: `upcoming` is capped at 100 (Laurel's `events.upcoming-limit`), `joined` returns the caller's upcoming events, hosted ones included, uncapped (past games are not listed). `POST /api/events/{id}/participants` joins and `DELETE` on the same path leaves; both return the updated event. `PUT /api/profile` with `{"displayName"}` returns the profile. An event carries `id`, `title`, `type` (`EventType`, including `other`), `startsAt`, `location {name, coordinate {latitude, longitude}}`, `capacity`, `participantCount`, `hostUserId`, `hostName`, `isJoined` (whether the caller participates) and the optional details `description`, `lookingFor`, `skillLevel` (`beginner|intermediate|advanced`) and `price {amount, currencyCode}` (a JSON number, absent means free); optional fields are absent, never `null`, and `SportEvent` decodes the shape directly, key for key. Failures carry `{"code", "message"}`: `EVENT_NOT_FOUND` (404), `EVENT_FULL`, `ALREADY_JOINED`, `NOT_A_PARTICIPANT`, `HOST_CANNOT_LEAVE`, `TRY_AGAIN` (409; the last means the write lost a race with another player or was throttled by DynamoDB and is safe to repeat) and `VALIDATION_FAILED` (400); the first six map to their own `AppError` cases and copy, anything else becomes `.eventsUnavailable` on a read and `.participationFailed` on a join or leave, and a transport failure becomes `.network`. `GET /api/events/{id}` returns one event: the detail screen fetches it after any of the 409s, and after a 500 or a transport failure on a join or leave (the write may have committed before the answer was lost), so the count on screen and in the lists behind it is the server's before the popup explains the refusal; a `TRY_AGAIN` is first repeated once after `AppConfig.API.tryAgainDelay`.

The Xcode project uses synchronized folder groups: any file added under `lily/`, `lilyTests/` or `lilyUITests/` joins the matching target automatically. The other side of that convenience is that **`lily/` must contain only Swift sources and `Assets.xcassets`** — any other file there is copied into the app bundle, and `.gitignore` does not prevent it, because Xcode reads the filesystem rather than the git index.

Rules: interfaces and implementations live in separate folders, constants live under `Config/`, every user-facing error goes through `ErrorCenter`, every log line goes through `Logging`.

## Architecture notes

- **Session state machine.** `SessionController` owns `SessionState` (`loading`, `signedOut`, `guest`, `signedIn`). Views only read it; all transitions are methods on the controller.
- **Auth interface mirrors Amplify.Auth.** `restoreSession`, `signIn(with:)`, `signUp`, `signOut` map 1:1 to `fetchAuthSession`, `signInWithWebUI` / `signIn(username:password:)`, `signUp`, `signOut`, so `CognitoAuthService` will replace `MockAuthService` without touching callers.
- **SessionStore is a hint, not truth.** In production it only stores the guest choice; Amplify keeps tokens in the Keychain. The mock also stores its fake session there.
- **Branding lives in `Config/AppBranding.swift`:** app name, landing headline and copy, tab titles, empty states, sign-in and profile copy, button titles. `AppBranding.Events` holds the capacity copy ("Full", "N spots left" on compact cards, "N of M joined" under the capacity bar) and `SportEvent.availabilityText` / `capacityText` are the only formatters, so the landing preview card and the capacity bar cannot disagree. Change copy there and every screen follows; UI tests match on the same literals.
- **Colors** are asset catalog colorsets with light and dark variants, exposed via generated symbols (`Color.lilyAccent`, `Color.lilySecondary`, `Color.lilySurface`, ...). Rust-leaning red `#B72734` is the accent, maroon `#5E0C26` the deep tone behind it, and the aurora core keeps the original raspberry `#B31B3F` in its own colorset (`LilyAuroraCore`) so the accent can be retuned without moving the background; amber (`lilySecondary`) is used sparingly for event-type chips, the hero badge and the "nearly full" capacity state.
- **Location:** `LocationService` returns one fix or `nil`; the app never blocks on it. `CoreLocationService` reads a `LocationUpdateSource` (`CoreLocationUpdateSource` wraps `CLLocationUpdate.liveUpdates`, which prompts for when-in-use permission; the usage text is an `INFOPLIST_KEY_` build setting) and races the first fix against `AppConfig.Location.fixTimeout` in a task group, so cancelling its caller closes the stream. The seam lets the timeout, denied and first-fix paths be unit tested with a scripted fake. `CachedLocationService` wraps it in production: concurrent callers share one upstream request (which deliberately outlives any single caller's cancellation, bounded by `fixTimeout`, so the fix it obtains is cached for the next screen), a fix is reused for `fixTTL` (300 s) and a missing fix for `failedFixTTL` (30 s), so sibling tabs never open two CoreLocation streams. When the app returns to the foreground (the one moment permission may have changed in Settings) the events screens call `retryUserLocationIfMissing()`, which asks the cache to `forgetMissingFix()` and requests again, so the distance filter becomes available without a relaunch. `Coordinate` stays Foundation-only; the CoreLocation bridge lives in `Coordinate+CoreLocation.swift`. Distance is computed on-device with a haversine, no network.
- **Events list caching:** `EventListViewModel.loadIfStale()` (used by `.task`) reuses events loaded within `AppConfig.Events.listStaleAfter` (60 s) when a tab reappears; pull-to-refresh calls `load()` and always reloads; a cancelled load is logged, not reported; a failed load shows a refreshable "Couldn't load events" state instead of the empty state, and `loadIfStale()` does not retry it for `AppConfig.Events.retryAfterFailure` (10 s), so switching tabs while the backend is down does not hammer it; a change made elsewhere or a change of caller ends that wait early, because it proves the backend is up and the answer different. A join or leave on the detail screen comes back through `replace(_:)`, which updates the list in place (and drops the event from a joined-only list when the user left), and bumps the shared `EventChangeTracker`; every other list compares the version it loaded against it and reloads on its next appearance, so My Events shows a join made from Explore without waiting out the 60 s. A list also remembers the user it loaded for and reloads after a sign-in or sign-out, because `isJoined` is the server's answer for that caller. Every one of these decisions is logged under `.cache`: the reason for a reload (never loaded, changed elsewhere, caller changed, retry after failure, older than TTL), a skipped reload (fresh, or waiting to retry) and the invalidation of sibling lists in `replace(_:)`. A failed load reports the mapped error ("You're offline", "Events unavailable"), never a blanket one. This view-model-level check is interim until the cached `EventRepository` ships.
- **Filter panel and capacity bar.** `EventFilter` holds every criterion: `types` (a set of `EventType`, which now includes `other`), `maxDistanceMeters` (defaults to `AppConfig.Events.defaultFilterRadiusMeters`, 10 km, so the default filter already limits distance and still counts as inactive; `nil` is "anywhere"), `maxPrice` (free-form cap, `nil` any, zero free only), `skillLevel`, `dateWindow` (`DateWindow`: whole days, inclusive; switching dates on proposes today plus `defaultFilterDateSpanDays`) and `openSpotsOnly`; `isActive` is simply "differs from the default". `EventListViewModel.filter` is `private(set)` and changed only through `updateFilter { }`, which logs each change; `visibleEvents` is what list and map render, judged against `userLocation` for distance, and while the position is unknown the distance criterion is skipped rather than hiding every game (the panel shows a note instead of the distance choice). `availableTypes` are the types in the loaded events plus any selected type a reload dropped, so a choice can always be undone; `isEverythingFilteredOut` swaps in a "Show all events" empty state whose action is `showEverything()` (`EventFilter.everything`, no criterion at all), because the default radius alone can hide every game and a reset would keep it. A list without a filter button (My Events) starts from `.everything` for the same reason (`AppDependencies.makeEventListViewModel`). `EventFilterButton` drops `EventFilterPanel` down as a popover, kept a popover on iPhone too via `presentationCompactAdaptation(.popover)`, so it reads as a dropdown: type chips in a `FlowLayout`, a segmented distance choice, a decimal `TextField` for the price cap with the market currency symbol (`Price.symbol(for:)`) beside a "Free only" chip that sets the cap to zero, a level picker, a dates toggle with two compact `DatePicker`s, and the open-spots toggle; Reset and Done sit in the header. Only Explore is `filterable`. Amounts are compared without conversion (`AppConfig.Events.marketCurrencyCode`), and filtering is on device over the loaded page until the backend takes the criteria as query parameters. `CapacityBar` fills with the occupied share (red, amber when nearly full, muted grey when full) over a faint track, and the label under it counts the same way ("6 of 10 joined"); the fixtures carry fixed participant counts so the feed shows an open, a nearly full and a full game.
- **Optional event details.** `SportEvent.description`, `lookingFor` (the host's own words for who is still needed), `skillLevel` (`SkillLevel`: beginner, intermediate, advanced; `nil` means any level, and such games match every level choice in the filter) and `price` (`Price`: amount plus ISO currency code; `nil` means free, and so does a zero amount) are all optional with `nil` defaults in the explicit initialiser, so existing call sites keep compiling and payloads written before a field existed keep decoding (tested). `SportEvent.priceText` is the one price formatter ("Free" or the localised amount); the detail screen adds price and level rows to the facts card only when set, shows the description under the title and "Looking for" in its own card, and paid games get a small glass price chip on `EventCard` and the price in the `EventPreviewCard` caption; free games stay uncluttered. Whole amounts drop their minor units ("€5"), other amounts keep the currency's usual form ("€7.50"), formatted in the user's locale (`Price.text(in:)` takes a locale for tests). Stacked fact rows use `.labelStyle(.iconColumn)` so glyphs of different widths share one text edge. Fixtures cover every detail present and absent.
- **Networking seam:** repositories depend on the `APIClient` protocol and describe a call as an `APIRequest` (method, path, query items, optional `Encodable` body, response type). `URLSessionAPIClient` builds the URL from `AppConfig.API.baseURL`, sends and decodes JSON with the shared conventions in `APIJSONCoding`, adds `X-Local-User-Id` in debug builds when a user is signed in, and turns non-2xx answers into `APIError.http(status:body:)` with the backend's `{code, message}`; transport failures stay `URLError`. `APIClient.send(_:failingWith:)` then maps known backend codes to their `AppError`, other `URLError`s to `.network` and anything else to the caller's fallback, while cancellation passes through untouched so a screen the user left never raises the popup. Request failures are logged with method, path and status (never bodies or headers).
- **Join and leave:** `EventDetailViewModel` owns the event on screen, runs one change at a time (`isBusy`), replaces the event with the server's answer and hands it to the list; failures go to `ErrorCenter`. A `TRY_AGAIN` is repeated once after `AppConfig.API.tryAgainDelay`; a refusal that means the event moved on (`eventFull`, `alreadyJoined`, `notAParticipant`, `hostCannotLeave`, a second `tryAgain`; logged at warning, since a full game is a product state and not a fault) refetches it through `EventRepository.event(id:)` so the detail and the lists show the server's state before the popup explains why. So does a failure that leaves the outcome unknown, a 500 (`participationFailed`) or a transport error (`network`): Laurel commits the join before it reads the event back, so the write may have landed although the answer was lost; when the refetched event already shows what the user asked for (in after a Join, out after a Leave) the popup is skipped and an info line says the write landed, otherwise it shows; the refetch tolerates its own failure. A join or leave that fills the last spot logs "Capacity reached for event <id>". `Participation` decides the control from the event and the caller: hidden for guests, `hosting` when `hostUserId` is the caller, `leave` when `isJoined`, `full` when no spots remain, otherwise `join`. The detail reads the caller through the same `IdentityProvider` the API client uses.
- **Sign-in flow:** the sheet mounts its own `.errorPopup`, because a sheet is drawn above the root where the shared popup lives (`ErrorCenter` tracks the mounts and only the topmost draws), and it dismisses when `session.state.user` appears, which also works for guests who are already inside the app. `SignInViewModel` and `EmailSignInViewModel` own their sign-in `Task` and cancel it when the sheet disappears; `SessionController` treats `CancellationError` as a quiet exit, holds one authentication slot for sign-in and sign-up alike, and `signOut()` clears local state before the remote call and ignores re-entry. `UserDefaultsSessionStore` logs cache hit, miss and invalidation and discards an unreadable blob with a warning.
- **Buttons are native iOS 26 controls.** `lilyProminentButton(sizing:)` (accent `.glassProminent`) and `lilyGlassButton(sizing:)` (plain `.glass`) in `Core/UI/Components/ButtonModifiers.swift` set the capsule shape, `.controlSize(.large)`, `.buttonSizing(.flexible)` (full width) or `.fitted` (hugging) and the button font; nothing puts a frame on a capsule button's label, so every capsule has the system's 50pt height and padding and grows with Dynamic Type. Text fields use `DesignTokens.Layout.fieldHeight` (50pt) to match the button under them, and text-only (`.borderless`) buttons get a 44pt tappable area through `tappableLabel()`. The `.glass` style colours its label from the tint, so ink labels (landing "Sign in", provider buttons) pass `labelColor: .lilyInk`; "Sign out" keeps the red on purpose. Provider buttons centre glyph and title like the system Sign in with Apple button, and the spinner takes the glyph's place while loading. The landing shows two stacked full-width capsules (prominent "Find a game near you", glass "Sign in") inside one `GlassEffectContainer`.
- **Typography:** SF Pro only, with tight tracking on the wordmark and headline (sizes and tracking in `DesignTokens.Typography`).
- **Aurora background** is a 4x4 `MeshGradient` in a 30 fps `TimelineView`, in the spirit of the Raycast home page: a near-black surface with soft luminous red glows and a whisper of grain. Two maroon masses, upper-left behind the headline and lower-right behind the button, are joined by a thin diagonal with a darker valley on either side (`AuroraPalette.roles`), drawn with bicubic smoothing so no cell edge shows. Corners are pinned, edge points slide along their edge, interior points wander on paths that sum three sines drawn from four incommensurate periods (19, 23, 29, 37 s) with golden-angle phase offsets. The red visibly flows because a brightness ripple travels down the main diagonal every 29 s and a weaker one crosses the other diagonal every 41 s (`AuroraGeometry.cellIntensities`), while the raspberry core, kept on the top edge so its peak never swallows the red headline line, breathes every 23 s. The whole background fades in from nothing over 3.5 s (ease-in-out) when a screen appears. Numbers live in `DesignTokens.Aurora`; the math lives in `Core/UI/Effects` (`AuroraGeometry`, `AuroraPalette`, `FilmGrain`) and is unit tested; `LilyTheme` maps roles to asset colors and the view only draws. Every screen adds live film grain: 12 seeded 128 px noise tiles with a squared distribution (sparse bright speckle, blacks stay black), generated once, drawn at 2 device pixels per noise pixel without interpolation and cycled at 24 fps, blended `plusLighter` at 8%. Content screens draw the mesh at `contentIntensity` (0.55), the landing at 0.85, the launch screen at full strength. Reduce Motion freezes the first frame (the fade-in stays, being a crossfade). The app is forced to dark mode via the `INFOPLIST_KEY_UIUserInterfaceStyle` build setting; colorsets keep their light variants for when the light theme returns. Phases are reduced modulo their period in `Double` before becoming `Float`: `timeIntervalSinceReferenceDate` cast to `Float` only resolves steps of several radians, and the old mesh stood still for a minute at a time.
- **Liquid Glass layering.** Two rules that iOS 26 enforces and that are easy to get wrong. A toolbar item already draws its own glass capsule, so the segmented list/map `Picker` sets `.sharedBackgroundVisibility(.hidden)` on its `ToolbarItem` to avoid a doubled background. The tab bar floats above content, so `EventsMapView` lets only the `Map` ignore the bottom safe area and keeps the selected-event card as a `ZStack` sibling inside the safe area; a UI test asserts the card stays above the tab bar.
- **Event types:** `EventType` (football, basketball, tennis, padel, running, volleyball, cycling, climbing, other) drives the amber `EventTypeChip` badge, the map pins and the filter chips; "Other" is for games the list does not name yet.
- **Provider glyphs:** Apple and Email are SF Symbols in the ink color (the envelope filled so it weighs the same as the Apple mark); Google uses its official multicolor "G" as a vector asset (`GoogleLogo`). The Apple button must meet Apple's Sign in with Apple guidelines (or use `SignInWithAppleButton`) once real auth lands.

## AWS deployment

Not yet. The plan: a Cognito user pool with Apple and Google identity providers (Amplify Swift wired into `AppDependencies.makeDefault()`), then the Laurel Spring backend (today only local, see [Backend](#backend)) on AWS ECS with DynamoDB behind it, validating Cognito JWTs and owning events and chat. Once that exists, `AppConfig.API.baseURL` points at it and the API client carries the Cognito token instead of the debug-only local identity header. See `CLAUDE.md` for the reasoning. `amplifyconfiguration.json` is git-ignored.
