# Lily

Meetup-style iOS app for sport events: sign in, create and join events, chat with participants.
iOS 26+, SwiftUI, Liquid Glass, dark-only design (for now) with a rust-leaning red accent over maroon. The backend, Laurel (`iris-dc/laurel`, a Spring Boot 4 service), runs on AWS on a tight budget: Cognito for identity, one small ECS Fargate task over DynamoDB for business logic and data; see AWS deployment below.

## Status

Early days. Auth is real: email + password against the Cognito user pool `lily-users` through Amplify Swift, configured in code (no JSON file in the bundle), with the verification code Cognito emails after sign-up entered in the app; Apple and Google stay on the sheet and answer "Coming soon" until the pool has identity providers. Events and profiles come from the Laurel backend when it runs locally (see [Backend](#backend)) or from in-memory mocks with `-mock-events`; `-mock-auth` swaps Cognito for a mock. The AWS side (Laurel on Fargate at `https://api.iskra.red`, DynamoDB, the Cognito user pool) is defined and deployed by the `iris-dc/rose` CDK repository; release builds point at it and send the Cognito access token as a Bearer (see [AWS deployment](#aws-deployment)).

- Landing screen that explains the product (headline, live preview of upcoming events) with one tap into the app. Sign-in (Apple / Google / Email) is optional and lives in a sheet; the email form signs in, signs up, and takes the 6-digit confirmation code Cognito emails (with "Resend code" and "Back to sign in").
- Tabbed shell (Explore, My Events, Groups in debug builds, Profile). Explore switches between a list (with distance from the user) and a map with one glass pin per event; selecting a pin shows a preview card that opens the event detail. A filter panel drops down from the Explore toolbar and narrows list and map by event type (multi-select, including "Other"), distance from the user's position (10 km by default), a maximum price you type in, skill level, a date range and open spots. An event may carry optional details: a description, who the host is looking for, a skill level and a per-person price; the detail screen shows whichever are set, and list cards and preview cards show the price of paid games. My Events asks a guest to sign in instead of requesting a user-scoped list.
- Event detail with join and leave for signed-in users: the button follows the caller's relation to the event (Join, Leave, "Event is full", "You host this game"; nothing for guests), the count and capacity bar update from the server's answer, and the list behind it reflects the change on the way back.
- Creating a game from Explore: a floating "+" over the list and the map opens a form sheet with a title, the event type, when, a place name and the spot on a map (it starts from your position), the number of players, and the optional description, "looking for", level and price per person. The draft is checked on the device against the same limits the backend enforces (text lengths counted in UTF-16 units, as the backend counts them, so an emoji counts two), so the Create button is enabled exactly when the backend would accept it; the new game appears in the Explore list when the active filter matches it, and always under My Events, which lists hosted games alongside joined ones, and its detail says "You host this game". When the answer to a create is lost, the app asks the backend whether the game exists before showing a failure, so a game that did land is never reported as missing. A guest tapping "+" gets the sign-in sheet instead.
- Groups (debug builds, behind `AppConfig.FeatureFlags.groups`): a Groups tab that opens on Mine for a user and on Discover for a guest, with Mine (a conversation list of your groups: initials, name with a lock or globe, "34 members · Football · Active today", an unread dot) and Discover (public groups as cards, a search field, an event-type dropdown, paging), a floating "+" that opens the create form (name, description, event type, public or private, what members may do), a "Join with code" sheet that formats the code as you type, and a group detail with the actions your role allows (Open chat, Invite, Create game, Join group, "Invite only", "Group is full"), Events and Members segments (role badges, a context menu with Make admin / Remove / Ban for admins, a Banned list with Unban), and a toolbar menu with Invite, Edit, Leave and Delete. Inviting creates a link and a code for the expiry and use limit you pick, with Share and Copy. An invite link (`https://api.iskra.red/invite/<code>`) or the `-open-invite <code>` launch argument opens the preview over whatever is on screen; a guest signs in first and is joined right after. A Mine row opens the group's chat: bubbles in the accent for your own messages and on the surface colour for everyone else's, grouped into runs with the sender's name and avatar on the first and the time under the last, day chips, a centred "Marta created Sunday 5-a-side" row that opens the game, a composer that grows to five lines with a counter near the limit, your message shown at once and marked "Not sent. Tap to retry." when it fails (Retry / Delete in its menu), long-press for Copy and Delete, older pages loading as you scroll up without the list jumping, an unread dot on the row and a badge on the tab until you open the room, and an info button that leads to the group. Games live in groups too: the event form has a Group row (a menu of the groups you may create games in, preset and read-only when the form opens from a group's "Create game"), a group's Events segment lists its upcoming games, cards on Explore and in that segment carry the group as a badge, preview cards show it under the caption, and the event detail says "Hosted in <group>" (a link to the group when it is public; "Members only" under it when it is private).

## Requirements

- Xcode 26.5 or newer (the deployment target is iOS 26.5; the project was last upgraded with Xcode 26.6), with an iOS 26.5 simulator runtime.
- No AWS credentials needed to run or test. Signing in for real needs a network and the `lily-users` pool (the ids are in `AppConfig.Cognito`); every test and preview runs on the mock.

## Run

Open `lily.xcodeproj`, select an iPhone simulator, run the `lily` scheme.

From the command line:

```sh
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer   # only if xcode-select points at the Command Line Tools
xcodebuild -scheme lily -destination 'platform=iOS Simulator,name=iPhone 17 Pro' -skipPackagePluginValidation build
```

`-skipPackagePluginValidation` is needed on the command line (and in `ci.sh`) because Amplify pulls in `smithy-swift`, whose build plug-in `xcodebuild` otherwise refuses to validate without an interactive approval; Xcode asks once in the IDE.

## Test

```sh

./scripts/ci.sh ui       # UI smoke tests (lilyUITests)
```

## CI

GitHub Actions (`.github/workflows/ci.yml`) runs on every push and pull request to `main` on a `macos-26` runner: it selects the newest Xcode 26, installs SwiftLint with Homebrew (the runner image does not ship it), then runs `scripts/ci.sh all` as one step (lint, one build for testing, then unit and UI tests without rebuilding) and uploads the result bundles as an artifact. The runner needs Xcode 26.5 or newer, the same minimum as [Requirements](#requirements).

To run on the mock auth service, launch with `-mock-auth`; add `-mock-auth-fail` to make every auth call fail and see the error popup, or `-mock-auth-confirm` to walk the confirmation step with the code `123456` (previews can use `AppDependencies.makeMock(authBehavior: .fail(.network))` or `.requireConfirmation(code:)`). Without any of them the app talks to the real pool.

## Backend

Events and profiles come from **Laurel**, the Spring Boot backend (its own repository), which the app reaches at `AppConfig.API.baseURL`. The base URL follows the build configuration: **debug** builds use `AppConfig.API.localBaseURL`, `http://localhost:8080`, and **release** builds `AppConfig.API.productionBaseURL`, `https://api.iskra.red` (Laurel on AWS, deployed by `iris-dc/rose`; see [AWS deployment](#aws-deployment)).

**Simulator.** The simulator shares the Mac's loopback interface, so a Laurel started locally with its `local` profile (DynamoDB Local, auth bypass, seeded with the same nine fixture events the mocks produce) is all that is needed: start it, run the app, and Explore shows the seeded events. Participation is not seeded: against the backend every game shows Join and My Events starts empty, while the mocks pre-join every fourth fixture so the tab has content. Plain HTTP to `localhost` needs no App Transport Security exception, because ATS exempts unqualified host names.

**Physical iPhone.** A device on the same Wi-Fi reaches the Mac by its Bonjour name. Add the launch argument `-api-base-url http://<mac-name>.local:8080` to the `lily` scheme (Product → Scheme → Edit Scheme → Run → Arguments; the Mac's name is under System Settings → General → Sharing, "Local hostname"). `-api-base-url` is the only launch argument that takes a value, the next argument; `AppConfig.LaunchArguments.value(following:in:)` reads it and `AppDependencies.apiBaseURL(from:logger:)` accepts it when it parses as a URL with a scheme and a host (logged at info as `API base URL overridden: <url>`; anything else is logged at warning and ignored). Like every launch argument it is honoured in debug builds only. Laurel binds all interfaces, so nothing changes on its side; macOS may ask once whether to allow incoming connections for Java. iOS shows the Local Network permission prompt on the first request (the usage text is the `INFOPLIST_KEY_NSLocalNetworkUsageDescription` build setting of the Debug configuration only: a release build ignores the argument and never reaches a `.local` host), and that first request may fail before you tap Allow: pull to refresh.

**Release.** `https://api.iskra.red` takes the Cognito access token the app sends as `Authorization: Bearer <token>`; anonymous reads (`GET /api/events?scope=upcoming`, `GET /api/events/{id}`) work without one, so guests browse, and everything else answers 401 without a valid token, which the app shows as "Session expired".

Without a backend, launch with `-mock-events`: `MockEventRepository` serves the fixtures and joins, leaves and creates in memory (a created game is hosted by the signed-in mock user under the host name "You", with the draft's client id as its id), and `MockProfileRepository` accepts every display name. Previews use the same mocks through `AppDependencies.makeMock()`, and the UI tests pass the argument so they never depend on a running server. Without either, every list load and join reports "You're offline" through the popup, and the lists show the refreshable "Couldn't load events" state (the landing preview fails silently, logged at warning, and just shows no events).

**Identity.** The user id is the Cognito `sub`. The app authenticates with the Cognito **access token** (`Authorization: Bearer <token>`, `AppConfig.API.Headers`), read per request from an `AuthTokenProvider` (`CognitoAuthService` over Amplify, which refreshes tokens itself); a guest has none and sends no `Authorization` header. A 401 from the backend maps to `AppError.sessionExpired` and a 429 (Laurel's rate limit, code `RATE_LIMITED`) to `AppError.rateLimited`, whatever was asked and before the code lookup (`APIError.appError(fallback:)`); the popup then reads "Slow down a moment". Locally, Laurel's `local` profile still bypasses auth for requests **without** a Bearer header and trusts the `X-Local-User-Id` header a **debug build** adds for the signed-in user (`AppConfig.API.sendsLocalUserHeader`, `true` only under `#if DEBUG`); a debug build signed in through Cognito sends a real token too, which the local Laurel validates for real, so start it with the pool and client ids (`COGNITO_USER_POOL_ID=eu-central-1_JmfE31ODT COGNITO_APP_CLIENT_ID=54dul3essertek166u2st78s4a`); it ignores the local header when a Bearer token is present. A guest against the local backend runs as its `local-dev` user, which the backend treats like any other user; it is the app that hides Join and Leave for guests (`Participation.hidden`), so a header-less `curl` can join as `local-dev`. The header value comes from an `IdentityProvider` (`SessionIdentityProvider` reads `SessionController.state.user?.id`), so the client never depends on the session controller. Right after a successful sign-in the app `PUT`s the user's display name to the profile endpoint, fire and forget, so the backend can stamp the host's name onto events; a failure is logged, never shown.

**Contract, in words.** JSON, UTF-8, ISO-8601 instants in UTC (`2026-09-13T17:00:00Z`; the app also reads fractional seconds and always writes without). Every request carries `X-App-Version: <CFBundleShortVersionString> (<CFBundleVersion>)`, e.g. `1.0 (42)` (`AppConfig.API.Headers.appVersion`; the value is an `AppVersion` read once from `Bundle.main` and injected into `URLSessionAPIClient`, so tests pin it), so the backend can tell app versions apart in its logs and statistics. `GET /api/events?scope=upcoming|joined` lists events: `joined` returns the caller's upcoming events, hosted ones included, uncapped and ascending by start (past games are not listed); `upcoming` is capped at 100 (Laurel's `events.upcoming-limit`) and **ordered by relevance for the caller, not by start**. Explore sends the user's position with that request as `lat` and `lon` when it is known (`EventRepository.events(in:near:)`; `Coordinate.rounded(toDecimals:)` at `AppConfig.Events.positionPrecision`, two decimals, about a kilometre, printed with fixed decimals and a `.` whatever the locale; never sent with `joined`), and the backend weighs distance, the event types the caller views and joins, the hosts they join, their own participation and the start time; a guest with a position gets distance and time, without one the plain start order, and the app tolerates any order (a game created from Explore goes to the top of that list, by start time on My Events). `POST /api/events/{id}/participants` joins and `DELETE` on the same path leaves; both return the updated event. `POST /api/events` creates a game and answers `201` with the event, the caller as host and first participant; the body (`CreateEventPayload`) carries `clientEventId`, `title`, `type`, `startsAt`, `location {name, coordinate}`, `capacity` and the optional `description`, `lookingFor`, `skillLevel` and `price`, left out when blank or free. `clientEventId` is a UUID the app chooses once per draft (`EventDraft.clientId`) and sends with every attempt; the backend uses it as the event id (lower-cased), so a create repeated after a lost answer or a `TRY_AGAIN` gets the same game back instead of making a second one, and `409 EVENT_ID_TAKEN` means another user's game already has that id. `EVENT_ID_REUSED` (409, the same id retried with a different body) is handled the same way: the app knows neither code, maps both to `.eventCreationFailed`, and its refetch of the id then finds the game that did land. The form's limits (`AppConfig.Events.Creation`: 80 UTF-16 units of title, 120 of place name, 1000 of description, 300 of "looking for", counted with `utf16.count` because Bean Validation's `@Size` counts Java's `String.length()`, so an emoji is two; 2 to 200 players; a price with at most seven integer digits and two decimals) mirror the backend's constraints, so a draft that passes on the device never earns a `400 VALIDATION_FAILED`; the app additionally requires a start at least 15 minutes ahead, where the backend only requires the future. `PUT /api/profile` with `{"displayName"}` returns the profile. An event carries `id`, `title`, `type` (`EventType`, including `other`), `startsAt`, `location {name, coordinate {latitude, longitude}}`, `capacity`, `participantCount`, `hostUserId`, `hostName`, `isJoined` (whether the caller participates) and the optional details `description`, `lookingFor`, `skillLevel` (`beginner|intermediate|advanced`) and `price {amount, currencyCode}` (a JSON number, absent means free); optional fields are absent, never `null`, and `SportEvent` decodes the shape directly, key for key. Failures carry `{"code", "message"}`: `EVENT_NOT_FOUND` (404), `EVENT_FULL`, `ALREADY_JOINED`, `NOT_A_PARTICIPANT`, `HOST_CANNOT_LEAVE`, `TRY_AGAIN` (409; the last means the write lost a race with another player or was throttled by DynamoDB and is safe to repeat) `VALIDATION_FAILED` (400) and `RATE_LIMITED` (429, with a `Retry-After` header; the app maps it to `.rateLimited`, "Slow down a moment", by the code and by the status alone when the body is missing, the way a 401 becomes `.sessionExpired`, whatever was asked); the first six map to their own `AppError` cases and copy, anything else (including `EVENT_ID_TAKEN`) becomes `.eventsUnavailable` on a read, `.participationFailed` on a join or leave and `.eventCreationFailed` ("Couldn't create your game") on a create, and a transport failure becomes `.network`. `GET /api/events/{id}` returns one event: the detail screen fetches it after any of the 409s, and after a 500 or a transport failure on a join or leave (the write may have committed before the answer was lost), so the count on screen and in the lists behind it is the server's before the popup explains the refusal; a `TRY_AGAIN` is first repeated once after `AppConfig.API.tryAgainDelay`.

**Usage statistics.** The taps the backend cannot see for itself are reported by a signed-in user to `POST /api/interactions` (`Core/Statistics`): `event_viewed` (event id, type and host id) when a detail opens, `filter_applied` when the filter panel closes on a changed filter or "Show all events" is tapped, and `presentation_changed` (`list` or `map`). The body is `{"interactions": [{"kind", "occurredAt", ...}]}` with at most `AppConfig.Statistics.batchSize` entries, answered `202 {"accepted": n}`. A `filter_applied` carries the **shape** of the filter (`FilterSummary`: the selected type names, the radius in metres, and whether a price cap, a level, a date range or "open spots only" is set), never the amount, the dates or any text; no interaction carries a coordinate, by construction of `Interaction`. `RemoteInteractionRecorder` buffers them per user and posts when `batchSize` (10) have gathered, `flushDelay` (30 s) after the first one, or when the app goes to the background (`AppRootView`); the buffer is capped at `maxBuffered` (100, oldest dropped) and a failed post is a warning under the `.statistics` log category, never a popup or a retry. **Guests send nothing, ever**: an interaction recorded without a signed-in user is dropped on the spot, and entries recorded for a user who signed out before the flush are dropped then. Mock runs (`-mock-events`, previews, UI tests) use `NoOpInteractionRecorder`. The backend records joins, leaves, creates and list views itself, keeps per-user aggregates and a Firehose stream to S3 (see the `iris-dc/rose` and `iris-dc/laurel` READMEs); only the Cognito `sub` identifies a user there.

## Groups

Groups are communities around a sport (or "Any type"): a chat room, a member list and the games hosted in the group. The feature ships in debug builds only until it is finished, behind `AppConfig.FeatureFlags.groups` (`Config/AppConfig+FeatureFlags.swift`; `FeatureFlags.chat` gates the chat screens, and with `groups` on and `chat` off a group row opens the group instead of its chat). A release build has three tabs.

- **Visibility.** A group is `public` (anyone finds it on Discover and joins with one tap) or `private` (reachable only through an invite; a non-member gets "group not found", never its existence). Visibility is chosen at creation and never changes.
- **Roles.** The creator is the `owner` (exactly one; cannot leave, may delete the group and change roles), `admin`s edit the group, invite, create games, remove and ban members, and `member`s chat and join games. Per group, two switches say what members may do beyond that: "Create games" (`membersCanCreateEvents`) and "Invite people" (`membersCanInvite`), both on by default. A ban is a marker row, not a membership: a banned user cannot rejoin or redeem an invite until an admin unbans them. `GroupAccess` (`Features/Groups/Models`) turns a group and the caller's id into what the screen may offer, the way `Participation` does for events.
- **Invite codes and links.** An invite is a 12-symbol Crockford base32 code (no `I`, `L`, `O`, `U`; typed `I`/`L` become `1` and `O` becomes `0`, so a code read aloud still works), shown in groups of four, valid for 1, 7 or 30 days, for anyone with the link, one person or up to ten. The code is a capability: the app only ever sends it in a request body (`POST /api/invites/preview`, `POST /api/invites/redeem`) and never logs it. It travels as the universal link `https://api.iskra.red/invite/<code>` (`AppConfig.Groups.inviteLinkBaseURL`), which `DeepLinkCenter` parses when the app is opened with it, or as the plain code typed into "Join with code" on the Groups tab. Either way the same preview shows (group name, type, visibility, members, expiry) with a Join button, or, for a code the backend refuses as invalid or expired, the reason in place of the preview (no popup, no retry); a guest signs in first and is joined right after, and the join opens the group's chat. The mock repositories accept one code, `AppConfig.Groups.mockInviteCode` (`KRZB7K3MQX9P`), which previews and admits into "Climbing Buddies"; the `-open-invite <code>` launch argument stands in for a tapped link on the simulator.
- **Games in groups.** A game may be hosted in a group: the event form's Group row offers the groups the caller may create games in (`MyGroupsStore.eligibleForEvents`) and is preset, read-only, when the form opens from a group's "Create game". A public group's games are on Explore like any other, with the group's name as a badge on the card and "Hosted in <group>" on the detail, which links to the group. A private group's games never reach Explore; their detail is served to members and participants only and says "Members only" under the group's name. Every group's upcoming games are listed under the Events segment of its detail.
- **Launch arguments.** `-open-invite <code>` (above) and `-mock-user-id <sub>`, which makes every mock sign-in yield that user so two simulators can act as two people (only together with `-mock-auth`; a Cognito user is whoever the pool says). `-mock-chat-replies` makes a fixture member answer every message sent in a mock room after 1.5 s (never passed by the UI tests); `-realtime-endpoint <url>` names the realtime API for a debug build against a deployed backend (otherwise `GET /api/me` names it, and a local Laurel gets none: chat catches up over REST on appear, after a send, on foreground and on pull to refresh). All are ignored by release builds like every other argument.
- **Chat.** One chat room per group, visible to members (`ChatView`, pushed from a Mine row, a group's "Open chat", or a redeemed invite; the tab bar hides while it is open). Messages are REST writes: `POST /api/groups/{id}/messages` with a `clientMessageId` chosen once per composed message and kept through every retry, so the backend replays a repeat instead of storing a duplicate, and the bubble keeps its identity when the stored message replaces the optimistic one. A message is text only (`Text(verbatim:)`, no link detection, so a pasted URL never opens on tap), at most 2 000 UTF-16 units, drawn as a plain fill (accent + white for the caller, surface + ink for others; glass is kept for the composer and the day chips because a room scrolls dozens of bubbles at once). One sender's messages within five minutes and on the same day form a run; the timeline (`ChatTimeline`, pure) inserts day chips, shows the sender's *current* name from the roster, hides blocked senders and turns deleted messages into an italic "Message deleted". Deleting is for the sender and the group's admins. A system row (`event_created`) names the game once it is fetched and opens it. The read marker is sent when the room opens, at most once a minute while it is open, and when it closes or the app goes to the background; `UnreadCenter` (fed by the Mine load, live messages and the open room) drives the row dot and the tab badge. A 429 closes the composer for the `Retry-After` seconds with "Slow down a moment" under it. Report and Block appear in a message's menu but are disabled until moderation ships. The unsent outbox is in memory: a message that failed to send is lost when the app is killed.

## Realtime

The realtime API (AWS AppSync Events; the client lands in a later milestone, `Repositories.remote` wires `NoRealtimeTransport` until then) only pushes what the backend has committed, on `rooms/<groupId>/<channelEpoch>` and `users/<sub>`. Every leave, removal and ban bumps a room's `channelEpoch`, which renames its channel, so someone who left stops receiving without the server having to track sockets. `RealtimeSessionController` (`Core/Realtime`) holds the one connection while the app is active with a signed-in user, driven by `AppRootView` from `scenePhase` and the session (`setDesired(active:user:)`): `users/<sub>` plus the open room and the ten most recently active groups of Mine, closed in the background and on sign-out (it is a `SessionObserver`, like every per-user store), renewed with a force-refreshed token (`AuthTokenProvider.freshAccessToken()`, used for nothing else) five minutes before the token expires; a refresh that yields the same token falls into a backoff instead of looping.

- **Resume protocol.** Every open (launch, foreground, reconnect) subscribes first, reloads Mine once, then catches up over REST only the open room and the cached rooms whose newest message moved, three at a time. A naive foreground would fetch every room; this stays under five requests.
- **Two cursors per room.** `ChatRoomState` keeps what is shown and the REST watermark, which only `newest`/`newer` pages move, so the next catch-up always starts where REST left off; a lost publish is a delay, never a hole. The room cache (`InMemoryChatHistoryCache`, 300 newest rows per room) is the one owner of room state: the controller's live inserts and catch-ups land where the open chat reads.
- **Epochs.** A `member_left` carrying a newer epoch is trusted and resubscribed with a small jitter (no group read), and any answer carrying a newer epoch (a page, a send, a read marker, a group) makes the room resubscribe and catch up.
- **Endpoint discovery.** `GET /api/me` names the realtime endpoint; `-realtime-endpoint <url>` overrides it for a debug build against a deployed backend, and the release constant is the fallback. Against a local Laurel none is known, so the connection stays off and chat catches up over REST only: on appear, after a send and on foreground.
- **Mock transport.** `-mock-events` wires `MockRealtimeTransport`, an in-memory bus: the mock chat echoes every send to the room's channel after 200 ms, and `-mock-chat-replies` makes Marta answer after 1.5 s and deepens every room to 300 rows.

## Architecture notes

- **Session state machine.** `SessionController` owns `SessionState` (`loading`, `signedOut`, `guest`, `signedIn`). Views only read it; all transitions are methods on the controller.
- **Auth is Cognito through Amplify, behind two seams.** `AuthService` (`restoreSession`, `signIn(with:)`, `signUp`, `confirmSignUp`, `resendConfirmationCode`, `signOut`) is what the app calls; `CognitoAuthService` implements it, and `AuthTokenProvider`, over a `CognitoClient`, the thin mockable surface the service needs (`isSignedIn`, `accessToken`, `currentUser`, `fetchEmail`, `signIn`, `signUp`, `confirmSignUp`, `resendCode`, `signOut`, failing with `CognitoClientError`). `AmplifyCognitoClient` is the one file that imports Amplify: it maps `AuthError`/`AWSCognitoAuthError` to `CognitoClientError`, reads the access token from `fetchAuthSession()` (Amplify refreshes it), and configures Amplify once, on its first call, from `AmplifyConfigurationBuilder` (the legacy `awsCognitoAuthPlugin` JSON built from `AppConfig.Cognito`, stating `USER_SRP_AUTH` explicitly) instead of an `amplifyconfiguration.json` in the bundle. Configuring on first use rather than at construction keeps Amplify out of the unit tests, which build the default composition root. `CognitoAuthService` maps the client errors to `AppError` (wrong or unknown credentials to `invalidCredentials`, since the pool hides user existence; `emailNotConfirmed`, `emailTaken`, `invalidConfirmationCode`, `tooManyAttempts`, `sessionExpired`), makes the `AuthUser` from `sub` and the email attribute (`AuthUser.displayName(fromEmail:)`), and answers Apple and Google with `providerUnavailable` ("Coming soon") until the pool has identity providers.
- **SessionStore is a hint, not truth.** It stores the guest choice and the signed-in user as last seen, so a relaunch shows the profile without a round trip; `CognitoAuthService` only trusts a cached `.signedIn` while Amplify still has a session and drops it otherwise. Tokens never live there: Amplify keeps them in the keychain. The mock stores its fake session in the same place.
- **Branding lives in `Config/AppBranding.swift`:** app name, landing headline and copy, tab titles, empty states, sign-in and profile copy, button titles. `AppBranding.Events` holds the capacity copy ("Full", "N spots left" on compact cards, "N of M joined" under the capacity bar) and `SportEvent.availabilityText` / `capacityText` are the only formatters, so the landing preview card and the capacity bar cannot disagree. Change copy there and every screen follows; UI tests match on the same literals.
- **Colors** are asset catalog colorsets with light and dark variants, exposed via generated symbols (`Color.lilyAccent`, `Color.lilySecondary`, `Color.lilySurface`, ...). Rust-leaning red `#B72734` is the accent, maroon `#5E0C26` the deep tone behind it, and the aurora core keeps the original raspberry `#B31B3F` in its own colorset (`LilyAuroraCore`) so the accent can be retuned without moving the background; amber (`lilySecondary`) is used sparingly for event-type chips, the hero badge and the "nearly full" capacity state.
- **Location:** `LocationService` returns one fix or `nil`; the app never blocks on it. `CoreLocationService` reads a `LocationUpdateSource` (`CoreLocationUpdateSource` wraps `CLLocationUpdate.liveUpdates`, which prompts for when-in-use permission; the usage text is an `INFOPLIST_KEY_` build setting) and races the first fix against `AppConfig.Location.fixTimeout` in a task group, so cancelling its caller closes the stream. The seam lets the timeout, denied and first-fix paths be unit tested with a scripted fake. `CachedLocationService` wraps it in production: concurrent callers share one upstream request (which deliberately outlives any single caller's cancellation, bounded by `fixTimeout`, so the fix it obtains is cached for the next screen), a fix is reused for `fixTTL` (300 s) and a missing fix for `failedFixTTL` (30 s), so sibling tabs never open two CoreLocation streams. When the app returns to the foreground (the one moment permission may have changed in Settings) the events screens call `retryUserLocationIfMissing()`, which asks the cache to `forgetMissingFix()` and requests again, so the distance filter becomes available without a relaunch. `Coordinate` stays Foundation-only; the CoreLocation bridge lives in `Coordinate+CoreLocation.swift`. Distance is computed on-device with a haversine, no network.
- **Events list caching:** `EventListViewModel.loadIfStale()` (used by `.task`) reuses events loaded within `AppConfig.Events.listStaleAfter` (60 s) when a tab reappears; pull-to-refresh calls `load()` and always reloads; a cancelled load is logged, not reported; a failed load shows a refreshable "Couldn't load events" state instead of the empty state, and `loadIfStale()` does not retry it for `AppConfig.Events.retryAfterFailure` (10 s), so switching tabs while the backend is down does not hammer it; a change made elsewhere or a change of caller ends that wait early, because it proves the backend is up and the answer different. A join or leave on the detail screen comes back through `replace(_:)`, which updates the list in place (and drops the event from a joined-only list when the user left), and bumps the shared `ChangeTracker` (`AppDependencies.eventChanges`); every other list compares the version it loaded against it and reloads on its next appearance, so My Events shows a join made from Explore without waiting out the 60 s. A list also remembers the user it loaded for and reloads after a sign-in or sign-out, because `isJoined` is the server's answer for that caller. Explore sends the user's position with the request when it is known (`EventRepository.events(in:near:)`, so the backend can order by distance); content loaded without one while a position is known now counts as stale, and a position that arrives while the request is out earns one reload from `load()` itself, so the backend's relevance order replaces the first answer's time order without waiting for the next appearance (My Events never sends a position and never reloads for one). Every one of these decisions is logged under `.cache`: the reason for a reload (never loaded, changed elsewhere, caller changed, position became known, retry after failure, older than TTL), a skipped reload (fresh, or waiting to retry) and the invalidation of sibling lists in `replace(_:)`. A failed load reports the mapped error ("You're offline", "Events unavailable"), never a blanket one. The rules themselves (TTL, version, caller, cooldown) live in `ContentFreshness` (`Core/Changes`), a value both `EventListViewModel` and `MyGroupsStore` hold; only the position reason is Explore's own. This view-model-level check is interim until the cached `EventRepository` ships.
- **Groups data layer.** `Features/Groups` follows the events layout. `SportGroup` decodes the backend's `Group` directly (named like `SportEvent` because `Group` is a SwiftUI view); `membership` is absent for non-members and banned users, so `role`/`isMember` never read a banned marker as a membership. `GroupAccess(group:userID:)` is the `Participation` analogue (`guest`, `canJoin`, `inviteOnly`, `member(role)`, `full`) with the permission helpers every screen switches on; the server stays the authority. `GroupDraft` validates name (3..60) and description (<= 500) in UTF-16 units against `AppConfig.Groups`, keeps a lower-case UUID `clientId` that the backend uses as the group id (a repeated create answers the same group), and `makeGroup(ownerName:now:)` is the one place a draft becomes a stored group (mock and test fake). Invite codes are `InviteCode` values: normalised (`-` and spaces dropped, upper-cased, `I`/`L` read as `1`, `O` as `0`) and validated against `AppConfig.Groups.inviteCodePattern`; they travel only in request bodies (`InviteCodePayload` on `POST /api/invites/preview` and `/redeem`), never in a path the client logs. `RemoteGroupRepository` needs the `IdentityProvider` because leaving is `DELETE .../members/<own id>`. Failures map through the shared `BackendErrorCode` table (every code of the backend's error list has a case; `GROUP_ID_TAKEN`/`GROUP_ID_REUSED` become `groupCreationFailed` so the create flow can refetch by client id); the fallbacks are `groupsUnavailable` for reads, `groupActionFailed` for writes, `groupCreationFailed` for creates, `inviteInvalid` for previews, `reportFailed` for reports. `MyGroupsStore` (app-lifetime, on `AppDependencies.myGroups`) is the one source of the caller's groups (`reload()`, `loadIfStale()` with the events staleness rules over `AppConfig.Groups.listStaleAfter`/`retryAfterFailure` and `AppDependencies.groupChanges`, `add`/`replace`/`remove`, `eligibleForEvents`); `MeStore` (`AppDependencies.me`) holds `GET /api/me` (`Account`: operator flag, terms owed, realtime endpoint) and accepts the terms; both are `SessionObserver`s cleared on sign-out. Mocks: six fixture groups (Kreuzberg Kickers as member with an unread room, Tempelhof Runners as admin, Sunday Padel Crew as owner, Berlin Basketball to join, Spree Volley full, Climbing Buddies private and reachable only through `AppConfig.Groups.mockInviteCode` = `KRZB7K3MQX9P`), rosters of a few named members plus the caller as "You", `MockMeRepository` making the Apple tester an operator, `MockModerationRepository` keeping blocks in memory. `-mock-events` swaps all four repositories along with the events ones.
- **Groups screens.** Every `NavigationStack` root (Explore, My Events, the guest My Events, Groups) applies `.groupDestinations(dependencies:)`, which registers `SportGroup` -> `GroupDetailView(.standalone)`, `GroupInfoDestination` -> the detail reached from a chat (`.fromChat`, "Open chat" hidden), `EventGroupRef` -> `GroupLoaderView` (fetch, then the detail; "This group is no longer available" on a 404, a retry on anything else) and `ChatDestination` -> `ChatView`, so an event's "Hosted in" link works on every tab; the Groups root alone also registers `SportEvent` (one declaration per stack). `GroupsRootView` owns one `GroupListViewModel` per scope, a toolbar segmented picker (Mine | Discover, `.sharedBackgroundVisibility(.hidden)`), `.searchable` on Discover only (the search bar is applied conditionally, so Mine has none), the type dropdown (`GroupTypeFilterButton` + `GroupTypeFilterPanel`, a popover like the Explore filter), "Join with code" and the floating "+"; `GroupsContent(for:)` decides whether Mine shows the list or the sign-in prompt, and Discover works for guests. A Mine row calls `AppNavigation.open(chat:)`; a Discover card is a `NavigationLink(value: group)` whose detail hands changes back through `GroupListViewModel.replace`. `GroupDetailView` rebuilds its `MembersViewModel` when the caller's role changes and takes roster and edit changes through `GroupDetailViewModel.accept(_:)`; `isGone` pops the screen. `InvitePreviewContent` is shared by the root invite sheet and the "Join with code" sheet: a guest's Join presents sign-in and the join runs once a user exists. `DeepLinkCenter` (`AppDependencies.deepLinks`) accepts only `AppConfig.Groups.inviteLinkBaseURL/<code>` (`parse`), seeds itself from `-open-invite`, and never logs the URL or the code; `AppRootView` mounts the preview sheet over the root, waits while the session restores, and enters the app as a guest first when the link arrives on the landing. `AppRootView` also loads `MeStore` and `MyGroupsStore` when a user signs in and when the app becomes active. `AvatarCircle` draws initials (or a glyph) in tinted glass at `avatarSmall`/`avatarMedium`/`avatarSize`; `String.initials` is the one initials rule (Profile and rosters share it).
- **Groups view models.** One view model per screen under `Features/Groups/ViewModels`, built by the factories in `AppDependencies+Groups.swift`. `GroupListViewModel(scope:)` is a projection over `MyGroupsStore` for Mine and pages Discover itself (`+Discover`: `query` debounced by `AppConfig.Groups.searchDebounce` over an injected `Sleep`, `typeFilter` applied at once, `loadMore()` by cursor, a newer search drops an older answer, guests allowed; it records `group_search_performed` with `hasQuery` and `resultCount` only). `GroupDetailViewModel` follows the events detail: join/leave/delete with one `TRY_AGAIN` repeat (`LostRace.attemptTwice`, which the events detail uses too), refusals refetch the group and then show the popup, a `.network`/`.groupActionFailed` refetch that already shows the intent skips it (and `NOT_A_MEMBER` on a leave counts as done); a redeemed or joined group goes into Mine through `MyGroupsStore.add`, a leave through `replace`, a delete through `remove`; `isGone` tells the screen the caller can no longer see the group; `showsOpenChat` is false from the chat (`GroupDetailContext.fromChat`) and while `FeatureFlags.chat` is off. `CreateGroupViewModel` refetches by `draft.clientId` after an unknown outcome and accepts the group when `role == .owner`. `MembersViewModel.actions(for:)` decides the row menu from `GroupAccess` and never offers the caller's own row; admins also load the banned list. `InviteViewModel` creates one invite per set of options (changing an option drops it), copies the grouped code through the `Pasteboard` seam and records `invite_shared` (group id only). `JoinWithCodeViewModel` formats the field as typed (`InviteCode.normalize` + `grouped`, capped at twelve symbols) and hands a complete code to an `InvitePreviewViewModel`, which previews, asks guests to sign in (`needsSignIn`; the sheet calls `join()` again afterwards), redeems, adds to Mine and opens the chat through `AppNavigation.open(chat:)`. Every failure goes through `GroupErrorReporter`: the shared popup plus `MeStore.noteTermsRequired()` on `.termsRequired`. Log lines under `.groups` carry ids only, never names, codes or query text.
- **Chat screens.** `ChatView` (`Features/Chat/Views`) is `ContentScreen { ChatTranscript ... .safeAreaInset(edge: .bottom) { MessageComposer } }` with the group's name as its inline title, the member count as the subtitle, the tab bar hidden and an info button that pushes `GroupInfoDestination` (the `.fromChat` detail, whose "Open chat" is hidden so the path never cycles). `ChatTranscript` is a `ScrollView` + `LazyVStack` over `viewModel.rows` anchored to the bottom (`defaultScrollAnchor(.bottom)`, `scrollPosition`): `TranscriptScrollPolicy` (`Features/Chat/Models`, pure and unit-tested) decides from each geometry report: pin the newest row above the composer once the first page has laid out (the default bottom anchor ignores the composer's safe-area inset), ask for the page before only when the reader has scrolled within `Layout.olderPageTriggerDistance` of the top after that first settle, and keep what was on screen where it was after the prepend by adding the new height to the offset; the caller's own messages always scroll into view, others' only while the list is already at the bottom (`onScrollGeometryChange` decides, within `Layout.atBottomThreshold`); a change of the bottom inset (keyboard, a growing composer) puts a list that was at the bottom back there, because the scroll view otherwise leaves the offset past the end. `MessageBubble` and `PendingMessageBubble` are plain fills (`Radius.bubble`, `Layout.bubbleMaxWidthFraction` of the list), never glass; `DaySeparator` is a `lilyChip(.regular)`; `MessageComposer` uses `lilyMultilineField()` (glass in a rounded rectangle at the field's minimum height, since a five-line capsule reads as a blob) and `lilyIconButton()` (a prominent glass circle) inside a `GlassEffectContainer`, and re-evaluates its cooldown caption once a second. A bubble's identifier is `message-client-<clientMessageId>` when the message has one and `message-<id>` otherwise. The Groups tab carries `.badge(unreadCenter.count)`, a Mine row its `UnreadDot`; `AppRootView` drives `RealtimeSessionController.setDesired(active:user:)` from `scenePhase` and the session, and sign-out closes the connection through `SessionObserver`.
- **Filter panel and capacity bar.** `EventFilter` holds every criterion: `types` (a set of `EventType`, which now includes `other`), `maxDistanceMeters` (defaults to `AppConfig.Events.defaultFilterRadiusMeters`, 10 km, so the default filter already limits distance and still counts as inactive; `nil` is "anywhere"), `maxPrice` (free-form cap, `nil` any, zero free only), `skillLevel`, `dateWindow` (`DateWindow`: whole days, inclusive; switching dates on proposes today plus `defaultFilterDateSpanDays`) and `openSpotsOnly`; `isActive` is simply "differs from the default". `EventListViewModel.filter` is `private(set)` and changed only through `updateFilter { }`, which logs each change; `visibleEvents` is what list and map render, judged against `userLocation` for distance, and while the position is unknown the distance criterion is skipped rather than hiding every game (the panel shows a note instead of the distance choice). `availableTypes` are the types in the loaded events plus any selected type a reload dropped, so a choice can always be undone; `isEverythingFilteredOut` swaps in a "Show all events" empty state whose action is `showEverything()` (`EventFilter.everything`, no criterion at all), because the default radius alone can hide every game and a reset would keep it. A list without a filter button (My Events) starts from `.everything` for the same reason (`AppDependencies.makeEventListViewModel`). `EventFilterButton` drops `EventFilterPanel` down as a popover, kept a popover on iPhone too via `presentationCompactAdaptation(.popover)`, so it reads as a dropdown: type chips in a `FlowLayout`, a segmented distance choice, a decimal `TextField` for the price cap with the market currency symbol (`Price.symbol(for:)`) beside a "Free only" chip that sets the cap to zero, a level picker, a dates toggle with two compact `DatePicker`s, and the open-spots toggle; Reset and Done sit in the header. Only Explore is `filterable`. Amounts are compared without conversion (`AppConfig.Events.marketCurrencyCode`), and filtering is on device over the loaded page until the backend takes the criteria as query parameters. `CapacityBar` fills with the occupied share (red, amber when nearly full, muted grey when full) over a faint track, and the label under it counts the same way ("6 of 10 joined"); the fixtures carry fixed participant counts so the feed shows an open, a nearly full and a full game.
- **Optional event details.** `SportEvent.description`, `lookingFor` (the host's own words for who is still needed), `skillLevel` (`SkillLevel`: beginner, intermediate, advanced; `nil` means any level, and such games match every level choice in the filter) and `price` (`Price`: amount plus ISO currency code; `nil` means free, and so does a zero amount) are all optional with `nil` defaults in the explicit initialiser, so existing call sites keep compiling and payloads written before a field existed keep decoding (tested). `SportEvent.priceText` is the one price formatter ("Free" or the localised amount); the detail screen adds price and level rows to the facts card only when set, shows the description under the title and "Looking for" in its own card, and paid games get a small glass price chip on `EventCard` and the price in the `EventPreviewCard` caption; free games stay uncluttered. Whole amounts drop their minor units ("€5"), other amounts keep the currency's usual form ("€7.50"), formatted in the user's locale (`Price.text(in:)` takes a locale for tests). Stacked fact rows use `.labelStyle(.iconColumn)` so glyphs of different widths share one text edge. Fixtures cover every detail present and absent.
- **Networking seam:** repositories depend on the `APIClient` protocol and describe a call as an `APIRequest` (method, path, query items, optional `Encodable` body, response type). `URLSessionAPIClient` builds the URL from the base URL it is given (`AppDependencies.apiBaseURL(from:logger:)`: `AppConfig.API.baseURL` for the build configuration, or the `-api-base-url` launch argument in debug builds), sends and decodes JSON with the shared conventions in `APIJSONCoding`, adds `X-App-Version` on every request and `X-Local-User-Id` in debug builds when a user is signed in, and turns non-2xx answers into `APIError.http(status:body:)` with the backend's `{code, message}`; transport failures stay `URLError`. `APIClient.send(_:failingWith:)` then maps known backend codes to their `AppError`, other `URLError`s to `.network` and anything else to the caller's fallback, while cancellation passes through untouched so a screen the user left never raises the popup. Request failures are logged with method, path and status (never bodies or headers).
- **Join and leave:** `EventDetailViewModel` owns the event on screen, runs one change at a time (`isBusy`), replaces the event with the server's answer and hands it to the list; failures go to `ErrorCenter`. A `TRY_AGAIN` is repeated once after `AppConfig.API.tryAgainDelay`; a refusal that means the event moved on (`eventFull`, `alreadyJoined`, `notAParticipant`, `hostCannotLeave`, a second `tryAgain`; logged at warning, since a full game is a product state and not a fault) refetches it through `EventRepository.event(id:)` so the detail and the lists show the server's state before the popup explains why. So does a failure that leaves the outcome unknown, a 500 (`participationFailed`) or a transport error (`network`): Laurel commits the join before it reads the event back, so the write may have landed although the answer was lost; when the refetched event already shows what the user asked for (in after a Join, out after a Leave) the popup is skipped and an info line says the write landed, otherwise it shows; the refetch tolerates its own failure. A join or leave that fills the last spot logs "Capacity reached for event <id>". `Participation` decides the control from the event and the caller: hidden for guests, `hosting` when `hostUserId` is the caller, `leave` when `isJoined`, `full` when no spots remain, otherwise `join`. The detail reads the caller through the same `IdentityProvider` the API client uses.
- **Creating a game.** `CreateEventViewModel` owns an `EventDraft` (`Features/Events/Models`): the form's fields plus `issues(now:)`, which names everything still wrong, in form order, against `AppConfig.Events.Creation` (text lengths in UTF-16 units, as the backend counts them), so the Create button is enabled exactly when the backend would accept the body and each section's footer can show its first issue. A new draft proposes the next full hour at least a day ahead (`defaultStartOffset`); `prepare()` takes the spot from the `LocationService` when none is set yet, and `LocationPickerView` moves it; without a spot the picker opens on the user's position (MapKit's default view when that is unknown) and ignores the map's first settle, so leaving it without a drag keeps the spot unset. `CreateEventPayload` is the wire body, built only from a draft with a coordinate, with blank details and a free price left out; `EventDraft.price(currencyCode:)` and `EventDraft.makeEvent(hostUserId:hostName:coordinate:)` are the one place a draft becomes a `Price` or a stored `SportEvent` (the payload, the mock and the test fake use them), and `Price.parseAmount(_:locale:)` reads what is typed into a price field, here and in the filter panel. The draft's `clientId` is chosen once and sent with every attempt, so a retry after a lost answer cannot make a second game (the backend answers the one it has). `submit()` runs one create at a time and stays quiet on cancellation; after a failure that leaves the outcome unknown (`.network`, `.eventCreationFailed`: the backend commits before it answers) it fetches `EventRepository.event(id: draft.clientId)` first and treats the create as landed when that event exists with the caller as host (logged `Create landed for event <id> despite <error>`, no popup; the counterpart of the join/leave refetch in `EventDetailViewModel`), while every other failure, and a lookup that finds nothing, another host's game or fails, reaches the `ErrorCenter` (the sheet mounts its own popup, like the sign-in sheet); on success the sheet dismisses and `EventListViewModel.add(_:)` inserts the game into the list behind it, first on Explore (whose order is the backend's relevance for the caller, so there is no slot to compute) and by start time on My Events (a joined-only list only takes a game the caller is in, and the host always is; never twice for one id), bumps the shared `ChangeTracker` (`AppDependencies.eventChanges`) so My Events reloads on its next appearance, and logs the invalidation under `.cache`. The floating "+" (`CreateEventButton`, `lilyFloatingActionButton()`) is a `ZStack` sibling of the Explore content inside the safe area, above the floating tab bar, and the map's selected card is lifted by `DesignTokens.Layout.floatingButtonFootprint` so the two never overlap; a guest gets the sign-in sheet from it. `MockEventRepository.create` mirrors the backend in memory: the draft's client id is the event id, the `IdentityProvider`'s user the host (named "You"), and a repeated client id answers the existing game.
- **Games in groups.** `EventScope.group(id:)` is the third list scope: `RemoteEventRepository` reads it from `GET /api/groups/{id}/events` (no `scope` query, never a position; the backend answers the group's upcoming games in start order), `MockEventRepository` filters its fixtures by `group?.id`, and `makeEventListViewModel(scope: .group(id))` starts from `EventFilter.everything` like My Events, so a group's game 30 km away is never hidden. `EventListViewModel.add` inserts a created game by start time into the group's list only when `event.group?.id` matches. `SportEvent.group: EventGroupRef?` is decoded from the backend's `group` (absent for an ungrouped game) and survives `updatingParticipation`; `EventDraft.group` is the ref too, so `makeEvent` and the mocks can show the badge without a lookup, while `CreateEventPayload.groupId` sends only the id (omitted when `nil`). `CreateEventViewModel` takes `MyGroupsStore` and an optional `lockedGroup`: `prepare()` reads `eligibleForEvents` (no request; the store is loaded on sign-in), `showsGroupRow` hides the row for a user without eligible groups, and a locked group is stamped on the draft and shown read-only. `GroupDetailView` owns an `EventListViewModel(scope: .group)` for its Events segment (`GroupEventsSegment`), reloads it with `.task(id: eventChanges.version)` and pull-to-refresh, and hands `events.add` to the create sheet as `onCreated`. On cards the badge is `GroupBadge`; `EventCard`'s first row is a `ViewThatFits`: chips and the relative time on one line while they fit whole (the badge capped at `DesignTokens.Layout.groupBadgeMaxWidth`), otherwise the chips wrap in a `FlowLayout` (badge uncapped; `FlowLayout` now proposes the line's width to a subview wider than the line, so a long name truncates inside the card) with the time under them. `EventPreviewCard` gives the group a caption line of its own and becomes a column at accessibility type sizes.
- **Usage statistics and privacy.** `InteractionRecorder` (`record(_:)`, `flush()`) is the seam the event screens report to; `RemoteInteractionRecorder` is the only type that posts, `NoOpInteractionRecorder` is wired wherever the repositories are mocked, so no preview, UI test or `-mock-events` run ever sends a statistic. Recording is fire-and-forget on the main actor: a guest's interaction is dropped at `record`, another user's at `flush`; sending happens at the batch size, on one timer (`Task` over an injected `sleep`, cancelled by any flush) after the first entry, or when the root view sees the scene go to the background. What is sent is what the backend cannot see for itself (the detail opened, the filter changed, the presentation switched) and is reduced to ids, types and flags before it leaves the view model (`Interaction`, `FilterSummary`): no coordinate, no amount, no date range, no text. The hooks are `EventDetailViewModel.recordViewed()` (once per instance, from the detail's `.task`), `EventListViewModel.filterPanelOpened()` / `filterPanelClosed()` (from `EventFilterButton`, one interaction per panel session and only when the filter changed) and `presentationChanged(to:)` (from `EventListView`); those and the other filter helpers live in `EventListViewModel+Filter.swift`, a split forced by SwiftLint's `type_body_length`, while every stored property stays in the main file. A failed post is a warning under the `.statistics` log category and is not retried.
- **Sign-in flow:** the sheet mounts its own `.errorPopup`, because a sheet is drawn above the root where the shared popup lives (`ErrorCenter` tracks the mounts and only the topmost draws), and it dismisses when `session.state.user` appears, which also works for guests who are already inside the app. `SignInViewModel` and `EmailSignInViewModel` own their sign-in `Task` and cancel it when the sheet disappears; `SessionController` treats `CancellationError` as a quiet exit, holds one authentication slot for sign-in, sign-up and confirmation alike, and `signOut()` clears local state before the remote call and ignores re-entry. Email sign-in and sign-up answer an `EmailAuthResult` (`signedIn`, `confirmationRequired`, `failed`): a sign-up the pool wants confirmed, or a sign-in refused because the email was never confirmed, is not an error and shows no popup; `EmailSignInViewModel` switches its `mode` to `.confirm`, where `canSubmit` needs `AppConfig.Cognito.confirmationCodeLength` digits, `submit()` runs `SessionController.confirmSignUp(email:code:password:)` (confirm, then the normal sign-in with the kept password), `resendCode()` asks for a new code and the mode toggle reads "Back to sign in". `UserDefaultsSessionStore` logs cache hit, miss and invalidation and discards an unreadable blob with a warning.
- **Buttons are native iOS 26 controls.** `lilyProminentButton(sizing:)` (accent `.glassProminent`) and `lilyGlassButton(sizing:)` (plain `.glass`) in `Core/UI/Components/ButtonModifiers.swift` set the capsule shape, `.controlSize(.large)`, `.buttonSizing(.flexible)` (full width) or `.fitted` (hugging) and the button font; nothing puts a frame on a capsule button's label, so every capsule has the system's 50pt height and padding and grows with Dynamic Type. Text fields use `DesignTokens.Layout.fieldHeight` (50pt) to match the button under them, and text-only (`.borderless`) buttons get a 44pt tappable area through `tappableLabel()`. The `.glass` style colours its label from the tint, so ink labels (landing "Sign in", provider buttons) pass `labelColor: .lilyInk`; "Sign out" keeps the red on purpose. Provider buttons centre glyph and title like the system Sign in with Apple button, and the spinner takes the glyph's place while loading. The landing shows two stacked full-width capsules (prominent "Find a game near you", glass "Sign in") inside one `GlassEffectContainer`.
- **Typography:** SF Pro only, with tight tracking on the wordmark and headline (sizes and tracking in `DesignTokens.Typography`).
- **Aurora background** is a 4x4 `MeshGradient` in a 30 fps `TimelineView`, in the spirit of the Raycast home page: a near-black surface with soft luminous red glows and a whisper of grain. Two maroon masses, upper-left behind the headline and lower-right behind the button, are joined by a thin diagonal with a darker valley on either side (`AuroraPalette.roles`), drawn with bicubic smoothing so no cell edge shows. Corners are pinned, edge points slide along their edge, interior points wander on paths that sum three sines drawn from four incommensurate periods (19, 23, 29, 37 s) with golden-angle phase offsets. The red visibly flows because a brightness ripple travels down the main diagonal every 29 s and a weaker one crosses the other diagonal every 41 s (`AuroraGeometry.cellIntensities`), while the raspberry core, kept on the top edge so its peak never swallows the red headline line, breathes every 23 s. The whole background fades in from nothing over 3.5 s (ease-in-out) when a screen appears. Numbers live in `DesignTokens.Aurora`; the math lives in `Core/UI/Effects` (`AuroraGeometry`, `AuroraPalette`, `FilmGrain`) and is unit tested; `LilyTheme` maps roles to asset colors and the view only draws. Every screen adds live film grain: 12 seeded 128 px noise tiles with a squared distribution (sparse bright speckle, blacks stay black), generated once, drawn at 2 device pixels per noise pixel without interpolation and cycled at 24 fps, blended `plusLighter` at 8%. Content screens draw the mesh at `contentIntensity` (0.55), the landing at 0.85, the launch screen at full strength. Reduce Motion freezes the first frame (the fade-in stays, being a crossfade). The app is forced to dark mode via the `INFOPLIST_KEY_UIUserInterfaceStyle` build setting; colorsets keep their light variants for when the light theme returns. Phases are reduced modulo their period in `Double` before becoming `Float`: `timeIntervalSinceReferenceDate` cast to `Float` only resolves steps of several radians, and the old mesh stood still for a minute at a time.
- **Liquid Glass layering.** Two rules that iOS 26 enforces and that are easy to get wrong. A toolbar item already draws its own glass capsule, so the segmented list/map `Picker` sets `.sharedBackgroundVisibility(.hidden)` on its `ToolbarItem` to avoid a doubled background. The tab bar floats above content, so `EventsMapView` lets only the `Map` ignore the bottom safe area and keeps the selected-event card as a `ZStack` sibling inside the safe area; a UI test asserts the card stays above the tab bar.
- **Event types:** `EventType` (football, basketball, tennis, padel, running, volleyball, cycling, climbing, other) drives the amber `EventTypeChip` badge, the map pins and the filter chips; "Other" is for games the list does not name yet.
- **Provider glyphs:** Apple and Email are SF Symbols in the ink color (the envelope filled so it weighs the same as the Apple mark); Google uses its official multicolor "G" as a vector asset (`GoogleLogo`). Apple and Google tap through to the popup's "Coming soon" until the pool has identity providers; the Apple button must meet Apple's Sign in with Apple guidelines (or use `SignInWithAppleButton`) once it signs in for real.

## AWS deployment

The infrastructure lives in the `iris-dc/rose` CDK repository (eu-central-1): an Application Load Balancer in front of one ECS Fargate task running Laurel at `https://api.iskra.red` (Route 53 zone `iskra.red`, ACM certificate), three on-demand DynamoDB tables, a Cognito user pool `lily-users` (email + password; Apple and Google identity providers are follow-ups) with the app client `lily-ios`, CloudWatch alarms and a monthly budget. The pool id and the client id the app will need are the `UserPoolId` and `UserPoolClientId` outputs of rose's `RoseAuthStack`. Pushing to `rose/main` deploys, and a green `laurel/main` run triggers a rose deploy with that commit.

Release builds point at `https://api.iskra.red` (`AppConfig.API.productionBaseURL`) and send the Cognito access token as a Bearer: `AppDependencies.makeDefault()` wires `CognitoAuthService(client: AmplifyCognitoClient(...))` as both the `AuthService` and the API client's `AuthTokenProvider`, with the pool and client ids from `AppConfig.Cognito` (no `amplifyconfiguration.json`; the file names stay git-ignored so a generated one can never ship by accident). The backend validates issuer, expiry, `token_use == access` and `client_id`. Apple and Google identity providers in the pool are the follow-up. See `CLAUDE.md` for the reasoning.
