# Lily

The codebase of **iskra**, a meetup-style iOS app for sport events (the app is named iskra on the home screen and in its copy since 2026-09-28; the Xcode project, targets, module, scheme and bundle id `iris.lily` keep the code name): sign in, create and join events, chat with participants.
iOS 26+, SwiftUI, Liquid Glass, dark-only design (for now) with a rust-leaning red accent over maroon. The backend, Laurel (`iris-dc/laurel`, a Spring Boot 4 service), runs on AWS on a tight budget: Cognito for identity, one small ECS Fargate task over DynamoDB for business logic and data; see AWS deployment below.

## Status

Early days. Auth is real: email + password against the Cognito user pool `lily-users` through Amplify Swift, configured in code (no JSON file in the bundle), with the verification code Cognito emails after sign-up entered in the app; Apple and Google stay on the sheet and answer "Coming soon" until the pool has identity providers. Events and profiles come from the Laurel backend when it runs locally (see [Backend](#backend)) or from in-memory mocks with `-mock-events`; `-mock-auth` swaps Cognito for a mock. The AWS side (Laurel on Fargate at `https://api.iskra.red`, DynamoDB, the Cognito user pool) is defined and deployed by the `iris-dc/rose` CDK repository; release builds point at it and send the Cognito access token as a Bearer (see [AWS deployment](#aws-deployment)).

## Requirements

- Xcode 26.5 or newer (the deployment target is iOS 26.5; the project was last upgraded with Xcode 26.6), with an iOS 26.5 simulator runtime.
- No AWS credentials needed to run or test. Signing in for real needs a network and the `lily-users` pool (the ids are in `AppConfig.Cognito`); every test and preview runs on the mock.

## Run

Open `lily.xcodeproj`, select an iPhone simulator, run the `lily` scheme.

From the command line:

```sh
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer   # only if xcode-select points at the Command Line Tools
xcodebuild -scheme lily -destination 'platform=iOS Simulator,name=iPhone 17 Pro' -skipPackagePluginValidation build
```

`-skipPackagePluginValidation` is needed on the command line (and in `ci.sh`) because Amplify pulls in `smithy-swift`, whose build plug-in `xcodebuild` otherwise refuses to validate without an interactive approval; Xcode asks once in the IDE.

## CI

GitHub Actions (`.github/workflows/ci.yml`) runs on every push and pull request to `main` on a `macos-26` runner: it selects the newest Xcode 26, installs SwiftLint with Homebrew (the runner image does not ship it), then runs `scripts/ci.sh all` as one step (lint with the string-catalog check, one build for testing, then unit and UI tests without rebuilding) and uploads the result bundles as an artifact. The runner needs Xcode 26.5 or newer, the same minimum as [Requirements](#requirements). Every `uses:` in the workflow is pinned to a commit SHA, with the release tag it was resolved from in a trailing comment; Dependabot (`.github/dependabot.yml`, `github-actions`, weekly) proposes the bumps as one grouped pull request, so a week's updates cost one CI run.

To run on the mock auth service, launch with `-mock-auth`; add `-mock-auth-fail` to make every auth call fail and see the error popup, or `-mock-auth-confirm` to walk the confirmation step with the code `123456` (previews can use `AppDependencies.makeMock(authBehavior: .fail(.network))` or `.requireConfirmation(code:)`). Without any of them the app talks to the real pool.

## Backend

Events and profiles come from **Laurel**, the Spring Boot backend (its own repository), which the app reaches at `AppConfig.API.baseURL`. The base URL follows the build configuration: **debug** builds use `AppConfig.API.localBaseURL`, `http://localhost:8080`, and **release** builds `AppConfig.API.productionBaseURL`, `https://api.iskra.red` (Laurel on AWS, deployed by `iris-dc/rose`; see [AWS deployment](#aws-deployment)).

**Simulator.** The simulator shares the Mac's loopback interface, so a Laurel started locally with its `local` profile (DynamoDB Local, auth bypass, seeded with the same nine fixture events the mocks produce) is all that is needed: start it, run the app, and Explore shows the seeded events. Participation is not seeded: against the backend every game shows Join and Home starts empty, while the mocks pre-join every fourth fixture so the tab has content. Plain HTTP to `localhost` needs no App Transport Security exception, because ATS exempts unqualified host names.

**Physical iPhone.** A device on the same Wi-Fi reaches the Mac by its Bonjour name. Add the launch argument `-api-base-url http://<mac-name>.local:8080` to the `lily` scheme (Product → Scheme → Edit Scheme → Run → Arguments; the Mac's name is under System Settings → General → Sharing, "Local hostname"). `-api-base-url` takes a value, the next argument (as `-mock-user-id`, `-realtime-endpoint` and `-app-language` do); `AppConfig.LaunchArguments.value(following:in:)` reads it and `AppDependencies.apiBaseURL(from:logger:)` accepts it when it parses as a URL with a scheme and a host (logged at info as `API base URL overridden: <url>`; anything else is logged at warning and ignored). Like every launch argument it is honoured in debug builds only. Laurel binds all interfaces, so nothing changes on its side; macOS may ask once whether to allow incoming connections for Java. iOS shows the Local Network permission prompt on the first request (the usage text is the `INFOPLIST_KEY_NSLocalNetworkUsageDescription` build setting of the Debug configuration only: a release build ignores the argument and never reaches a `.local` host), and that first request may fail before you tap Allow: pull to refresh.

**Release.** `https://api.iskra.red` takes the Cognito access token the app sends as `Authorization: Bearer <token>`; anonymous reads (`GET /api/events?scope=upcoming`, `GET /api/events/{id}`) work without one, so guests browse, and everything else answers 401 without a valid token, which the app shows as "Session expired".

Without a backend, launch with `-mock-events`: `MockEventRepository` serves the fixtures and joins, leaves and creates in memory (a created game is hosted by the signed-in mock user under the host name "You", with the draft's client id as its id), and `MockProfileRepository` accepts every display name. Previews use the same mocks through `AppDependencies.makeMock()`, and the UI tests pass the argument so they never depend on a running server. Without either, every list load and join reports "You're offline" through the popup, and the lists show the refreshable "Couldn't load events" state (the landing preview fails silently, logged at warning, and just shows no events).

**Identity.** The user id is the Cognito `sub`. The app authenticates with the Cognito **access token** (`Authorization: Bearer <token>`, `AppConfig.API.Headers`), read per request from an `AuthTokenProvider` (`CognitoAuthService` over Amplify, which refreshes tokens itself); a guest has none and sends no `Authorization` header, and the client asks for one only while the app's session has a user (`IdentityProvider.currentUserID`), so a token Amplify still holds after a sign-in the app rolled back never personalises a guest's requests. A 401 from the backend maps to `AppError.sessionExpired` and a 429 (Laurel's rate limit, code `RATE_LIMITED`) to `AppError.rateLimited`, whatever was asked and before the code lookup (`APIError.appError(fallback:)`); the popup then reads "Slow down a moment". Locally, Laurel's `local` profile still bypasses auth for requests **without** a Bearer header and trusts the `X-Local-User-Id` header a **debug build** adds for the signed-in user (`AppConfig.API.sendsLocalUserHeader`, `true` only under `#if DEBUG`); a debug build signed in through Cognito sends a real token too, which the local Laurel validates for real, so start it with the pool and client ids (`COGNITO_USER_POOL_ID=eu-central-1_JmfE31ODT COGNITO_APP_CLIENT_ID=54dul3essertek166u2st78s4a`); it ignores the local header when a Bearer token is present. A guest against the local backend runs as its `local-dev` user, which the backend treats like any other user; it is the app that hides Join and Leave for guests (`Participation.hidden`), so a header-less `curl` can join as `local-dev`. The header value comes from an `IdentityProvider` (`SessionIdentityProvider` reads `SessionController.state.user?.id`), so the client never depends on the session controller. Right after a successful sign-in the app `PUT`s the user's display name to the profile endpoint, fire and forget, so the backend can stamp the host's name onto events; a failure is logged, never shown.

**Contract, in words.** JSON, UTF-8, ISO-8601 instants in UTC (`2026-09-13T17:00:00Z`; the app also reads fractional seconds and always writes without). Every request carries `X-App-Version: <CFBundleShortVersionString> (<CFBundleVersion>)`, e.g. `1.0 (42)` (`AppConfig.API.Headers.appVersion`; the value is an `AppVersion` read once from `Bundle.main` and injected into `URLSessionAPIClient`, so tests pin it), so the backend can tell app versions apart in its logs and statistics. `GET /api/events?scope=upcoming|joined` lists events: `joined` returns the caller's upcoming events, hosted ones included, uncapped and ascending by start (past games are not listed); `upcoming` is capped at 100 (Laurel's `events.upcoming-limit`) and **ordered by relevance for the caller, not by start**. Explore sends the user's position with that request as `lat` and `lon` when it is known (`EventRepository.events(in:near:)`; `Coordinate.rounded(toDecimals:)` at `AppConfig.Events.positionPrecision`, two decimals, about a kilometre, printed with fixed decimals and a `.` whatever the locale; never sent with `joined`), and the backend weighs distance, the event types the caller views and joins, the hosts they join, their own participation and the start time; a guest with a position gets distance and time, without one the plain start order, and the app tolerates any order (a game created from Explore goes to the top of that list, by start time on Home). `POST /api/events/{id}/participants` joins and `DELETE` on the same path leaves; both return the updated event. `PUT /api/events/{id}` (`UpdateEventPayload`: the create body without `clientEventId` and `groupId`, an absent optional removing the stored one) replaces every editable field for the host and returns the event; `403 NOT_HOST` ("Not your game") for anyone else, `409 CAPACITY_TOO_LOW` ("Too few spots") when the new capacity is below the people already in, which the form prevents beforehand by flooring the stepper at that count (neither applies while the edit allows extra players, when the capacity is a target the host may set below them, nor when it sends none, which lifts the limit), and anything else without copy becomes `.eventUpdateFailed` ("Couldn't save your changes"). `POST /api/events` creates a game and answers `201` with the event, the caller as host and first participant; the body (`CreateEventPayload`) carries `clientEventId`, `title`, `type`, `startsAt`, `location {name, coordinate}`, the optional `capacity` (left out for a game without a limit), `allowsExtraParticipants` (always sent; `true` makes a capacity the number of players needed, so joins past it are accepted and the game is never full) and the optional `description`, `lookingFor`, `skillLevel` and `price`, left out when blank or free. `clientEventId` is a UUID the app chooses once per draft (`EventDraft.clientId`) and sends with every attempt; the backend uses it as the event id (lower-cased), so a create repeated after a lost answer or a `TRY_AGAIN` gets the same game back instead of making a second one, and `409 EVENT_ID_TAKEN` means another user's game already has that id. `EVENT_ID_REUSED` (409, the same id retried with a different body) is handled the same way: the app knows neither code, maps both to `.eventCreationFailed`, and its refetch of the id then finds the game that did land. The form's limits (`AppConfig.Events.Creation`: 80 UTF-16 units of title, 120 of place name, 1000 of description, 300 of "looking for", counted with `utf16.count` because Bean Validation's `@Size` counts Java's `String.length()`, so an emoji is two; 2 to 200 players; a price with at most seven integer digits and two decimals) mirror the backend's constraints, so a draft that passes on the device never earns a `400 VALIDATION_FAILED`; the app additionally requires a start at least 15 minutes ahead, where the backend only requires the future. `PUT /api/profile` with `{"displayName"}` returns the profile. An event carries `id`, `title`, `type` (`EventType`, including `other`), `startsAt`, `location {name, coordinate {latitude, longitude}}`, `capacity` (absent for a game without a limit), `allowsExtraParticipants` (read as `false` when absent, so older payloads and fixtures keep decoding), `participantCount`, `hostUserId`, `hostName`, `isJoined` (whether the caller participates) and the optional details `description`, `lookingFor`, `skillLevel` (`beginner|intermediate|advanced`) and `price {amount, currencyCode}` (a JSON number, absent means free); optional fields are absent, never `null`, and `SportEvent` decodes the shape directly, key for key. Failures carry `{"code", "message"}`: `EVENT_NOT_FOUND` (404), `EVENT_FULL`, `ALREADY_JOINED`, `NOT_A_PARTICIPANT`, `HOST_CANNOT_LEAVE`, `TRY_AGAIN` (409; the last means the write lost a race with another player or was throttled by DynamoDB and is safe to repeat) `VALIDATION_FAILED` (400) and `RATE_LIMITED` (429, with a `Retry-After` header; the app maps it to `.rateLimited`, "Slow down a moment", by the code and by the status alone when the body is missing, the way a 401 becomes `.sessionExpired`, whatever was asked); the first six map to their own `AppError` cases and copy, anything else (including `EVENT_ID_TAKEN`) becomes `.eventsUnavailable` on a read, `.participationFailed` on a join or leave and `.eventCreationFailed` ("Couldn't create your game") on a create, and a transport failure becomes `.network`. `GET /api/events/{id}` returns one event: the detail screen fetches it after any of the 409s, and after a 500 or a transport failure on a join or leave (the write may have committed before the answer was lost), so the count on screen and in the lists behind it is the server's before the popup explains the refusal; a `TRY_AGAIN` is first repeated once after `AppConfig.API.tryAgainDelay`.

**Usage statistics.** The taps the backend cannot see for itself are reported by a signed-in user to `POST /api/interactions` (`Core/Statistics`): `event_viewed` (event id, type and host id) when a detail opens, `filter_applied` when the filter panel closes on a changed filter or "Show all events" is tapped, and `presentation_changed` (`list` or `map`). The body is `{"interactions": [{"kind", "occurredAt", ...}]}` with at most `AppConfig.Statistics.batchSize` entries, answered `202 {"accepted": n}`. A `filter_applied` carries the **shape** of the filter (`FilterSummary`: the selected type names, the radius in metres, and whether a price cap, a level, a date range or "open spots only" is set), never the amount, the dates or any text; no interaction carries a coordinate, by construction of `Interaction`. `RemoteInteractionRecorder` buffers them per user and posts when `batchSize` (10) have gathered, `flushDelay` (30 s) after the first one, or when the app goes to the background (`AppRootView`); the buffer is capped at `maxBuffered` (100, oldest dropped) and a failed post is a warning under the `.statistics` log category, never a popup or a retry. **Guests send nothing, ever**: an interaction recorded without a signed-in user is dropped on the spot, and entries recorded for a user who signed out before the flush are dropped then. Mock runs (`-mock-events`, previews, UI tests) use `NoOpInteractionRecorder`. The backend records joins, leaves, creates and list views itself, keeps per-user aggregates and a Firehose stream to S3 (see the `iris-dc/rose` and `iris-dc/laurel` READMEs); only the Cognito `sub` identifies a user there.

## Groups

Groups are communities around a sport (or "Any type"): a chat room, a member list and the games hosted in the group. The feature ships in debug builds only until it is finished, behind `AppConfig.FeatureFlags.groups` (`Config/AppConfig+FeatureFlags.swift`; `FeatureFlags.chat` gates the Chats tab and the chat screens, and with `groups` on and `chat` off a group row opens the group instead of its chat). A release build has three tabs.

- **Visibility.** A group is `public` (anyone finds it on Discover and joins with one tap) or `private` (reachable only through an invite; a non-member gets "group not found", never its existence). Visibility is chosen at creation and never changes.
- **Roles.** The creator is the `owner` (exactly one; cannot leave, may delete the group and change roles), `admin`s edit the group, invite, create games, remove and ban members, and `member`s chat and join games. Per group, two switches say what members may do beyond that: "Create games" (`membersCanCreateEvents`) and "Invite people" (`membersCanInvite`), both on by default. A ban is a marker row, not a membership: a banned user cannot rejoin or be invited until an admin unbans them. `GroupAccess` (`Features/Groups/Models`) turns a group and the caller's id into what the screen may offer, the way `Participation` does for events. Since 2026-09-29 a **public** group's roster is readable by every signed-in user (`GroupAccess.canSeeMembers(in:)`; the Members segment shows, rows open profiles, no actions, no banned list), a private group's stays members-only.
- **Direct invites.** A member with invite rights (owners and admins always, members when "Invite people" is on) opens the Invite sheet from the group's detail and picks a person from **the people they share a group or a game with**: `GET /api/groups/{id}/invitees` answers them sorted by name, each with the first shared group or game as context ("In Kreuzberg Kickers", "Played Sunset 5-a-side") and `isInvited` while a pending invite into this group exists; the group's members and banned users are never among them. `POST /api/groups/{id}/invites` with `{"userId"}` sends the invite and answers it (`SentInvite`, whose id is the invitee's inbox item id); inviting someone who already holds a pending invite answers that invite again. The invitee finds it in the inbox on their Chats tab and taps Accept or Decline (see [Chats and inbox](#chats-and-inbox)). Refusals with copy of their own: `ALREADY_MEMBER` ("They're already in this group"), `CANNOT_INVITE` (banned from the group), `USER_NOT_FOUND`, `NOT_A_MEMBER` and `FORBIDDEN`, the per-user rate limit; anything else is "Couldn't send the invite". Invites expire after seven days; there is no code, no link and no name search over every account, so nobody can enumerate users, and revoking a sent invite is a follow-up.
- **Games in groups.** A game may be hosted in a group: the event form's Group row offers the groups the caller may create games in (`MyGroupsStore.eligibleForEvents`) and is preset, read-only, when the form opens from a group's "Create game". A public group's games are on Explore like any other, with the group's name as a badge on the card and "Hosted in <group>" on the detail, which links to the group. A private group's games never reach Explore, on the device too: one you create in a private group shows on Home and under the group, not on the Explore list behind the form, and the mock feed hides the Padel Crew's game the same way. Their detail is served to members and participants only and says "Members only" under the group's name. Every group's upcoming games are listed under the Events segment of its detail.
- **Launch arguments.** `-mock-user-id <sub>` makes every mock sign-in yield that user so two simulators can act as two people (only together with `-mock-auth`; a Cognito user is whoever the pool says). `-mock-chat-replies` makes a fixture member answer every message sent in a mock room after 1.5 s (never passed by the UI tests); `-mock-attachment-picker` makes the composer's attach menu add the bundled fixtures at once instead of opening the system pickers, which run out of process and cannot be driven by XCUITest: "Photo library" adds `MockAttachmentPhoto`, "Camera" (shown without a camera then) the clip `MockAttachmentVideo`, "File" the document `MockAttachmentFile` (the mock run's uploads land in `MockAttachmentStore`, whose `mock://attachments/...` links `MockAttachmentURLProtocol` serves back to the loader); `-realtime-endpoint <url>` names the realtime API for a debug build against a deployed backend (otherwise `GET /api/me` names it, and a local Laurel gets none: chat catches up over REST on appear, after a send and, for the open room, on every return from the background). All are ignored by release builds like every other argument. `-system-push` keeps the system's permission prompt and APNs registration under `-mock-events` (the device registry stays in memory), so the prompt and an `xcrun simctl push <udid> iris.lily payload.json` banner can be seen on a simulator without a backend.
- **Chat.** One chat room per group, visible to members (`ChatView`, pushed on the Chats stack from a Chats row, a group's "Open chat" or an accepted invite; the tab bar hides while it is open). Messages are REST writes: `POST /api/groups/{id}/messages` with a `clientMessageId` chosen once per composed message and kept through every retry, so the backend replays a repeat instead of storing a duplicate, and the bubble keeps its identity when the stored message replaces the optimistic one; a send answered `TRY_AGAIN` (the sender's own overlapping writes racing on the backend) is repeated once with the same id (`LostRace.attemptTwice`), and every chat failure goes through `GroupErrorReporter`, so a `TERMS_REQUIRED` on a send or a delete raises the terms sheet as on the groups screens. History is read from `GET /api/groups/{id}/messages` with `limit` and either `before` or `after`: a page is `{items, hasMore, channelEpoch, nextBefore, nextAfter}`, the two cursors being message ids to continue from, present only with `hasMore` and in the direction asked (they may name a message the caller cannot see, so a page of hidden or already-held messages still advances); when a page names none, the app pages before the oldest id it holds and moves its watermark to the newest id returned. A message is text only (`Text(verbatim:)`, no link detection, so a pasted URL never opens on tap), at most 2 000 UTF-16 units, drawn as a plain fill (accent + white for the caller, surface + ink for others; glass is kept for the composer and the day chips because a room scrolls dozens of bubbles at once). One sender's messages within five minutes and on the same day form a run; the timeline (`ChatTimeline`, pure) inserts day chips, shows the sender's *current* name from the roster, hides blocked senders and turns deleted messages into an italic "Message deleted". Deleting a message is for the sender and the group's admins. A message can answer another: Reply, first in a bubble's long-press menu (for any member's message that is not deleted; system rows cannot be answered), puts a preview above the composer ("Replying to Marta", one line of the original, an X) and focuses the field; the send carries `replyToMessageId`, and the backend snapshots a compact quote onto the stored message (`replyTo {messageId, senderUserId, senderName, excerpt?, kind, attachmentKind?}`, the excerpt cut to `AppConfig.Chat.replyExcerptLength`, 120 UTF-16 units, the same cut the app makes for its preview), so pages need no lookup. The bubble draws the quote above its text (a bar, the sender's name, two lines of the excerpt or "Photo" / "Video" / "File" for a media target without text); tapping it scrolls to the original, loading up to `maxReplyLookupPages` (3) older pages when it lies before the history held, and washes it in the accent for a moment. The server never rewrites a stored quote, so a quote reads "Message deleted" only once this device knows the original is gone (the room's tombstones). A reply refused with `REPLY_TARGET_NOT_FOUND` ("That message is gone") keeps its bubble, failed and without the quote, and Retry sends it as a plain message. Clearing the room is per side: `DELETE /api/groups/{id}/messages` moves the caller's history floor to now (the floor the backend already honours on every page) and drops their read marker, so the messages before it are gone for the caller alone while every other member keeps them; a group keeps its row and gets an empty room back in the cache (a live line still lands there, and the next open costs one page at most), a direct conversation (whose item reads "Delete chat") leaves the Chats tab until either side writes again and then returns with only the new lines (`ChatHistoryClearer` in `Features/Chat/Services`, shared by the room's menu and the Chats rows' context menu, both behind a confirmation). A system row (`event_created`) names the game once it is fetched and opens it. The read marker is sent when the room opens, at most once a minute while it is open, and when it closes or the app goes to the background; `UnreadCenter` (fed by the Mine load, live messages and the open room) drives the dot on a Chats row and, with the inbox's unread flag, the badge on the Chats tab; a Mine load is merged into it, not copied: a live mark newer than the snapshot's read marker stays, and the snapshot's flag is taken only when its newest message is newer than what was read here, so joining or editing a group cannot bring a read room's dot back. A 429 closes the composer for the `Retry-After` seconds with "Slow down a moment" under it. Report and Block appear in a message's menu but are disabled until moderation ships. The unsent outbox is in memory: a message that failed to send is lost when the app is killed.
- **Attachments (pictures, videos and files).** A "+" leading the composer's field opens Photo library (the system picker for pictures and videos, no permission prompt), Camera (hidden where there is none, the simulator included) or File (the files importer, any type, several at once); it shows only while `GET /api/me` says `attachmentsEnabled` (the backend has a bucket; without one it answers `409 ATTACHMENTS_DISABLED` and the button is simply absent). Each picked item becomes an `AttachmentDraft` in the composer's `AttachmentComposerModel` (`DeviceMediaPreparer` behind the `MediaPreparer` seam routes it to one of three workers). A picture is downsampled to 2048 px on the longest side and re-encoded as JPEG at quality 0.85 (`ImagePreparer` over `CGImageSource`, off the main actor, so a HEIC or a PNG leaves the device as `image/jpeg` and a 48 MP photo is never decoded whole) with a 512 px thumbnail (at most 200 KB, left out when it will not fit). A video is exported at `AVAssetExportPreset1280x720` into an MP4 (`VideoPreparer`, so a 4K recording leaves the device as 720p `video/mp4`), a frame at 0.5 s becomes its thumbnail through the same image path, and its duration and dimensions ride along as hints; a clip longer than 3 minutes is refused before any export, one over 50 MB after it. A file is copied in under the draft's id (`FilePreparer`, reading the importer's URL under its security scope), typed from what the system knows (`application/octet-stream` when nothing), named after itself (cut to 255 UTF-16 units), refused over 25 MB, and gets no thumbnail (the backend refuses one on a file). Every draft then asks for a ticket (`POST /api/groups/{id}/uploads` with `{clientAttachmentId, kind, contentType, sizeBytes, width, height, thumbnail {contentType, sizeBytes}}` -> `{attachmentId, upload {url, headers}, thumbnailUpload?, expiresAt}`) and PUTs both files to the presigned targets with exactly the headers the ticket names (`URLSessionAttachmentUploader`, a session of its own with `waitsForConnectivity` and a 120 s timeout; two uploads at a time). The strip above the field shows each item at 72 pt (a picture as its thumbnail, a video as its thumbnail under a play badge, a file as a chip with its type glyph, name and size) with its progress ring, a failed glyph that retries on tap (a new ticket) and an X; Send opens once every item is uploaded (words alone, attachments alone or both), and the message's `attachments` names the tickets' ids (`{attachmentId, kind, contentType, sizeBytes, fileName?, width?, height?, durationSeconds?, hasThumbnail}`, `text` omitted when blank). Caps mirror Laurel's (`AppConfig.Chat.Attachments`): 10 per message, 10 MB per picture after re-encoding, 50 MB and 180 s per video after the export, 25 MB per file (over a cap the item is refused on the device with "That's too big", whose body names all three), file names cut at 255. The stored message carries `attachments [{id, kind, contentType, sizeBytes, fileName?, width?, height?, durationSeconds?, url, thumbnailUrl?, urlExpiresAt}]` with presigned links good for an hour; the bubble draws pictures and videos as a gallery (one at its own aspect ratio, two side by side, three or four as squares, "+N" on the fourth beyond that; a video tile carries a play badge and its length; a caption below, and media alone is the bubble itself) and files as cards under it (type glyph, name, size, a download glyph until the bytes are on the device; a file card keeps the bubble's fill), a tap opens the full picture over black (pinch to zoom, double-tap to reset, Share), plays the video in the system player once the clip is on the device (a ring shows the download), or opens the file in QuickLook (downloaded with a ring on the card first), and a tombstone drops them all. Links are never cached, only bytes by attachment id: `DiskAttachmentCache` keeps them under `Caches/Attachments/<id>` and `<id>.thumb` (200 MB, least recently used out first, cleared on sign-out), the files of an item just sent are copied in under the stored id so it never downloads, and `AttachmentLoader` fetches a miss once (reporting progress when asked), refreshing the link through `GET /api/groups/{id}/messages/{mid}/attachments/{aid}` when it is within a minute of expiry and once more after a 403 (presigned links die with the backend's credentials); the player and QuickLook read a hard link to the cached bytes under `tmp/AttachmentPreviews/<id>/<name>`, named after the file or, for a video, the content type's extension, because both decide what they read from the name. Refusals with copy of their own: `ATTACHMENT_NOT_FOUND` (the upload never finished, or someone else's), `ATTACHMENT_TOO_LARGE`, `ATTACHMENT_TYPE_NOT_ALLOWED`, `ATTACHMENTS_DISABLED`; a ticket or PUT that fails otherwise is "Couldn't upload the attachment", a download "Couldn't load the attachment". Uploads are foreground only: backgrounding mid-upload fails the item and Retry asks for a new ticket.

## Chats and inbox

The Chats tab (debug builds, behind `AppConfig.FeatureFlags.chat`; bar order Home, Explore, Chats, Profile) lists every conversation: the **inbox** pinned first, then the caller's rooms, group rooms and direct conversations together, most recently active first, each with an unread dot (a conversation is a person row: the other person's initials in the accent, their name, "Direct message") and a context menu on long press whose one item clears the chat for the caller ("Clear chat" for a group, "Delete chat" for a conversation; see [Groups](#groups)); a guest sees the sign-in prompt instead, and nothing is requested for them. The tab's badge counts the rooms with unread messages plus one while the inbox holds something unseen (`unreadCenter.count + (inbox.hasUnread ? 1 : 0)`); Home rows carry no dots, because they open the group's detail, not the room.

- **The inbox** is one conversation titled with the app's name ("iskra") whose rows are system cards: an **invite** ("**Noor** invited you to **Climbing Buddies**", the group's visibility, Accept / Decline while it is pending and not expired, afterwards "You joined", "Declined" or "Expired") and a **game reminder** ("Game reminder", the game's title, its place, when it starts as the day, the clock time and the distance ("Today, 6:30 PM · in 58 minutes"), "Hosted in <group>" for a grouped game; the whole card opens the game's detail). Accepting is `POST /api/me/inbox/{id}/accept`, which answers the item and the group with the caller's membership; the group goes into Mine at once and its chat opens; a repeat on an accepted invite answers the same shape. Declining is `POST .../decline`. Opening the inbox marks it read (`PUT /api/me/inbox/read` with the newest item's id; the backend keeps the marker monotonic), and so does an item that lands while it is open. Verdicts on an invite (`INVITE_NOT_PENDING`, `INVITE_EXPIRED`) reach the popup and reload the inbox, so the card shows what the backend has.
- **Where it comes from.** `GET /api/me/inbox?limit=50[&before=<id>]` pages by ULID (ids sort as time, so an ascending page's last item is the newest); `InboxStore` (`Features/Inbox/State`, app-lifetime, a `SessionObserver` cleared on sign-out) is the one source for the Chats row's caption, the badge and the inbox screen, loaded on the shell sync (launch, foreground, sign-in) and on the Chats tab with the lists' staleness rules (`AppConfig.Inbox`), with "Load earlier" fetching the page before the oldest item. A live `inbox_item` on `users/<sub>` (once the realtime connection exists) goes through `InboxStore.apply`. A kind this build does not know decodes and stays hidden, so a newer backend cannot break the page.
- **Reminders** are written by the backend one hour before a game starts, one per participant (host included), into the inbox, and since 2026-10-02 also **pushed** to the user's registered devices through APNs, so a reminder reaches a phone whose app is closed. A game created less than an hour ahead gets none.
- **Push notifications** (`Core/Push`). A signed-in user entering the app (launch with a restored session, or a sign-in) is asked for the notification permission once, as the shell appears (`PushCoordinator.offerReminders()` from the root view's sync; the system prompt, no pre-screen), and again after the first successful join or create should that ask not have happened (`PushOptIn.offerReminders()` from `EventDetailViewModel` and `CreateEventViewModel`); the system remembers the answer, so no later call shows anything. Guests are never asked: reminders need an account. While the permission is granted, every shell sync of a signed-in user (launch, foreground, sign-in) runs `PushCoordinator.sync()`: `registerForRemoteNotifications` through `SystemPushRegistrar` (answered by `LilyAppDelegate` through `PushEventRelay`, with a 10 s timeout), then `PUT /api/me/devices` `{token, platform: "ios", environment: "sandbox" | "production" (by build configuration), appVersion}` when the token or the user changed or the last registration (kept in `UserDefaults`) is a day old. A sign-out sends `DELETE /api/me/devices/{token}` **before** the session flips (`SessionObserver.sessionWillEnd()`, awaited by `SessionController.signOut()`), so the Bearer still goes out; it waits `AppConfig.Push.unregisterTimeout` (3 s) at most, since the row expires on the backend and another account registering the token takes it away. The backend's payload carries `kind: "event_reminder"` and `eventId`; a tap (`LilyAppDelegate`, `userNotificationCenter(_:didReceive:)`) opens the game through `EventOpener` (the inbox's reminder card uses the same), on the Chats stack, or Home while chat is off; a tap that launches the app waits for the session restore (`PushCoordinator.pendingEventID`). A reminder that arrives while the app is open shows as a banner too. Failures (no entitlement on a simulator, no network, a refused registration) are logged under `push`, never shown. `lily.entitlements` at the repository root carries `aps-environment` (`CODE_SIGN_ENTITLEMENTS` in both configurations); pushes need an Apple Developer Program team on the target and the APNs key in rose's secret (its README, first-time setup step 10). `-mock-events` swaps in `MockPushRegistrar` (grants without a prompt, a fixed token) and `MockDeviceRepository`, so the UI tests never meet the alert.
- **Mocks.** `-mock-events` serves two inbox items (a reminder for "Sunset 5-a-side" starting an hour after launch, then Noor's invite into the private Climbing Buddies, which nothing else reaches), remembers the read marker and the answers for the run, and computes invite candidates from the fixture rosters and game hosts: for Sunday Padel Crew they are Aiko, Ayşe, Dev, Jonas, Marta, Noor and Sam (its own members and its banned Priya are out), and inviting one of them marks the row "Invited" for the run.

## People

Every person the app names can be opened (2026-09-29): roster rows, event participant rows, the host line on an event and a sender's name or avatar in a chat push `UserProfileDestination(userId, displayName, context)`, which every stack root registers through `.groupDestinations` (`context` is `.fromChat` when a conversation's info button or the other person's bubbles push it, and that profile then offers no "Message" back into the room it came from); the caller's own rows say "You" and are not links, and guests are never offered one (names are members-level information, like a roster).

- **Profiles.** `GET /api/users/{userId}` answers `UserProfile {userId, displayName, sharedGroups: [GroupSummary {id, name, visibility, type?, memberCount}]}`: the person's current display name and the live groups both are in, sorted by name (the caller's own id answers their own groups). `UserProfileView` shows the initials, the name (also the inline title), a prominent "Message" button for anyone but the caller (not on the profile a conversation's info button opens, though: that chat is one Back away and the button would only push it again) and "Groups in common" as rows that open the group's detail (through the `EventGroupRef` destination, since a summary is not the whole group); "No groups in common yet" when there are none, a retry when the load failed (the popup says why: "Couldn't load this profile"); the reload the screen runs on the way back from a pushed group keeps the profile on screen. `UserRepository` (`Features/People/Interfaces`) is the seam, `RemoteUserRepository` and `MockUserRepository` (profiles from the fixture rosters: a person is whoever any roster names, the groups in common are the caller's groups whose roster names them) the implementations, `UserProfileViewModel` the screen's flow.
- **Direct conversations.** A conversation with a person **is a group of kind `direct`**: `SportGroup.kind` (`GroupKind`, `group` or `direct`; a payload without the field, older fixtures and samples included, reads as `group`, and a value this build does not know is kept as `unknown(name)`: such a room stays on Chats, is no community and offers chat and the roster only, no group actions) and `counterpart {userId, displayName}` (the other person, as the caller sees them) are the only additions, and the other fields are fixed by the backend: `name` = the person's display name (so every screen that shows the name shows the person), private, two of two members, `channelEpoch` 1 forever, both permissions off, `member` on both sides. Everything chat already does (history, sending, read markers, unread, realtime rooms, blocks, deleting your own messages) therefore applies unchanged, and the room is a `ChatView` titled with the person, without a member count, whose info button opens their profile instead of a group detail. "Message" lives on a profile (`POST /api/conversations {userId}`; idempotent, one id per pair, so a repeat answers the same room and `TRY_AGAIN` is repeated once): the conversation goes into Mine at once and its chat opens on the Chats tab. What a conversation cannot do, on the device (`GroupAccess.conversation`: chat and the two-person roster only) and on the backend (`403 FORBIDDEN`): be edited, deleted as a group, left, invited into, given roles, or host a game; "Delete chat" (the room's menu, or a long press on its Chats row) is the per-side way out: the conversation leaves the caller's Chats tab and returns, without the old messages, when either side writes again. **Chats versus Home:** `MyGroupsStore.groups` holds everything and feeds the Chats tab (a conversation is a person row captioned "Direct message", the accent avatar of every single person), the unread set and the realtime rooms; `MyGroupsStore.communities` (kind `group`) is what "your groups" means on Home, in the event form's Group picker and in the invite sheet, so a conversation is never a row there, never a group in common on a profile and never a place to host a game. A conversation the other side starts arrives on `users/<sub>` as a `membership_changed(joined)` for a room Mine has never seen, which only reloads Mine. Refusals with copy of their own: `USER_NOT_FOUND`, `CONVERSATION_LIMIT` ("You have too many conversations", the cap `AppConfig.People.maxConversations` = 200), the terms gate, the rate limit; anything else is "Couldn't start the conversation". The mock ships one conversation, with Marta (`mock-dm-mock-user-marta`: six lines, her last three unread, so the Chats tab shows a person row with a dot from the start), and creates `mock-dm-<userId>` for anyone else, so the room, Mine and the Chats tab treat it like any group.
- **Who's in.** `GET /api/events/{eventId}/participants` answers `{items: [EventParticipant {userId, displayName, joinedAt, isHost}]}`, the host first, then by join time, never paged, for signed-in callers who may read the event; the detail lists them under its facts (`EventDetailViewModel.participants`, loaded on appear and again after a join, a leave or the refetch that follows a refusal), each row a link to the person's profile with a "Host" chip on the host's, the caller's own saying "You". The host line under the title links to the host's profile when the host's id is known and the caller is signed in and not the host. The mock lists the fixture's host, then `participantCount - 1` deterministic roster names, then the caller as "You" when they joined.

## Tournaments

A tournament (slice L1 of the tournaments plan, 2026-10-04; debug builds, behind `AppConfig.FeatureFlags.tournaments`) is an organiser-run competition for one event type: a `format` (`single_elimination`, byes to the next power of two with seed 1 meeting seed N, or `round_robin`, the circle method), `teamSize` (1 means players enter alone; more means a captain names a team and teammates join it until it is full; one entry per user), `maxEntries` (2 to 64 for a bracket, at most 12 for a round robin: a start writes every match in one transaction), `allowsDraws` (team sports by default, racket sports, esports and board games not; always sent by the app), a start, an optional registration deadline before it, a place, and optionally the group that hosts it (then its visibility is the group's and creating it follows "members can create games"); a standalone one picks public or private. The lifecycle is `registration` -> `in_progress` (the organiser starts it by hand from the detail's menu once the format's minimum is in: 2 entries for a bracket, 3 for a round robin) -> `completed` (the final's result, in a bracket) or `cancelled`; entries are taken while in registration and before the deadline.

- **The room is a group.** A tournament's chat is a `Group` of kind `tournament` under the tournament's id: the organiser holds the `owner` row, every player a `member` row; `name`, `visibility` and `type` are the tournament's, `maxMembers` is `maxEntries * teamSize + 1`, both member permissions are off. `GET /api/groups?scope=mine` lists it, so the Chats tab shows it like any room (trophy mark, "Tournament · 6 players"); it is never on Discover groups, never a community on Home or in the forms (`SportGroup.isCommunity`), and `GroupAccess.room` gives its members chat and the roster only: entering and leaving go through the tournament's entries, and the group routes (join, leave, edit, delete, invites, roles) answer `403` for it. A room row on Chats opens the chat, whose info button opens the tournament; a room pushed as a group (a profile's "Groups in common") opens the tournament too (`GroupDestinations`).
- **Reads and writes.** `GET /api/tournaments?scope=upcoming[&type=&lat=&lon=]` (public, in registration, soonest first; the coarse position is for the statistics only), `?scope=mine` (every tournament whose room the caller is in: in progress first, then registration by start, then the finished newest first), `GET /api/groups/{id}/tournaments` (all but cancelled), `GET /api/tournaments/{id}` answering `TournamentDetail {tournament, entries, matches, standings}` (anyone for a public one; a private one to its players, its organiser and the hosting group's members, `404 TOURNAMENT_NOT_FOUND` otherwise). `POST /api/tournaments` with `CreateTournamentPayload` (`clientTournamentId` chosen once per draft, so a create repeated after a lost answer finds its tournament; `visibility` omitted with a `groupId`), `PUT /api/tournaments/{id}` with `UpdateTournamentPayload` (every field while in registration; after the start only the name, description and place may differ, `409 TOURNAMENT_LOCKED` otherwise, and `maxEntries` never drops below the entries in: `409 CAPACITY_TOO_LOW`), `POST .../entries` (`{name}` for a team, empty for an individual) answering the `Entry`, `POST .../entries/{entryId}/members` (join a team), `DELETE .../entries/{entryId}/members/{userId}` (leave, or the captain or organiser removes a player; `204` when the entry emptied), `DELETE .../entries/{entryId}` (the organiser drops an entry), `POST .../start`, `PUT .../matches/{matchId}/result`, `POST .../confirm`, `.../dispute`, `.../walkover`, `PUT .../schedule`, `POST .../cancel`. `TournamentRepository` (`Features/Tournaments/Interfaces`) is the seam, `RemoteTournamentRepository` and `MockTournamentRepository` the implementations; the two `204` routes decode through `NoContent` / `OptionalBody` (`Core/Networking/Models/EmptyBody.swift`), the first empty answers the client meets. Refusals with copy of their own: `TOURNAMENT_NOT_FOUND`, `TOURNAMENT_LIMIT` (10 open per organiser), `NOT_ORGANIZER`, `TOURNAMENT_LOCKED`, `REGISTRATION_CLOSED`, `TOURNAMENT_FULL`, `ALREADY_ENTERED`, `TEAM_FULL`, `ENTRY_NOT_FOUND`, `NOT_ENOUGH_ENTRIES`, `NOT_IN_MATCH`, `MATCH_NOT_READY`, `DRAW_NOT_ALLOWED`, plus the reused `CAPACITY_TOO_LOW`, `MEMBERSHIP_LIMIT`, `GROUP_NOT_FOUND`, `FORBIDDEN`, `TRY_AGAIN` (repeated once by every write), `TERMS_REQUIRED`.

## Languages

The app ships in English (the source language and the fallback), Russian, Spanish, French, Ukrainian, Polish and Portuguese (`AppLanguage`; the codes are the `.lproj` folders: `en`, `ru`, `es`, `fr`, `uk`, `pl`, `pt`, so `pt-BR` and `pt-PT` devices both get Portuguese). Which one shows is decided in this order: the Language row on Profile when the user fixed one (a menu with "System" and every language naming itself, stored in `UserDefaults` under `AppConfig.Storage.Keys.languagePreference`), else the system's pick among the app's localizations (`Bundle.main.preferredLocalizations`, which honours the per-app language in iOS Settings), else English. A pick applies at once: `LanguageStore` (`Core/Localization`, on `AppDependencies.language`) persists it, sets `AppLocale` and publishes the language, and `AppRootView` rebuilds the whole tree under `.id(language)` with `.environment(\.locale, ...)`, so every screen, the tab bar and every formatted date, distance and price relabel without a relaunch (the navigation stacks kept in `AppNavigation` survive; a screen's own `@State` restarts).

- **Every line of copy is read through `localized(_:)`** (`Core/Localization/Localized.swift`): `AppBranding` and `ErrorMessageMapper` hold `static var`s and functions, never `static let` strings, so a lookup happens at read time, in the language of that moment. The key is the English text (`localized("Sign in")`), so a language without the translation falls back to English, and a `String.LocalizationValue` interpolation (`localized("\(count) spots left")`) becomes the catalog's `%lld` or `%@` placeholder and picks the plural variant for its number in the language's rules (Russian, Ukrainian and Polish have one/few/many; the catalog carries them). `localized` reads the fixed language's `.lproj` through `Bundle(path:)` (the main bundle while the system chooses, so iOS applies the user's preferred languages) and formats with `AppLocale.locale`, the chosen language in the user's region (a Russian reader in the US keeps US units and the US calendar), because `String(localized:locale:)` alone does **not** switch the language and `String(format:)` evaluates plural categories with the locale it is given, not the lproj's. Model text (`EventType.displayName`, `SkillLevel.displayName`, the day chips, `Price.text`, road distances, file sizes) goes through the same `localized` / `AppLocale.locale`, and SwiftUI's own `Text(date, format:)` follows the environment locale.
- **The catalog** is `lily/Localizable.xcstrings` (one key per line of copy, translations as Xcode's String Catalog JSON; edit it in Xcode's catalog editor or by hand) plus `lily/InfoPlist.xcstrings` for the camera and location usage descriptions. The build compiles them into `<code>.lproj/Localizable.strings` + `.stringsdict` + `InfoPlist.strings`; `knownRegions` in the project file needs no edit. `scripts/l10n-check.py` (run by `ci.sh lint`) fails when a `localized("...")` literal in the code has no key, a key is no longer used, a language lacks a translation, or a translation's placeholders differ from the key's; `LocalizedCatalogTests` checks the compiled bundles the same way and that the lookups answer in the right language and plural form. Adding copy: write `localized("The English text")`, add the key with six translations to the catalog, run the check. Adding a language: a case in `AppLanguage`, the translations for every key, the two usage strings.
- **Backend and mails.** The device registration (`PUT /api/me/devices`) carries `locale`, the language the app shows, and the reminder push is composed in it by Laurel (`i18n/push_<code>.properties`, English fallback); a language change re-registers the device (`AppRootView`'s sync key includes the language, and `LastDeviceRegistration` remembers the locale it sent). Sign-up and "Resend code" pass `clientMetadata: {locale}` to Cognito (`AmplifyCognitoClient`), which rose's Custom Message Lambda reads to mail the confirmation code in that language.
- **Launch arguments.** `-app-language <code>` shows the app in a language for one run without storing the choice (screenshots of every language without a tap on Profile; an unknown code is ignored with a warning); `-reset-session` also forgets the stored language, so every UI test starts in the simulator's language. `LilyLanguageTests` picks Russian on Profile and checks the screen and the tab bar relabel, then goes back to English.
- **Translations** were written in one pass with the feature (2026-10-03) and should be read by native speakers before launch; the terms are consistent per language (a "game" is игра / partido / match / гра / gra / jogo, a "spot" место / plaza / place / місце / miejsce / vaga), Russian and Ukrainian address the user as вы, French as vous, Spanish and Polish informally, Portuguese is neutral between the two varieties.

## Realtime

The realtime API (AWS AppSync Events; the client lands in a later milestone, `Repositories.remote` wires `NoRealtimeTransport` until then) only pushes what the backend has committed, on `rooms/<groupId>/<channelEpoch>` and `users/<sub>`. Every leave, removal and ban bumps a room's `channelEpoch`, which renames its channel, so someone who left stops receiving without the server having to track sockets. `RealtimeSessionController` (`Core/Realtime`) holds the one connection while the app is active with a signed-in user, driven by `AppRootView` from `scenePhase` and the session (`setDesired(active:user:)`): `users/<sub>` plus the open room and the ten most recently active groups of Mine, closed in the background and on sign-out (it is a `SessionObserver`, like every per-user store), renewed with a force-refreshed token (`AuthTokenProvider.freshAccessToken()`, used for nothing else) five minutes before the token expires; a refresh that yields the same token falls into a backoff instead of looping.

- **Resume protocol.** Every open (launch, foreground, reconnect) subscribes first, reloads Mine once, then catches up over REST only the open room and the cached rooms whose newest message moved, three at a time. A naive foreground would fetch every room; this stays under five requests. A page that answers a newer epoch than the room is subscribed at makes the room resubscribe there and be caught up once more, by name, because its watermark already moved. One connect runs at a time: a caller finding one in flight waits for it and then makes its own attempt, and `close()` cancels the connect in flight, so a suspend or a sign-out during a slow connect opens nothing, or closes at once what the handshake still opened. When no connection comes up (no endpoint, no token, a failed open), the open room alone is caught up over REST, so a foreground against a local Laurel still shows what arrived meanwhile.
- **Two cursors per room.** `ChatRoomState` keeps what is shown and the REST watermark, which only `newest`/`newer` pages move, so the next catch-up always starts where REST left off; a lost publish is a delay, never a hole. The room cache (`InMemoryChatHistoryCache`, 300 newest rows per room) is the one owner of room state: the controller's live inserts and catch-ups land where the open chat reads. `ChatCatchUp` merges every page into the room as the cache holds it at that moment (`ChatHistoryCache.update`) and re-reads the watermark after each request, never from a copy taken before it, so a live insert, a tombstone or a drop that landed while the page was in flight is neither overwritten nor resurrected; a room dropped meanwhile stays dropped (`loadNewest` and `catchUp` answer `nil`).
- **Epochs.** A `member_left` carrying a newer epoch is trusted and resubscribed with a small jitter (no group read), and any answer carrying a newer epoch (a page, a send, a read marker, a group) makes the room resubscribe and catch up.
- **Endpoint discovery.** `GET /api/me` names the realtime endpoint; `-realtime-endpoint <url>` overrides it for a debug build against a deployed backend, and the release constant is the fallback. Against a local Laurel none is known, so the connection stays off and chat catches up over REST only: on appear, after a send and, for the open room, on every return from the background (`RealtimeSessionController.resume()` runs that catch-up itself when no connection came up, and only after a `suspend()`: an active <-> inactive flip fetches nothing).
- **Mock transport.** `-mock-events` wires `MockRealtimeTransport`, an in-memory bus: the mock chat echoes every send to the room's channel after 200 ms, and `-mock-chat-replies` makes Marta answer after 1.5 s and deepens every room to 300 rows.

The Xcode project uses synchronized folder groups: any file added under `lily/`, `lilyTests/` or `lilyUITests/` joins the matching target automatically. The other side of that convenience is that **`lily/` must contain only Swift sources, `Assets.xcassets` and the two string catalogs** — any other file there is copied into the app bundle, and `.gitignore` does not prevent it, because Xcode reads the filesystem rather than the git index.

Rules: interfaces and implementations live in separate folders, constants live under `Config/`, every user-facing error goes through `ErrorCenter`, every log line goes through `Logging`.

## Architecture notes

- **Session state machine.** `SessionController` owns `SessionState` (`loading`, `signedOut`, `guest`, `signedIn`). Views only read it; all transitions are methods on the controller.
- **Auth is Cognito through Amplify, behind two seams.** `AuthService` (`restoreSession`, `signIn(with:)`, `signUp`, `confirmSignUp`, `resendConfirmationCode`, `signOut`) is what the app calls; `CognitoAuthService` implements it, and `AuthTokenProvider`, over a `CognitoClient`, the thin mockable surface the service needs (`isSignedIn`, `accessToken`, `currentUser`, `fetchEmail`, `signIn`, `signUp`, `confirmSignUp`, `resendCode`, `signOut`, failing with `CognitoClientError`). `AmplifyCognitoClient` is the one file that imports Amplify: it maps `AuthError`/`AWSCognitoAuthError` to `CognitoClientError`, reads the access token from `fetchAuthSession()` (Amplify refreshes it), and configures Amplify once, on its first call, from `AmplifyConfigurationBuilder` (the legacy `awsCognitoAuthPlugin` JSON built from `AppConfig.Cognito`, stating `USER_SRP_AUTH` explicitly) instead of an `amplifyconfiguration.json` in the bundle. Configuring on first use rather than at construction keeps Amplify out of the unit tests, which build the default composition root. `CognitoAuthService` maps the client errors to `AppError` (wrong or unknown credentials to `invalidCredentials`, since the pool hides user existence; `emailNotConfirmed`, `emailTaken`, `invalidConfirmationCode`, `tooManyAttempts`, `sessionExpired`), makes the `AuthUser` from `sub` and the email attribute (`AuthUser.displayName(fromEmail:)`), signs the pool out again when that read fails after the pool accepted the sign-in (or on a restore without a cached user), so the app is never a guest over a pool session, and answers Apple and Google with `providerUnavailable` ("Coming soon") until the pool has identity providers.
- **SessionStore is a hint, not truth.** It stores the guest choice and the signed-in user as last seen, so a relaunch shows the profile without a round trip; `CognitoAuthService` only trusts a cached `.signedIn` while Amplify still has a session and drops it otherwise. Tokens never live there: Amplify keeps them in the keychain. The mock stores its fake session in the same place.
- **Branding lives in `Config/AppBranding.swift`:** app name, landing headline and copy, tab titles, empty states, sign-in and profile copy, button titles. `AppBranding.Events` holds the capacity copy ("Full", "N spots left" on compact cards, "N of M joined" under the capacity bar; for a game that allows extra players "N more needed" / "N joined" and "N joined · M needed", for one without a limit "N joined", in `AppBranding+Capacity.swift`) and `SportEvent.availabilityText` / `capacityText` are the only formatters, so the landing preview card and the capacity bar cannot disagree. Change copy there and every screen follows; UI tests match on the same literals.
- **Colors** are asset catalog colorsets with light and dark variants, exposed via generated symbols (`Color.lilyAccent`, `Color.lilySecondary`, `Color.lilySurface`, ...). Rust-leaning red `#B72734` is the accent, maroon `#5E0C26` the deep tone behind it, and the aurora core keeps the original raspberry `#B31B3F` in its own colorset (`LilyAuroraCore`) so the accent can be retuned without moving the background; amber (`lilySecondary`) is used sparingly for event-type chips, the hero badge and the "nearly full" capacity state.
- **Location:** `LocationService` returns one fix or `nil`; the app never blocks on it. `CoreLocationService` reads a `LocationUpdateSource` (`CoreLocationUpdateSource` wraps `CLLocationUpdate.liveUpdates`, which prompts for when-in-use permission; the usage text is an `INFOPLIST_KEY_` build setting) and races the first fix against `AppConfig.Location.fixTimeout` in a task group, so cancelling its caller closes the stream. The seam lets the timeout, denied and first-fix paths be unit tested with a scripted fake. `CachedLocationService` wraps it in production: concurrent callers share one upstream request (which deliberately outlives any single caller's cancellation, bounded by `fixTimeout`, so the fix it obtains is cached for the next screen), a fix is reused for `fixTTL` (300 s) and a missing fix for `failedFixTTL` (30 s), so sibling tabs never open two CoreLocation streams. The events screens ask for the position on every appearance (`loadUserLocation()`; a hit within the TTL costs nothing, a later ask follows the user) and again when the app returns to the foreground (`refreshUserLocation()`, which asks the cache to `forgetMissingFix()` first, because that is the one moment permission may have changed in Settings), so the distance filter becomes available without a relaunch and distances, the default radius and the position sent for relevance follow the user instead of staying where the app was first opened; a miss after a fix keeps the view model's last known position rather than blanking the distances (the cache itself remembers the miss for `failedFixTTL`), and the position is logged at info only when it became known or changed. `Coordinate` stays Foundation-only; the CoreLocation bridge lives in `Coordinate+CoreLocation.swift`. Distance is computed on-device with a haversine, no network.
- **Events list caching:** `EventListViewModel.loadIfStale()` (used by `.task`) reuses events loaded within `AppConfig.Events.listStaleAfter` (60 s) when a tab reappears; pull-to-refresh calls `load()` and always reloads; a cancelled load is logged, not reported; a failed load shows a refreshable "Couldn't load events" state instead of the empty state, and `loadIfStale()` does not retry it for `AppConfig.Events.retryAfterFailure` (10 s), so switching tabs while the backend is down does not hammer it; a change made elsewhere or a change of caller ends that wait early, because it proves the backend is up and the answer different. A join or leave on the detail screen comes back through `replace(_:)`, which updates the list in place (and drops the event from a joined-only list when the user left), and bumps the shared `ChangeTracker` (`AppDependencies.eventChanges`); every other list compares the version it loaded against it and reloads on its next appearance, so Home shows a join made from Explore without waiting out the 60 s. A list also remembers the user it loaded for and reloads after a sign-in or sign-out, because `isJoined` is the server's answer for that caller. Explore sends the user's position with the request when it is known (`EventRepository.events(in:near:)`, so the backend can order by distance); content loaded for another position than the one known now counts as stale (without one while one is known, or for a place the user has since left; positions are compared as `Coordinate.coarse`, the same rounding (`AppConfig.Events.positionPrecision`) the repository sends, so GPS drift never counts), and a position that arrives or moves while the request is out earns one reload from `load()` itself, so the backend's order for where the user is replaces the answer without waiting for the next appearance (Home never sends a position and never reloads for one). Every one of these decisions is logged under `.cache`: the reason for a reload (never loaded, changed elsewhere, caller changed, position became known, position changed, retry after failure, older than TTL), a skipped reload (fresh, or waiting to retry) and the invalidation of sibling lists in `replace(_:)`. A failed load reports the mapped error ("You're offline", "Events unavailable"), never a blanket one. The rules themselves (TTL, version, caller, cooldown) live in `ContentFreshness` (`Core/Changes`), a value both `EventListViewModel` and `MyGroupsStore` hold; only the position reason is Explore's own. This view-model-level check is interim until the cached `EventRepository` ships.
- **Groups data layer.** `Features/Groups` follows the events layout. `SportGroup` decodes the backend's `Group` directly (named like `SportEvent` because `Group` is a SwiftUI view); `membership` is absent for non-members and banned users, so `role`/`isMember` never read a banned marker as a membership. `GroupAccess(group:userID:)` is the `Participation` analogue (`guest`, `canJoin`, `inviteOnly`, `member(role)`, `full`, `conversation`) with the permission helpers every screen switches on; the server stays the authority. `GroupDraft` validates name (3..60) and description (<= 500) in UTF-16 units against `AppConfig.Groups`, keeps a lower-case UUID `clientId` that the backend uses as the group id (a repeated create answers the same group), and `makeGroup(ownerName:now:)` is the one place a draft becomes a stored group (mock and test fake). - **Filter panel and capacity bar.** `EventFilter` holds every criterion: `types` (a set of `EventType`, which now includes `other`), `maxDistanceMeters` (defaults to `AppConfig.Events.defaultFilterRadiusMeters`, 10 km, so the default filter already limits distance and still counts as inactive; `nil` is "anywhere"), `maxPrice` (free-form cap, `nil` any, zero free only), `skillLevel`, `dateWindow` (`DateWindow`: whole days, inclusive; switching dates on proposes today plus `defaultFilterDateSpanDays`) and `openSpotsOnly`; `isActive` is simply "differs from the default". `EventListViewModel.filter` is `private(set)` and changed only through `updateFilter { }`, which logs each change; `visibleEvents` is what list and map render, judged against `userLocation` for distance, and while the position is unknown the distance criterion is skipped rather than hiding every game (the panel shows a note instead of the distance choice). The type chips are `EventType.allCases`, the same list the create forms offer (until 2026-09-30 the panel listed only the types present in the loaded page, which hid a type whenever no such game was loaded); `isEverythingFilteredOut` swaps in a "Show all events" empty state whose action is `showEverything()` (`EventFilter.everything`, no criterion at all), because the default radius alone can hide every game and a reset would keep it. A list without a filter button (Home) starts from `.everything` for the same reason (`AppDependencies.makeEventListViewModel`). `EventFilterButton` drops `EventFilterPanel` down as a popover, kept a popover on iPhone too via `presentationCompactAdaptation(.popover)`, so it reads as a dropdown: type chips in a `FlowLayout`, a segmented distance choice, a decimal `TextField` for the price cap with the market currency symbol (`Price.symbol(for:)`) beside a "Free only" chip that sets the cap to zero, a level picker, a dates toggle with two compact `DatePicker`s, and the open-spots toggle; Reset and Done sit in the header. Only Explore is `filterable`. Amounts are compared without conversion (`AppConfig.Events.marketCurrencyCode`), and filtering is on device over the loaded page until the backend takes the criteria as query parameters. `CapacityBar` fills with the occupied share (red, amber when nearly full, muted grey when full) over a faint track, and the label under it counts the same way ("6 of 10 joined"); a game that allows extra players (`SportEvent.playerLimit == .minimum`) fills red up to the number it needs and stays red and open past it ("6 joined · 4 needed"), and a game without a limit (`capacity == nil`, `.unlimited`) draws no track at all, just "N joined"; `isFull` and `isNearlyFull` are always false for both, so "Open spots only" keeps them and Join stays on. The fixtures carry fixed participant counts so the feed shows an open, a nearly full, a full game, one short of and one past the players it needs (Hills ride, Bouldering intro) and one without a limit (Easy 8k loop).
- **Optional event details.** `SportEvent.description`, `lookingFor` (the host's own words for who is still needed), `skillLevel` (`SkillLevel`: beginner, intermediate, advanced; `nil` means any level, and such games match every level choice in the filter) and `price` (`Price`: amount plus ISO currency code; `nil` means free, and so does a zero amount) are all optional with `nil` defaults in the explicit initialiser, so existing call sites keep compiling and payloads written before a field existed keep decoding (tested). `SportEvent.priceText` is the one price formatter ("Free" or the localised amount); the detail screen adds price and level rows to the facts card only when set, shows the description under the title and "Looking for" in its own card, and paid games get a small glass price chip on `EventCard` and the price in the `EventPreviewCard` caption; free games stay uncluttered. Whole amounts drop their minor units ("€5"), other amounts keep the currency's usual form ("€7.50"), formatted in the user's locale (`Price.text(in:)` takes a locale for tests). Stacked fact rows use `.labelStyle(.iconColumn)` so glyphs of different widths share one text edge. Fixtures cover every detail present and absent.
- **Networking seam:** repositories depend on the `APIClient` protocol and describe a call as an `APIRequest` (method, path, query items, optional `Encodable` body, response type). `URLSessionAPIClient` builds the URL from the base URL it is given (`AppDependencies.apiBaseURL(from:logger:)`: `AppConfig.API.baseURL` for the build configuration, or the `-api-base-url` launch argument in debug builds), sends and decodes JSON with the shared conventions in `APIJSONCoding`, adds `X-App-Version` on every request and `X-Local-User-Id` in debug builds when a user is signed in, and turns non-2xx answers into `APIError.http(status:body:)` with the backend's `{code, message}`; transport failures stay `URLError`. `APIClient.send(_:failingWith:)` then maps known backend codes to their `AppError`, other `URLError`s to `.network` and anything else to the caller's fallback, while cancellation passes through untouched so a screen the user left never raises the popup. Request failures are logged with method, path and status (never bodies or headers).
- **Join and leave:** `EventDetailViewModel` owns the event on screen, runs one change at a time (`isBusy`), replaces the event with the server's answer and hands it to the list; failures go to `ErrorCenter`. A `TRY_AGAIN` is repeated once after `AppConfig.API.tryAgainDelay`; a refusal that means the event moved on (`eventFull`, `alreadyJoined`, `notAParticipant`, `hostCannotLeave`, a second `tryAgain`; logged at warning, since a full game is a product state and not a fault) refetches it through `EventRepository.event(id:)` so the detail and the lists show the server's state before the popup explains why. So does a failure that leaves the outcome unknown, a 500 (`participationFailed`) or a transport error (`network`): Laurel commits the join before it reads the event back, so the write may have landed although the answer was lost; when the refetched event already shows what the user asked for (in after a Join, out after a Leave) the popup is skipped and an info line says the write landed, otherwise it shows; the refetch tolerates its own failure. A join or leave that fills the last spot logs "Capacity reached for event <id>". `Participation` decides the control from the event and the caller: hidden for guests, `hosting` when `hostUserId` is the caller, `leave` when `isJoined`, `full` when no spots remain, otherwise `join`. The detail reads the caller through the same `IdentityProvider` the API client uses.
- **Creating a game.** `CreateEventViewModel` owns an `EventDraft` (`Features/Events/Models`): the form's fields plus `issues(now:)`, which names everything still wrong, in form order, against `AppConfig.Events.Creation` (text lengths in UTF-16 units, as the backend counts them), so the Create button is enabled exactly when the backend would accept the body and each section's footer can show its first issue. The Players section is a segmented choice (`create-player-limit`, `PlayerLimit`: "Any number", "Up to", "At least") over a stepper that hides for "Any number" and reads "N players needed" for "At least"; the draft keeps the stepper's value either way and sends `capacity` only when a limit is set, with `allowsExtraParticipants` for "At least", so the backend takes joins past that number or any number at all. A new draft proposes the next full hour at least a day ahead (`defaultStartOffset`); `prepare()` takes the spot from the `LocationService` when none is set yet, and `LocationPickerView` moves it; without a spot the picker opens on the user's position (MapKit's default view when that is unknown) and ignores the map's first settle, so leaving it without a drag keeps the spot unset. `CreateEventPayload` is the wire body, built only from a draft with a coordinate, with blank details and a free price left out; `EventDraft.price(currencyCode:)` and `EventDraft.makeEvent(hostUserId:hostName:coordinate:)` are the one place a draft becomes a `Price` or a stored `SportEvent` (the payload, the mock and the test fake use them), and `Price.parseAmount(_:locale:)` reads what is typed into a price field, here and in the filter panel. The draft's `clientId` is chosen once and sent with every attempt, so a retry after a lost answer cannot make a second game (the backend answers the one it has). `submit()` runs one create at a time and stays quiet on cancellation; after a failure that leaves the outcome unknown (`.network`, `.eventCreationFailed`: the backend commits before it answers) it fetches `EventRepository.event(id: draft.clientId)` first and treats the create as landed when that event exists with the caller as host (logged `Create landed for event <id> despite <error>`, no popup; the counterpart of the join/leave refetch in `EventDetailViewModel`), while every other failure, and a lookup that finds nothing, another host's game or fails, reaches the `ErrorCenter` (the sheet mounts its own popup, like the sign-in sheet); on success the sheet dismisses and `EventListViewModel.add(_:)` inserts the game into the list behind it, first on Explore (whose order is the backend's relevance for the caller, so there is no slot to compute) and by start time on Home (a joined-only list only takes a game the caller is in, and the host always is; never twice for one id), bumps the shared `ChangeTracker` (`AppDependencies.eventChanges`) so Home reloads on its next appearance, and logs the invalidation under `.cache`. The floating "+" (`CreateMenuButton`: a `Menu` with New game and New group under `menuStyle(.button)` so `lilyFloatingActionButton()` styles it; a guest gets the sign-in sheet from either item) is a `ZStack` sibling of the Explore content inside the safe area, above the floating tab bar, and the map's selected card is lifted by `DesignTokens.Layout.floatingButtonFootprint` so the two never overlap; a guest gets the sign-in sheet from it. `MockEventRepository.create` mirrors the backend in memory: the draft's client id is the event id, the `IdentityProvider`'s user the host (named "You"), and a repeated client id answers the existing game.
- **Editing a game.** `EditEventViewModel` (`makeEditEventViewModel(for:onChange:)`) starts from `EventDraft(editing:)`, the event as a draft (`clientId` is the event's id), and judges it by `EventDraft.Rules.editing(participantCount:)`: no lead time (`AppConfig.Events.Editing.minimumLeadTime`, zero, the backend's own rule) and a capacity floor at the people already in (`.capacityBelowParticipants`; the form's stepper starts there, so the issue is a safety net) unless the draft allows extra players or sets no limit, when `Rules.capacityRange(for:)` is the backend's whole range and the needed number may sit below the count (nothing is judged without a limit), as the backend's condition allows. `hasChanges` is `draft != EventDraft(editing: original)`, `canSubmit` needs it, and `submit()` sends `EventRepository.update(id:_:)` through `LostRace.attemptTwice` (Laurel pins the start its pre-read saw, so a second edit landing meanwhile is a `TRY_AGAIN` and the same request then goes through) (`PUT /api/events/{id}` with `UpdateEventPayload`), hands the answer to `EventDetailViewModel.accept`, which replaces the event and calls the same `onChange` a join does, so `EventListViewModel.replace` updates the list behind (and re-sorts a list in start order when the start moved). Both sheets are `EventDraftSheet<Model: EventDraftEditing>` around the generic `EventDraftForm` (the protocol names what the form reads: the draft, its issues, the earliest start, the capacity range, the group row); `CreateEventSheet` and `EditEventSheet` are thin wrappers, and the edit reuses the create identifiers, so a UI test drives both with `create-title` and `create-submit`. `SportEvent.updating(with:)` is how the mock and the test fake turn a draft back into the stored event. Edit shows for `EventDetailViewModel.canEdit`, the `.hosting` participation, identifier `event-edit`.
- **Games in groups.** `EventScope.group(id:)` is the third list scope: `RemoteEventRepository` reads it from `GET /api/groups/{id}/events` (no `scope` query, never a position; the backend answers the group's upcoming games in start order), `MockEventRepository` filters its fixtures by `group?.id`, and `makeEventListViewModel(scope: .group(id))` starts from `EventFilter.everything` like Home, so a group's game 30 km away is never hidden. `EventListViewModel.add` inserts a created game by start time into the group's list only when `event.group?.id` matches. `SportEvent.group: EventGroupRef?` is decoded from the backend's `group` (absent for an ungrouped game) and survives `updatingParticipation`; `EventDraft.group` is the ref too, so `makeEvent` and the mocks can show the badge without a lookup, while `CreateEventPayload.groupId` sends only the id (omitted when `nil`). `CreateEventViewModel` takes `MyGroupsStore` and an optional `lockedGroup`: `prepare()` reads `eligibleForEvents` (no request; the store is loaded on sign-in), `showsGroupRow` hides the row only for a user in no group at all (a member whose groups let only admins host sees a read-only "No group" with the reason in the footer, `explainsNoEligibleGroups`), and a locked group is stamped on the draft and shown read-only. `GroupDetailView` owns an `EventListViewModel(scope: .group)` for its Events segment (`GroupEventsSegment`), reloads it with `.task(id: eventChanges.version)` and pull-to-refresh, and hands `events.add` to the create sheet as `onCreated`. On cards the badge is `GroupBadge`; `EventCard`'s first row is a `ViewThatFits`: chips and the relative time on one line while they fit whole (the badge capped at `DesignTokens.Layout.groupBadgeMaxWidth`), otherwise the chips wrap in a `FlowLayout` (badge uncapped; `FlowLayout` now proposes the line's width to a subview wider than the line, so a long name truncates inside the card) with the time under them. `EventPreviewCard` gives the group a caption line of its own and becomes a column at accessibility type sizes.
- **Usage statistics and privacy.** `InteractionRecorder` (`record(_:)`, `flush()`) is the seam the event screens report to; `RemoteInteractionRecorder` is the only type that posts, `NoOpInteractionRecorder` is wired wherever the repositories are mocked, so no preview, UI test or `-mock-events` run ever sends a statistic. Recording is fire-and-forget on the main actor: a guest's interaction is dropped at `record`, another user's at `flush`; sending happens at the batch size, on one timer (`Task` over an injected `sleep`, cancelled by any flush; the timer lets go of its slot before it flushes, so its own flush never cancels the post) after the first entry, or when the root view sees the scene go to the background. What is sent is what the backend cannot see for itself (the detail opened, the filter changed, the presentation switched) and is reduced to ids, types and flags before it leaves the view model (`Interaction`, `FilterSummary`): no coordinate, no amount, no date range, no text. The hooks are `EventDetailViewModel.recordViewed()` (once per instance, from the detail's `.task`), `EventListViewModel.filterPanelOpened()` / `filterPanelClosed()` (from `EventFilterButton`, one interaction per panel session and only when the filter changed) and `presentationChanged(to:)` (from `EventListView`); those and the other filter helpers live in `EventListViewModel+Filter.swift`, a split forced by SwiftLint's `type_body_length`, while every stored property stays in the main file. A failed post is a warning under the `.statistics` log category and is not retried.
- **Sign-in flow:** the sheet mounts its own `.errorPopup`, because a sheet is drawn above the root where the shared popup lives (`ErrorCenter` tracks the mounts and only the topmost draws), and it dismisses when `session.state.user` appears, which also works for guests who are already inside the app. `SignInViewModel` and `EmailSignInViewModel` own their sign-in `Task` and cancel it when the sheet disappears; `SessionController` treats `CancellationError` as a quiet exit, holds one authentication slot for sign-in, sign-up and confirmation alike, and `signOut()` clears local state before the remote call and ignores re-entry. Email sign-in and sign-up answer an `EmailAuthResult` (`signedIn`, `confirmationRequired`, `failed`): a sign-up the pool wants confirmed, or a sign-in refused because the email was never confirmed, is not an error and shows no popup; `EmailSignInViewModel` switches its `mode` to `.confirm`, where `canSubmit` needs `AppConfig.Cognito.confirmationCodeLength` digits, `submit()` runs `SessionController.confirmSignUp(email:code:password:)` (confirm, then the normal sign-in with the kept password), `resendCode()` asks for a new code and the mode toggle reads "Back to sign in". `UserDefaultsSessionStore` logs cache hit, miss and invalidation and discards an unreadable blob with a warning.
- **Buttons are native iOS 26 controls.** `lilyProminentButton(sizing:)` (accent `.glassProminent`) and `lilyGlassButton(sizing:)` (plain `.glass`) in `Core/UI/Components/ButtonModifiers.swift` set the capsule shape, `.controlSize(.large)`, `.buttonSizing(.flexible)` (full width) or `.fitted` (hugging) and the button font; nothing puts a frame on a capsule button's label, so every capsule has the system's 50pt height and padding and grows with Dynamic Type. Text fields use `DesignTokens.Layout.fieldHeight` (50pt) to match the button under them, and text-only (`.borderless`) buttons get a 44pt tappable area through `tappableLabel()`. The `.glass` style colours its label from the tint, so ink labels (landing "Sign in", provider buttons) pass `labelColor: .lilyInk`; "Sign out" keeps the red on purpose. Provider buttons centre glyph and title like the system Sign in with Apple button, and the spinner takes the glyph's place while loading. The landing shows two stacked full-width capsules (prominent "Find a game near you", glass "Sign in") inside one `GlassEffectContainer`.
- **Typography:** SF Pro only, with tight tracking on the wordmark and headline (sizes and tracking in `DesignTokens.Typography`).
- **Aurora background** is a 4x4 `MeshGradient` in a 30 fps `TimelineView`, in the spirit of the Raycast home page: a near-black surface with soft luminous red glows and a whisper of grain. Two maroon masses, upper-left behind the headline and lower-right behind the button, are joined by a thin diagonal with a darker valley on either side (`AuroraPalette.roles`), drawn with bicubic smoothing so no cell edge shows. Corners are pinned, edge points slide along their edge, interior points wander on paths that sum three sines drawn from four incommensurate periods (19, 23, 29, 37 s) with golden-angle phase offsets. The red visibly flows because a brightness ripple travels down the main diagonal every 29 s and a weaker one crosses the other diagonal every 41 s (`AuroraGeometry.cellIntensities`), while the raspberry core, kept on the top edge so its peak never swallows the red headline line, breathes every 23 s. The whole background fades in from nothing over 3.5 s (ease-in-out) once per launch, on the wall clock (`AuroraReveal`): every instance reads the same curve, so a tab, a push or a sheet that appears mid-fade continues it instead of restarting from black. Numbers live in `DesignTokens.Aurora`; the math lives in `Core/UI/Effects` (`AuroraGeometry`, `AuroraPalette`, `AuroraReveal`, `FilmGrain`) and is unit tested; `LilyTheme` maps roles to asset colors and the view only draws. Every screen adds live film grain: 12 seeded 128 px noise tiles with a squared distribution (sparse bright speckle, blacks stay black), generated once, drawn at 2 device pixels per noise pixel without interpolation and cycled at 24 fps, blended `plusLighter` at 8%. Content screens draw the mesh at `contentIntensity` (0.55), the landing at 0.85, the launch screen at full strength. Reduce Motion freezes the first frame and shows it at once. The app is forced to dark mode via the `INFOPLIST_KEY_UIUserInterfaceStyle` build setting; colorsets keep their light variants for when the light theme returns. Phases are reduced modulo their period in `Double` before becoming `Float`: `timeIntervalSinceReferenceDate` cast to `Float` only resolves steps of several radians, and the old mesh stood still for a minute at a time.
- **Liquid Glass layering.** Two rules that iOS 26 enforces and that are easy to get wrong. A toolbar item already draws its own glass capsule, so the segmented list/map `Picker` sets `.sharedBackgroundVisibility(.hidden)` on its `ToolbarItem` to avoid a doubled background. The tab bar floats above content, so `EventsMapView` lets only the `Map` ignore the bottom safe area and keeps the selected-event card as a `ZStack` sibling inside the safe area; a UI test asserts the card stays above the tab bar.
- **Event types:** `EventType` (football, basketball, tennis, padel, running, volleyball, cycling, climbing, yoga, swimming, table tennis, badminton, martial arts, fitness, skiing, hiking, travel, esports, board games, other; the ten from swimming to board games since 2026-10-04) drives the amber `EventTypeChip` badge, the map pins and the filter chips; "Other" is for activities the list does not name yet. Multi-word types travel in the backend's snake_case (`table_tennis`, `martial_arts`, `board_games`), the raw values say so. Adding one is a case here with its SF Symbol and localized name, the name's six translations in the catalog, and the constant in Laurel's `EventType`.
- **Provider glyphs:** Apple and Email are SF Symbols in the ink color (the envelope filled so it weighs the same as the Apple mark); Google uses its official multicolor "G" as a vector asset (`GoogleLogo`). Apple and Google tap through to the popup's "Coming soon" until the pool has identity providers; the Apple button must meet Apple's Sign in with Apple guidelines (or use `SignInWithAppleButton`) once it signs in for real.

## AWS deployment

The infrastructure lives in the `iris-dc/rose` CDK repository (eu-central-1): an Application Load Balancer in front of one ECS Fargate task running Laurel at `https://api.iskra.red` (Route 53 zone `iskra.red`, ACM certificate), three on-demand DynamoDB tables, a Cognito user pool `lily-users` (email + password; Apple and Google identity providers are follow-ups) with the app client `lily-ios`, CloudWatch alarms and a monthly budget. The pool id and the client id the app will need are the `UserPoolId` and `UserPoolClientId` outputs of rose's `RoseAuthStack`. Pushing to `rose/main` deploys, and a green `laurel/main` run triggers a rose deploy with that commit.

Release builds point at `https://api.iskra.red` (`AppConfig.API.productionBaseURL`) and send the Cognito access token as a Bearer: `AppDependencies.makeDefault()` wires `CognitoAuthService(client: AmplifyCognitoClient(...))` as both the `AuthService` and the API client's `AuthTokenProvider`, with the pool and client ids from `AppConfig.Cognito` (no `amplifyconfiguration.json`; the file names stay git-ignored so a generated one can never ship by accident). The backend validates issuer, expiry, `token_use == access` and `client_id`. Apple and Google identity providers in the pool are the follow-up. See `CLAUDE.md` for the reasoning.
