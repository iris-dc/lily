# Lily — Project Guide

Lily is the codebase of **iskra**, a meetup-style iOS app for sport events (display name `INFOPLIST_KEY_CFBundleDisplayName = iskra` and `AppBranding.name` since 2026-09-28; project, targets, module, scheme and bundle id `iris.lily` keep the code name). Users sign in, create events, join events, and chat with the other participants of an event. The backend runs on AWS on a tight budget.

## Product Scope

- **Auth**: sign up, log in, log out, session persistence.
- **Events**: create, browse, join, leave. An event has an event type (a sport, or "other"), a required number of participants, a time, and a location, plus optional description, "looking for", level and price.
- **Chat**: one chat room per event, visible only to participants.
- **Design**: modern and minimalistic. Reusable SwiftUI components, consistent spacing and typography, no visual clutter.

## Architecture Principles

- **Small services behind interfaces**. Every piece of business logic lives in a small, single-purpose service. Callers depend on a protocol/interface, never on the concrete type. This keeps code testable and swappable.
- **Interfaces and implementations live apart**. Protocols/interfaces go in their own folder; concrete types go in an `Implementations/` folder. Never mix the two in one place.
- **Small, meaningful functions**. One responsibility per function. If a function or class grows, split it and move the parts to the right folder.
- **No duplication**. Before writing code, look for something that already does it. Extract shared logic into reusable components, helpers, or extensions.
- **Constants and configuration in dedicated files**. No magic strings or numbers inline. Keep them in `Config/AppConfig.swift` (and related files under `Config/`), grouped by domain (API endpoints, cache TTLs, UI spacing, feature limits).
- **Well-organized folders**. Group by feature and by layer (for example `Features/Events/Views`, `Features/Events/Services`, `Core/Networking`, `Core/UI/Components`).

## Cost Discipline (AWS)

- **Cache locally first**. Read from an on-device cache and only hit the network when data is stale or missing. Never poll DynamoDB or other services in a loop.
- **Prefer serverless and pay-per-use**: Lambda, DynamoDB on-demand, API Gateway, Cognito. Avoid always-on compute unless there is a proven need.
- **Batch and debounce** network calls where possible.
- **Question every new AWS resource** on cost before adding it.

## Distributed-Systems Correctness

The backend may run on multiple hosts at once. Every design must hold under that assumption:

- No in-memory state that must be shared across requests. Shared state lives in DynamoDB or another shared store.
- Writes that can race (joining an event when seats are limited) use conditional writes or atomic counters.
- Handlers are idempotent where a client might retry.
- Local caches are treated as hints, never as the source of truth.

## Error Handling

- The iOS app surfaces every user-facing error through the **existing shared error popup component**. Do not create new alert styles per screen.
- Errors are typed and mapped to user-friendly messages in one place.
- Failures are logged with enough context to reproduce them.

## Logging

Log the key events that a future debugging session would need:

- Auth: login success/failure, logout, token refresh.
- Events: create, join, leave, capacity reached.
- Chat: connection open/close, send failure.
- Network: request failures with status code and endpoint.
- Cache: hit, miss, invalidation.

Use a single logging facade (behind an interface) so the sink can change without touching call sites. Never log secrets or PII.

## Testing

- All business logic is covered by unit tests. Services depend on interfaces so they can be tested with fakes.
- The project must be runnable and testable locally without AWS credentials (use local fakes or mocks for AWS-backed services).
- Verify there are no memory leaks (retain cycles, unreleased observers) or connection leaks (unclosed sockets, streams, or clients).

## Workflow: Before Every Commit

1. **Spawn a review agent** to deeply review all uncommitted changes.
2. The agent must check and, where needed, fix:
   - Simplicity and readability. Small functions, clear names.
   - No redundancy. Shared logic is extracted and reused.
   - Interfaces and implementations are in separate folders.
   - Constants and config are in dedicated config files.
   - Logic is covered by tests and tests pass.
   - No memory or connection leaks.
   - Distributed-systems safety (see section above).
   - Errors reach the user via the shared popup.
   - Key events are logged.
   - Everything runs and tests locally.
   - Any UI change is checked as rendered on a simulator, not only by reading the code. Static review has missed layering and safe-area bugs that a screenshot showed immediately.
   - `README.md` reflects the current state of the project.
3. Refactor and re-run tests until the review passes.
4. Only then commit.

## Backend

- **Identity stays in Cognito** (Apple, Google, email + password). The backend never issues credentials; it validates Cognito JWTs (`spring-boot-starter-security-oauth2-resource-server` against the user-pool JWKS) and reads the user id from the `sub` claim. The iOS `AuthService` interface is shaped 1:1 after Amplify.Auth for this reason.
- **Business logic and data live in Laurel**, a Java Spring Boot 4 backend in its own repository (`/Users/makshr/laurel`, GitHub `iris-dc/laurel`) with its own `CLAUDE.md`, Gradle build and GitHub Actions on a Linux runner; iOS CI stays on macOS. It validates Cognito JWTs with `spring-boot-starter-security-oauth2-resource-server`, stores data in DynamoDB (on-demand), and runs as one small ECS Fargate task behind an ALB at `https://api.iskra.red` while traffic is low (watch idle cost against Lambda + SnapStart); the infrastructure is the `iris-dc/rose` CDK repository (`/Users/makshr/rose`). Its `GET /api/me` returns the caller's `sub`. Decided 2026-09-22 with Laurel and rose: the app sends the Cognito **access token** as `Authorization: Bearer <token>`; Laurel validates issuer, expiry, `token_use == access` and `client_id`; anonymous reads (`GET /api/events?scope=upcoming`, `GET /api/events/{id}`) need no token, everything else answers 401 without one.

## Notes for AI Agents

Facts that cost time to learn and are not obvious from the code:

- **Build and test with `./scripts/ci.sh [lint|build|unit|ui|ui-ipad|all]`.** SwiftLint runs in strict mode from `.swiftlint.yml`; fix violations rather than disabling rules. It picks a simulator, writes logs and `.xcresult` bundles to `build/results/`, and `all` runs locally what GitHub Actions runs across jobs (lint, one build for testing, both test bundles without rebuilding, then the iPad class on an iPad). Since 2026-10-09 CI is two stages (`.github/workflows/ci.yml`): `ci.sh build-and-unit` on one runner (lint, build-for-testing, unit; then `archive-products` tars `build/DerivedData/Build/Products/{Debug-iphonesimulator,*.xctestrun}` into `build/products.tgz`, 84 MB, because `upload-artifact` drops executable bits) and a matrix of `ci.sh ui-shard <1|2|3|ipad>` jobs that `restore-products` and run `xcodebuild test-without-building -xctestrun` (no `-scheme`, no package resolution). The one 45-minute job had been outgrown: the UI suite alone takes 22 minutes on a developer Mac (Tournament 337 s, Chat 221, Groups 211, Smoke 187, EventEdit 129, People 91, SignIn 68, Discover 44, Profile 32, Language 25) and longer on a runner. **A new UI test class must be added to `UI_SHARDS` in `ci.sh`**, grouped by running time; `ci.sh lint` (`check_ui_shards`) fails when a `class LilyXxxTests: LilyUITestCase` under `lilyUITests/` is in no shard or in two, or a shard names a class that does not exist, and when the workflow's `shard:` matrix does not list every entry of `UI_SHARDS` (a fourth shard needs a `4` there), so neither can be forgotten. `ui-shard N` runs `UI_SHARDS[N-1]` from the products on disk and needs a prior `build-and-unit` (or `all`); the `.xctestrun` holds `__TESTROOT__`-relative paths, so the archive restores anywhere. A test stage fails with "no tests were executed" when its log shows none of a `Test Case '...' passed` / `Test case '...' passed` line, `Executed N tests` with N > 0, or Swift Testing's `Test run with N tests in M suites passed` summary, because `xcodebuild` exits 0 when `-only-testing` matches nothing. Both test stages run with `-parallel-testing-enabled NO` (2026-09-23 for unit): with clones the unit suite took minutes on a loaded CI runner and one timing-based test failed; without them the same 380 tests finish in under ten seconds and the log switches to the Swift Testing format above. If `xcrun` cannot find `simctl`, `xcode-select` has fallen back to the Command Line Tools; ask the user to run `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`.
- **Never touch CoreSimulatorService with `launchctl` or `pkill`.** It broke the simulator for the whole login session once and required a reboot. If runtimes show as unavailable, ask the user to reboot.
- **Never seed app state with `simctl spawn <udid> defaults write`.** The value lands outside the app container: the app can read it but not clear it, and test clones inherit it. Use the launch arguments in `AppConfig.LaunchArguments` instead (`-reset-session`, `-start-as-guest`, `-mock-location`, `-mock-auth`, `-mock-auth-confirm`, `-mock-auth-fail`, `-mock-events`, `-app-language <code>`). UI tests already pass them. They are honoured in debug builds only (`AppConfig.LaunchArguments.isHonored`; `AppDependencies.makeDefault` reads `CommandLine.arguments` only when it is true), like the local identity header, so a release build cannot be started as a guest or on mock data from the outside.
- **UI tests run with `-parallel-testing-enabled NO`.** Simulator clones intermittently failed to launch the test runner.
- **A UI run can flip the simulator's keyboard language** (2026-10-02: two typing tests failed, the hierarchy dump showed a Russian keyboard, the email field still typed fine because its keyboard type is Latin while the password field got one character). A `typeText` into a field grazes the keyboard switcher, and iOS persists the choice in the simulator's `com.apple.keyboard.preferences` as `KeyboardLastUsed`, so every later test that types into a default-keyboard field fails until it is reset. Diagnose with `xcrun simctl spawn <udid> defaults read com.apple.keyboard.preferences KeyboardLastUsed`; fix with `defaults write ... KeyboardLastUsed -string "en_US@sw=QWERTY;hw=Automatic"` and `KeyboardsCurrentAndNext -array` of the same value, then `xcrun simctl shutdown <udid>` and `boot` (a device preference the run itself changed, not app state, so the rule above does not apply). Driving the switch from a test does not work: the secure and email keyboards show no globe, and on this simulator keyboard elements report frames one screen height too low, so taps on them miss.

- **Animating with `TimelineView` dates:** `context.date.timeIntervalSinceReferenceDate` is about 8e8 s. A phase like `Float(time / period * 2π)` lands near 1e8-3e8, where one `Float` step is 8-32 rad, so `sin` of it is constant for a minute and then jumps; the aurora shipped static because of this and nobody noticed for days. Reduce modulo the period in `Double` first (`time.truncatingRemainder(dividingBy: period)`), then convert. `AuroraGeometry.angle(at:period:)` does this; reuse it. Byte-identical `simctl` screenshots taken seconds apart are the quick test.

- **Backend calls go through one seam.** `Core/Networking/`: repositories depend on the `APIClient` protocol and build an `APIRequest` (method, path, query, optional `Encodable` body, response type); `URLSessionAPIClient` is the only type that knows URLs, headers and JSON conventions (`APIJSONCoding`: ISO-8601 instants, read with or without fractional seconds, written without). Every path lives in `AppConfig.API`, and so does the base URL per build configuration: `localBaseURL` (`http://localhost:8080`; the simulator reaches the Mac's loopback, and ATS exempts unqualified host names, so no plist exception) is `baseURL` under `#if DEBUG`, `productionBaseURL` (`https://api.iskra.red`) otherwise. `api.iskra.red` is defined by the `iris-dc/rose` CDK repo at `/Users/makshr/rose` (Laurel on Fargate behind an ALB; Cognito pool `lily-users`, client `lily-ios`, ids in the `RoseAuthStack` outputs; it resolves only after rose's first-time setup) and takes the Cognito access token the app sends as a Bearer (anonymous reads work without one; see the Cognito note below). A debug build on a physical iPhone reaches a Laurel on the same Wi-Fi through the one launch argument that takes a value, `-api-base-url http://<mac-name>.local:8080` (`AppConfig.LaunchArguments.apiBaseURL`; the value is the next argument, read by `AppConfig.LaunchArguments.value(following:in:)`, which returns `nil` when the flag is missing, last, or followed by another `-` flag); `AppDependencies.apiBaseURL(from:logger:)` takes it when it parses as a URL with a scheme and a host (info `API base URL overridden: <url>` under `.network`), otherwise warns and keeps `AppConfig.API.baseURL`, and hands the result to `URLSessionAPIClient(baseURL:)`. The device shows the Local Network permission prompt once (`INFOPLIST_KEY_NSLocalNetworkUsageDescription` in the app target's Debug block of the pbxproj only, because a release build ignores the argument and must not ship a development-only permission string; there is no build-setting form of `NSAppTransportSecurity`, and a `.local` host name needs none) and the first request may fail before it is answered: pull to refresh. Use `client.send(request, failingWith: fallback)` from repositories: it maps the backend's `{code, message}` codes to `AppError` (`APIFailureMapping.swift`), other `URLError`s to `.network`, everything else to the fallback, and lets cancellation through untouched.
